# rapidtriage output schemas

This document pins the current JSON contract for `rapidtriage` outputs.

Regression coverage lives in `tests/test_rapidtriage_output_samples.py`, which generates fresh command output and compares it against the checked-in sample JSON under `docs/rapidtriage-output-samples/`.

## Placeholder conventions

The sample JSON uses a few placeholders so the examples stay stable across machines:

- `<ROOT>` — scanned fixture root
- `<GENERATED_AT>` — runtime timestamp generated by the command
- `<PLATFORM>` — host platform string from the runtime

### `commercial-readiness`

- Output: `rapidtriage-commercial-readiness.json` and `rapidtriage-commercial-readiness.md`.
- Top-level keys:
  - `command`
  - `generated_at`
  - `backlog_path`
  - `status`
  - `commercial_claim_allowed`
  - `release_claim`
  - `readiness_score`
  - `item_count`
  - `commercial_ready_count`
  - `non_commercial_count`
  - `status_counts`
  - `severity_counts`
  - `category_counts`
  - `maturity_gate_definitions`
  - `maturity_gate_summary`
  - `commercial_blocker_matrix`
  - `commercial_uplift_plan`
  - `validation_evidence_summary`
  - `priority_work_plan`
  - `all_items`
  - `critical_non_commercial_items`
  - `non_commercial_items`
  - `required_release_evidence`
  - `operator_guidance`
- Each row in `all_items` preserves the 120-item commercial parity backlog entry with `number`, `title`, `status`, `category`, `severity`, `remaining_gap`, `commercial_grade_ready`, `commercial_blockers`, `release_gate`, `maturity_gates`, `highest_maturity_stage`, and `next_required_gate`.
- `maturity_gates` always evaluates `implemented`, `usable`, `validated`, and `commercial_grade` in order. A higher gate must not be claimed until every earlier gate passes.
- `maturity_gate_summary` includes `next_gate_samples` and `next_gate_blocker_counts` so reviewers can see where work is blocked without reading all 120 items.
- `commercial_blocker_matrix` classifies every non-commercial item by one or more blocker lanes (`native-parser-depth`, `known-answer-validation`, `large-scale-performance`, `security-legal-assurance`, `platform-release-evidence`, or `external-operator-evidence`), separates internally actionable work from external/trusted evidence requirements, and exposes `top_internal_items` plus `top_external_evidence_items` for the next execution batch.
- `priority_work_plan` lists the next highest-priority backlog items with `current_stage`, `next_gate`, and `required_action`; use `--next-gate validated --limit 10` to focus JSON output on one maturity gate.
- `commercial_uplift_plan` selects the highest-priority non-commercial items, defaults to 70 goals, and splits them into five-item batches. Each goal includes `objective`, `implementation_track`, `acceptance_evidence`, `large_data_strategy`, `remaining_gap`, `external_evidence_required`, and `internal_next_step`. The plan-level `large_data_strategy` records the streaming, checkpointing, cursor API, virtualized UI, and benchmark proof expectations for large evidence sets.
- `validation_evidence_summary` is populated by one or more `--validation-package` arguments. Repeating the option combines batch manifests, records `validation_package_count` and `validation_package_paths`, and maps every passing dataset to its backlog items. Only passing known-answer datasets that explicitly name backlog item numbers can satisfy an item's `validated` gate; this never bypasses `commercial_grade` blockers.
- `--write-known-answer-template PATH` writes a not-run known-answer manifest template plus Markdown sidecar for the selected `--next-gate`/`--limit` items. The generated datasets include `backlog_items`, `required_assertions`, `reference_tools`, `minimum_evidence`, and `status: "not-run"` so validation evidence cannot be accidentally treated as passed.
- `--write-known-answer-template-dir DIR --template-items 1-120 --template-batch-size 5` writes 24 not-run template pairs plus `known-answer-template-batches.index.json/.md`, allowing the 120-item backlog to be validated in repeatable five-item batches.

### `case-search`

- Output: JSON from `rapidtriage case-search`.
- Top-level keys include `summary`, `documents`, `large_case_search_plan`, `review_workflow_summary`, and `matches`.
- `summary.cursor_api.profile_version` is `case-search-cursor-v1`. `summary.next_cursor` is an opaque token for the next page when `summary.has_more` is true; it is bound to the case id, keywords, source filters, metadata filters, review status, and verification status. Reusing it with a different query is rejected instead of restarting silently. CLI uses `--cursor`; the web/API request body uses `cursor`.
- `large_case_search_plan.profile_version` is `case-search-large-case-plan-v1`. Each source row records whether it was requested, whether it used `sqlite-fts5`, `bounded-scan`, or `skipped`, the scan candidate cap, and `partial_coverage_warning` when a table has more rows than the bounded scan window can inspect. Treat bounded-scan warnings as a reason to narrow filters, search an FTS-backed source, or attach further large-case validation evidence before claiming absence.
- `summary.document_error_count` and `documents.errors[]` surface document text extraction failures recorded while importing a completed run into the Case DB. These rows include path, kind, audit citation, target document id, error type/message, and `case-search-documents-partial-coverage` effect. Treat them the same way as completed-run `documents.errors[]`: the Case DB search continued, but the listed documents were not text-indexed and need source-viewer byte-window search, a dedicated parser, or a trusted external extractor before absence can be asserted.

### `source-read`

- Output: JSON from `rapidtriage source-read`.
- `profile_version`: `source-read-v1`.
- Top-level keys include `source`, `analysis_root`, `path`, `relative_path`, `hashes`, `preview`, `source_locator`, `source_citation_package`, `forensic_read_profile`, and `reportability_decision`.
- `preview.preview_type` is one of `text`, `sqlite-table`, `hex`, or `error`; all preview modes are bounded so large files remain responsive.
- `--path archive.zip::entry.json` opens a bounded single ZIP member without extraction. The payload keeps `path` as the archive path, `relative_path` as `archive.zip::entry.json`, and adds `container_relative_path`, `archive_entry`, entry hashes, CRC32, compressed/uncompressed sizes, and `preview.strategy=bounded-zip-entry-text` or a bounded hex preview.
- `source_locator` is the stable viewer locator for the current preview, such as `text-preview`, `sqlite-table-page`, `byte-range`, `zip-entry-text-preview`, or `zip-entry-byte-range`.
- `source_citation_package` uses `source-read-citation-package-v1` and includes copy-safe `citation_text`, `source_locator`, optional `source_sha256`, `snippet`, `snippet_sha256`, `review_note_template`, `package_hash`, and report-selection blockers. Use the `Current-file hit:` template to carry verified source-viewer hits into review marks or report candidates without losing hash/locator provenance.
- `case-review --source-read-json <source-read.json>` imports that `review_note_template`, citation text, and package hash into the Case DB review note so the report history records the exact source-viewer handoff.

### `source-search`

- Output: JSON from `rapidtriage source-search`.
- `profile_version`: `source-search-cli-v1`.
- Searches only one bounded source preview at a time, including `--path archive.zip::entry.json` ZIP members without extraction. SQLite `.db`/`.sqlite`/`.sqlite3` files are opened read-only and scanned across bounded text columns; `--sqlite-row-scan-limit` controls the CLI scan cap and is echoed as `summary.sqlite_row_scan_limit`. Large plain-text sources can be searched by byte window with `--byte-offset` and `--max-search-bytes`; the summary then includes `plain_text_stream_search`, `stream_status`, `byte_offset`, `bytes_read`, `next_byte_offset`, `stream_truncated`, and `offset_semantics`.
- It returns `relative_path`, optional `container_relative_path`, `archive_entry`, normalized `keywords`, `summary.match_count`, `summary.zip_entry_search`, optional SQLite `summary.sqlite_search/sqlite_scanned_tables/sqlite_scanned_rows/sqlite_searchable_columns`, and `matches[]` with `keyword`, `line`, `offset`, `line_offset`, `snippet`, `citation`, `source_path`, plus SQLite `table`, `rowid`, and `column` when applicable. Plain-text stream matches also include `byte_offset` and `window_offset`.
- `source_locator` and `source_citation_package` mirror the matching `source-read` locator so terminal hit context can be verified in the web source viewer and carried into Case DB review notes without losing archive-entry provenance.
- `ready_for_review_note` means the package is usable as a reviewer handoff. `ready_for_court_report` remains `false` until analyst sign-off, original evidence provenance, and any parser-specific validation are attached.

### `large-case-readiness`

- Output: JSON from `rapidtriage large-case-readiness`.
- `profile_version`: `large-case-readiness-v1`.
- `item_numbers`: large-case readiness targets covered by the report: #66, #67, #74, #78, and #79.
- `status`: `internal-evidence-present` only when attached evidence passes the local checks; otherwise `needs-large-case-evidence`.
- `checks[]`: stable pass/fail rows for attached SQLite FTS benchmark JSON, 100k/1M/10M coverage, seeded hit-count parity, p95 threshold, Case DB attachment, FTS tables, and hot-path indexes.
- `benchmarks[]`: normalized summary of each `sqlite-fts-benchmark` JSON with record count, p50/p95 latency, expected-vs-returned hit counts, query-plan hash, and proof manifest hash.
- `case_db_profile`: optional read-only profile of the RapidTriage Case DB, including table counts, FTS tables, index names, SQLite pragmas, and the existing Case DB FTS optimization assessment.
- `search_backend_contract`: the current search backend contract for the representative keyword and corpus estimate.
- `commercial_grade_ready` is intentionally `false` until real 1TB/10TB stress evidence, UI virtualization evidence, cursor API regression evidence, and independent/lab validation are attached.

### `vsc-compare`

- Output: `rapidtriage-vsc-compare.json`
- Top-level keys:
  - `generated_at`
  - `tool`
  - `current_root`
  - `snapshot_roots`
  - `options`
  - `summary`
  - `comparisons`
  - `notes`
- Each comparison includes `snapshot_root`, `snapshot_label`, a per-snapshot `summary`, and change `records`.
- Change records include `status` (`deleted`, `added`, or `modified`), `relative_path`, and `snapshot`/`current` file payloads with path, size, mtime, and optional SHA256.
- `case-db --import-vsc-compare` stores each change record as `vsc-deleted-file`, `vsc-added-file`, or `vsc-modified-file` artifact rows so they can be searched, reviewed, tagged, and included in reports.
- `case-search --metadata KEY=VALUE` can narrow artifact results by promoted metadata such as `event_id=4104`, `event_family=execution`, `channel_family=powershell`, `channel=Security`, `status=deleted`, or `snapshot_label=VSC1`.

### `compare`

- Output: `rapidtriage-compare.json`
- Top-level keys:
  - `command`
  - `generated_at`
  - `options`
  - `inputs`
  - `summary`
  - `results`
- Each result includes `comparison_id`, `status`, `timestamp`, `path`, `left_path`, `right_path`, `summary`, per-field differences, input descriptors, and a bounded unified text diff when both files are safe UTF-8 text under the configured byte cap.
- With three or more input files, `options.mode` is `multi`, `inputs.baseline` is the first file, `inputs.items` lists every file, and `results[]` contains one pairwise comparison from the baseline to each remaining file.
- `case` can bookmark `/results/<index>` rows from compare JSON, and `case-report` renders those reviewed rows under `A/B compare review pivots`.

### `docs`

- Sample: `docs/rapidtriage-output-samples/docs-keyword-search.json`
- Top-level keys:
  - `command`
  - `root`
  - `generated_at`
  - `summary`
  - `manifest`
  - `candidates`
  - `results`
  - optional `extraction_errors`
  - optional `index` metadata when a processed-text index sidecar is written
- `summary` currently records:
  - `candidate_count`
  - `match_count`
  - `supported_extensions`
  - optional `extraction_error_count` and `skipped_document_count` when large/corrupt documents are skipped
- Supported document extensions include text/config/log/data, HTML/RTF, PDF, Office/OpenDocument files, EML/MBOX email, and bounded Outlook MSG/PST/OST string extraction.
- `extraction_errors[]` records path, kind, size, reason, error type, and `document-skipped-search-continues` effect so analysts can see that a missing hit is a partial-search condition, not proof that the keyword is absent.
- Optional `docs-index` sidecars use a processed-text inverted index and do not store full extracted text.
- `rapidtriage docs-index-search <docs-index.json> -k <keyword>` queries that sidecar without re-extracting document text. Output command `docs-index-search` includes matched document locators, text hashes, score, matched terms, result hashes, limit/truncation state, and an explicit `source-viewer-hit-context-validation-required` blocker because analysts must open the source document for context before reporting.

### `files`

- Sample: `docs/rapidtriage-output-samples/files-default-scan.json`
- Top-level keys:
  - `command`
  - `root`
  - `generated_at`
  - `filters`
  - `summary`
  - `known_good_suppression_profile`
  - `known_good_suppressed_candidates`
  - `file_signature_profile`
  - `signature_mismatch_candidates`
  - `candidates`
- Each candidate row currently includes:
  - `path`
  - `name`
  - `extension`
  - `size`
  - `modified_at`
  - `modified_epoch`
  - `categories`
  - `reasons`
- Default categories include documents, archives, databases, executables, emails, AXIOM-aligned disk/mobile images, memory dumps, vehicle exports, and image/OCR candidates.
- File scan summaries include #76 hash-cache, #77 duplicate-detection metadata, and analyst-supplied known-good suppression metadata. `hash_cache_manifest` records `hash-cache-manifest-v1` with hashed paths, basename, path/size/mtime/inode/device cache metadata, hit/miss/invalidation counters, recent cache events, and a manifest hash. `duplicate_group_count` and `duplicate_file_count` summarize `duplicate_content_groups`, while `duplicate_content_manifest` records `duplicate-content-manifest-v1` with stable duplicate group IDs/fingerprints, representative paths, not-suppressed analyst-review policy, and a manifest hash.
- `--known-good-hash-feed` accepts TXT/CSV/JSON MD5/SHA1/SHA256 feeds, bounded ZIP archives containing those feeds, and analyst-supplied NSRL RDS CSV headers such as `SHA-1`, `MD5`, `FileName`, `FileSize`, `ProductCode`, and `OpSystemCode`. Matching candidates get `known_good_status`, `known_good_match`, `known_good_match.source_detail`, and `report_suppression_status`; `--hide-known-good` removes those rows from `candidates` while preserving bounded `known_good_suppressed_candidates`. This is practical De-NISTing/whitelisting support for local feeds, not a bundled NSRL database download/update workflow.
- `known-good-index` writes `known-good-index-v1` JSON with normalized `records`, `feed_summaries`, source feed paths, duplicate/rejected counts, ZIP feed/member counts, NSRL RDS feed/row counts, and `manifest_hash`. The same JSON can be passed back to `--known-good-hash-feed`. NSRL RDS-style `.txt` files such as `NSRLFile.txt` are parsed as structured CSV when their header contains RDS fields, including when they are inside a bounded ZIP feed.
- File candidates with known extensions also get bounded header checks in `file_signature`. PE/PDF/ZIP/SQLite/PNG/JPEG/GIF/OLE/RAR/7z/GZIP magic mismatches are summarized in `file_signature_profile` and bounded `signature_mismatch_candidates`; the row remains visible and marked for analyst review.

### `run`

- Output: `rapidtriage-run-summary.json`, `rapidtriage-run-report.md`, `rapidtriage-run-fingerprint.json`, `rapidtriage-run-checkpoints.json`, and `rapidtriage-parser-scheduler.json`.
- Summary `outputs` includes `fingerprint`, `checkpoints`, and `parser_scheduler` in addition to manifest, docs, files, artifacts, timeline, indicators, report, and extraction manifests.
- Summary `workflow` uses `run-workflow-contract-v1` to expose the GUI-facing single-case pipeline: `ingest`, `extract`, `parse`, `index`, `review`, and `report`. Each stage carries status, step names, output keys, warnings, primary GUI handoff, `handoff_outputs` rows, and `analyst_checklist` rows. `analyst_checklist_summary` aggregates ready/warning/blocked/pending items so the workbench can show what must be opened or resolved before an analyst treats a stage as reliable.
- `rapidtriage-run-report.md` mirrors that checklist in a "Workflow analyst checklist" section so exported markdown preserves the same stage verification obligations shown in the GUI.
- Run output previews use `/api/runs/{run_id}/outputs/{output_name}/preview` and emit `run-output-preview-v1` with bounded renderer metadata, rewritten output download actions, and a reportability decision that treats the preview as an analyst review aid.
- `safety.resume`, `safety.resume_effective`, `safety.resume_disabled_reason`, and `safety.reused_outputs` describe whether stage output reuse was requested, allowed, and applied.
- `resource_caps` records bounded extraction/fingerprint/preview settings, and `safety.artifact_scheduler` records the bounded parallel artifact scheduler strategy.
- `rapidtriage-run-fingerprint.json` stores a bounded source tree fingerprint with scanned file count, total size, latest mtime, max files, truncation status, bounded per-file SHA-256 records, and a content-hash policy.
- `rapidtriage-run-fingerprint.json` stores #68 bounded path/size/mtime fingerprint metadata, bounded content hashes, `incremental-reuse-plan-v1` added/removed/changed/unchanged counts, `incremental-reuse-decision-manifest-v1` per-path reuse/rebuild row hashes, truncation status, incremental-indexing validation guidance, #68 `core_accuracy_gates`, and #68 `commercial_uplift_evidence` with reuse-safety controls and full large-file/large-case blockers.
- `rapidtriage-run-checkpoints.json` stores #70 per-stage output paths, existence, size, reused flag, row hash, status counts, resume assessment, `checkpoint-integrity-profile-v1` head hash, `checkpoint-resume-decision-manifest-v1` per-stage decision row hashes, the input fingerprint used for resume decisions, #70 `core_accuracy_gates`, and #70 `commercial_uplift_evidence` on both summary and stage checkpoint records.
- Run `processing` now includes #71 parser-crash isolation, #72 memory-cap enforcement, and #75 parallel parser scheduler assessments. It also emits `runtime_defensibility_profiles` for #71-#75 so analysts can review parser-crash, memory-cap, preview-sandbox, large SQLite/FTS, and scheduler blockers in one place. Isolated parser failures are written as parser-specific artifact JSON with `parser_errors`, per-error hashes, crash context, parser-error inventory metadata, and `parser-crash-continuation-manifest-v1` row hashes instead of silently dropping the stage. Memory-cap assessments include `memory-cap-policy-profile-v1` plus `memory-cap-stage-telemetry-manifest-v1` with per-stage RSS row hashes, cap configuration, utilization percentage, over-cap state, platform, and breach action. `rapidtriage-parser-scheduler.json` records `parser-scheduler-run-manifest-v1` with worker quota policy hash, deterministic output order, per-parser duration telemetry, event row hashes, reused/completed/error counts, output paths, and a manifest hash.
- `commercial-readiness` emits `review_scale_resilience_progress` for #76-#80, mapping hash cache, duplicate grouping, cursor APIs, UI virtualization, and cancel/retry controls to their primary outputs and required trusted manifests; #80 job payloads include `retry_lineage_profile`, `job-partial-output-policy-v1`, and `cancellation-retry-manifest-v1` hashes.
- `commercial-readiness` emits `validation_spine_progress` for #81-#85, mapping known-answer manifests, parser fixture corpora, FP/FN risk notes, independent validation signoff, and validation package hashes into one evidence chain.
- `commercial-readiness` emits `forensic_integrity_progress` for #86-#90, mapping Case DB custody, acquisition hashes, audit hash chains, reproducibility, and report-item provenance to the trusted manifests required for court-grade claims.
- `commercial-readiness` emits `report_quality_progress` for #91-#95, mapping parser confidence, validation warnings, legal limitation wording, court exhibit packages, and external tool version capture to their report-quality evidence chain and trusted-manifest blockers.
- `commercial-readiness` emits `acquisition_quality_progress` for #96-#100, mapping acquisition metadata, timezone normalization, clock-skew analysis, contamination warnings, and tamper-evident audit bundles to signed-handoff/trusted-manifest blockers.
- `commercial-readiness` emits `release_operations_progress` for #101-#105, mapping Windows signing, macOS notarization, Linux packaging, signed update channels, and local crash reporting to their release evidence chain and external signing/smoke-test blockers. #101 points at `windows_signed_installer.windows_signing_evidence_manifest.manifest_hash` and signing evidence slots; #102 points at `macos_notarized_package.macos_notarization_evidence_manifest.manifest_hash` and notarization evidence slots; #103 points at `linux_package.linux_package_evidence_manifest.manifest_hash` and distro package evidence slots; #104 points at `update-manifest.auto_update_evidence_manifest.manifest_hash` and signed-channel evidence slots; #105 points at `crash-report.crash_export_evidence_manifest.manifest_hash` and redaction/export evidence slots.
- `commercial-readiness` emits `enterprise_governance_progress` for #106-#110, mapping local-only enterprise policy, offline license handling, RBAC policy, multi-user server guardrails, and collaboration audit scope to their trusted governance blockers.
- `commercial-readiness` emits `operations_continuity_progress` for #111-#115, mapping backup/restore, release-note discipline, LTS/hotfix policy, support SLA, and training curriculum to their restore-drill/CI/staffing/training-delivery blockers.
- `commercial-readiness` emits `final_delivery_progress` for #116-#120, mapping analyst quickstart labs, admin deployment guidance, security hardening, malicious-evidence sandboxing, and dependency monitoring to their lab-run/AppSec/corpus/CI/SBOM blockers.
- `macos-live-smoke` emits `readiness_attachment` using `macos-live-smoke-readiness-attachment-v1`. It gives the exact `commercial-readiness --mac-first-evidence ...` command, API query hint, GUI note, supported Mac-preparable backlog item numbers, and required follow-up evidence so a Mac smoke run can be attached without hand-written command reconstruction. `outputs.readiness_attachment_script` points at an executable `attach-mac-evidence-to-readiness.sh` helper that reruns that command locally. When `--case-db <case.db>` is supplied, `inputs.case_db_path_hash` is populated and the embedded `large_case_readiness.case_db_profile` records Case DB FTS/index/table-count evidence without exposing the local path unless `--include-path-details` is explicitly used.
- `commercial-readiness --mac-first-evidence <macos-live-smoke.json>` attaches a `mac_first_evidence_summary` using `mac-first-evidence-attachment-v1`. It hashes each attached evidence JSON, records smoke/large-case status, failed checks, commercial blockers, and supported Mac-preparable backlog areas (#61, #64, #65, #66, #68, #74, #78, #79). This is intentionally preparatory evidence only; it does not satisfy `validated` or `commercial_grade` gates without trusted validation packages and external Windows/hardware/signoff evidence.
- The GUI/API readiness gate also returns `mac_first_evidence_summary` when `/api/commercial-readiness?mac_first_evidence=<path>` is used, so a local dashboard can display attached Mac smoke evidence separately from validation packages.
- Validation packages include #81 known-answer manifest status, #82 parser fixture corpus coverage, #83 parser false-positive/false-negative notes, #84 independent validation report hash metadata, and #85 validation package/hash-manifest assessment fields. The #85 package assessment records required output presence for the generated JSON, Markdown, and artifact manifest; the artifact manifest carries SHA256 and size rows for generated package files.
- Case DB report exports include #86 custody workflow, #87 acquisition hash workflow, #88 export-time audit hash chain, #89 deterministic report reproducibility hash, and #90 source provenance metadata on each selected report item.
- Report items also include #91 parser confidence scoring, #92 validation-required warning metadata, and #93 legal limitation assessment. Reviewer bundles include #94 court exhibit index metadata with exhibit row hashes, selected-evidence manifest hashes, `court-exhibit-package-manifest-v1`, and external signing slots; validation packages include #95 external tool version capture assessment with command argv, version-output hashes, per-tool row hashes, and `external-tool-version-manifest-v1`.
