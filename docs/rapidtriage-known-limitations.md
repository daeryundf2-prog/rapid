# RapidTriage Known Limitations

RapidTriage is a local triage and review tool, not a full commercial forensic suite.

## Evidence Handling

- Mounted folders and exported evidence folders are the most reliable input.
- E01/Ex01 direct handling requires external `libewf` and Sleuth Kit tools. RapidTriage records tool preflight/version data, partition offsets, command history, source integrity, and read-only safety notes, but this remains `commercial_grade_ready=false` until independently validated against broad known-answer and malformed corpora.
- Raw/split images can be extracted with Sleuth Kit (`mmls`, `tsk_recover`) when those tools are installed. Split-part discovery, gap warnings, bounded source hashes, partition metadata, selected offsets, and command history are recorded, but filesystem recovery remains delegated to installed Sleuth Kit behavior.
- E01 extraction writes to `<output>/_e01/fs` (completed runs that recorded `_e01/filesystem` keep resolving to it). After `tsk_recover`, a coverage-gap stage keeps the full stderr (`tsk_recover-stderr.log`, parsed into `extraction-failures.json`), writes one `fls -rpl -z UTC` listing (`fls-rpl.txt`), maps extracted paths to inodes (`extraction-inode-map.jsonl`), recovers files lost to Windows `MAX_PATH` with `icat` into `_e01/long/<inode>.bin` (`long-path-map.json`; cap 50,000 files / 20 GB), lists zero-byte `$DATA` files (`zero-byte-listing.json`), and recovers ADS streams up to 1 MB each into `_e01/ads/` (`ads-map.json`; `Zone.Identifier` first, parsed into `zone-identifier` artifact rows). Limitations: TSK win32 prints names in the ANSI code page, so listing names are decoded best-effort and characters outside that code page appear as `?`; inode and `$DATA` size are authoritative, names are not. Zero-byte rows are deduplicated by inode when the inode map has the file, otherwise by case-insensitive relative path. The files index keeps its category filter, so zero-byte/long-path/ADS rows appear only when they match a selected category. Resumed pre-2026-10 checkpoints only have the 2000-character stderr preview, and the gap stage runs on resume only for direct-EWF (`sleuthkit-direct-ewf`) runs.
- ISO/DMG/WIM/SWM images can be extracted when supported archive tooling is available (`7zz`/`7z`, or `bsdtar` for ISO).
- VHD/VHDX/VMDK/VDI/QCOW/QCOW2 virtual disks can be converted with `qemu-img` and then recovered with Sleuth Kit when those tools are installed. Output includes source and converted-raw integrity, tool preflight, conversion command history, nested raw recovery metadata, and warnings, but snapshot/differencing chains and encrypted/corrupt VM disks are not commercial-grade native handling.
- AD1, L01/Lx01, AFF/AFF4/AFF4-L, XVA, and proprietary mobile acquisition packages are still adapter-detected only and require vendor/tool export first. The evidence preflight records bounded source integrity, warnings, limitations, and export-first guidance; native container parsing is not implemented. Mobile CSV/JSON/JSONL export folders can be imported for normalized review. Memory dumps also receive bounded indicator scanning, not full process reconstruction.
- `rapidtriage evidence PATH --json` now reports `support_level`, `scan_strategy`, `next_actions`, `warnings`, and missing tools so analysts can decide whether to scan directly, install tooling, mount read-only, or vendor-export first.
- XFS/ext partition selection is supported for direct image recovery, but actual XFS file recovery depends on the installed Sleuth Kit build. XVA virtual-server dump workflows are not implemented yet.
- During `rapidtriage run`, evidence tree listings are cached for the duration of the run (each tree is walked once and reused by every provider), so files added to or removed from the evidence root while a run is in progress are not reflected until the next run; standalone collector commands always walk the tree live.
- `rapidtriage run` writes `rapidtriage-run-progress.json` (current stage plus per-provider queued/running/completed/error/reused state and timings) and the web API returns it as `progress` on `GET /api/runs/{run_id}`; it reports provider-level progress only, not per-file throughput or an ETA.
- Run per-kind artifact outputs stream every row to `artifacts/rapidtriage-artifacts-<kind>.jsonl`; the `.json` keeps only a 200-row preview, so tools that read `artifacts` from that JSON directly must follow `records_path` (or use `iter_artifact_output_rows`).
- `rapidtriage-manifest.json` from a run no longer embeds provider `artifacts` arrays; it records counts and the per-kind `records_path`.
- `artifact_record` in run outputs omits ArtifactRecordV1 `fields` (rebuilt from `details` on demand), so raw-JSON consumers that read `artifact_record.fields` must call `artifact_record_with_fields`.
- Per-type constant parts of governance blocks are stored once in `artifact_type_profiles`; raw rows carry only the residue plus `profile_ref`, and indicator extraction scans hoisted text once per profile rather than once per row (indicator source counts for that boilerplate drop accordingly).
- EVTX `eventlog-chunk` and `eventlog-record-candidate` structure rows are off by default (`--eventlog-structure-rows` re-enables them); unparseable record candidates are then only counted on the `eventlog-file` row.
- Decoded `eventlog-event` rows use a compact triage projection by default (message/EventData bounded to 512 characters and 64 values; per-event validation, citation, readiness and BinXML token blocks omitted); use `--eventlog-record-detail full` when those blocks are needed.
- Prefetch `file_reference_candidates` are capped at 64 and `referenced_paths` at 200 per PF (`*_truncated`/`*_total` markers), and prefetch-reference rows carry only a counts summary of the execution-depth manifest.
- During a run, `stat`/`is_file`/`resolve` answers for evidence-snapshot paths are memoized for the run as well, under the same "evidence tree is immutable while a run is in progress" assumption as the path cache.
- PDF text extraction (docs search/index) now keeps only literal strings inside PDF text objects (`BT`…`ET`) of inflated content streams; strings that only appeared in still-compressed bytes or font/image streams (binary noise) are no longer indexed, and CID-font PDFs without literal text yield little or no text.
- `GET /api/runs/{run_id}/capabilities` counts signals over the per-kind preview rows (first 200 per kind) and caches the response per server process until an artifacts output or the run summary changes on disk.
- Images with non-ASCII (e.g. Korean) paths are now decoded by reading the bytes and using `cv2.imdecode`; ASCII paths still use `cv2.imread`.
- The web console polls `GET /api/runs` every 1.5 s while a run is queued/running, every 5 s when idle, and every 15 s while the tab is hidden; run cards show stage, provider counts, and running providers for active runs.
- Run artifact collection streams each provider through temporary JSONL files next to the output (`*.raw.tmp`, then `*.tmp`), so the artifacts directory briefly needs about 2× a provider's final JSONL size in free disk space.
- Runs now enforce a default memory cap of 50% of physical RAM, checked after each artifact provider; a breach stops the run with `progress.error.code = "memory-cap"` (set `--memory-cap-bytes` or `RAPIDTRIAGE_MEMORY_CAP_BYTES`, `0` to disable). Providers already running when the cap trips finish in the background before the process exits.
- Deep deleted-file carving is available as a bounded signature workflow for JPEG, PNG, GIF, PDF, ZIP, 7z, RAR, SQLite and (r3) WAV, MP3, M4A/MP4, DOCX/XLSX/PPTX, HWP/HWPX, EML, PE and EVTX candidates. It is intentionally capped and does not replace full filesystem-aware carving or commercial media validation.

## Parser Coverage

- Browser, recent-file, EventLog export, Registry export, ShellBags export, Prefetch inventory, Task Scheduler XML, Defender MPLog, Firewall W3C log, WER report, and Zone.Identifier sidecar artifacts are implemented first.
- macOS user profile, browser history, quarantine event, TCC privacy permission, LaunchAgent plist triage, and bounded Unified Log/Spotlight/FSEvents/APFS snapshot hint pivots are implemented as a baseline; full native Unified Log, Spotlight, FSEvents, and APFS snapshot semantic decoding remains planned.
- Linux user, shell history, SSH, auth log, auditd, dpkg package status/logs, Docker container config, cron, and systemd triage is implemented as a baseline; full filesystem-level XFS parsing, binary journal replay, RPM database decoding, and deeper container/runtime artifact reconstruction remain planned.
- Full EVTX provider DLL/resource-table message rendering, full deleted-EVTX validation corpus coverage, full MFT attribute-list/data-run validation, Prefetch trace-chain entry interpretation, full Jump List DestList MRU/account metadata decoding, full OS-version validated SAM F/V decoding, SECURITY secret decryption, native Amcache/ShimCache/BAM binary decoding, full SRUDB/Windows.edb table decoding, full proprietary mobile package imports, and live cloud acquisition are roadmap items. Native EVTX record-header scanning emits partial rows with file-header/chunk context, parameter candidates, native message previews, first-pass BinXML token scans, inline scalar decoding for common String/ANSI/integer/bool/float/GUID/SID/FILETIME/SYSTIME/binary values, TemplateInstance IDs, TemplateInstance value spec/value decoding for common scalar types, promoted `Event/System`, `EventData`, and `UserData` fields when recoverable, rendered previews or built-in high-value fallback messages where possible, explicit `message_rendering` provenance/confidence/limitations, explicit `evtx_binxml_status`, `evtx_validation_checks`, `evtx_recovery_context`, separate native `eventlog-chunk` rows, and separate corrupt `eventlog-record-candidate` rows with caution labels, and EVTX-oriented XML/JSON/JSONL/CSV exports from tools such as EvtxECmd, Hayabusa, Chainsaw, or Velociraptor can be imported and normalized; native `$MFT` scans emit bounded FILE-header, common-attribute, timestamp, sequence-validation, and path pivots with commercial-readiness blockers; Prefetch v17/23/26/30/31 (MAM-compressed included, see the R3 O2 section) decodes header, run count, up to eight last-run times, file metrics with MFT references, volume tables and referenced paths natively, with explicit commercial blockers for trace-chain interpretation and PECmd known-answer corpus validation. Account/OS export rows now include separate lifecycle rows, UAC labels, SAM F/V binary presence/byte-count metadata, first-pass SAM F timestamp/RID/UAC candidates, SAM V string candidates, group-membership hints, service/mounted-device/LSA/privilege rows, SECURITY secret value metadata, validation guidance, and explicit commercial-readiness blockers, but full native SAM F/V validation and SECURITY secret decryption remain unimplemented. Direct SRUDB and Windows.edb files are currently inventoried with ESE header metadata, native validation metadata, hashes, and bounded string/path/URL pivots; SRUDB also emits table-family candidates with marker offsets/counts, bounded row string-cluster candidates, validation checks, commercial-readiness blockers, and native pivot rows for review and search, with Windows.edb additionally separating content candidates and likely gather/property/content/deleted-state table families. Jump Lists traverse recoverable OLE/CFB streams, promote embedded Shell Link destinations with stream provenance when recoverable, and emit bounded DestList metadata candidates with validation checks and explicit commercial blockers, but report-grade DestList field semantics, deleted entries, and account attribution still require a dedicated parser. NTUSER/UsrClass user-hive activity pivots are now surfaced for common keys such as UserAssist, TypedURLs/TypedPaths, RecentDocs, Run/RunOnce, Explorer/MRU, ShellBags, MountPoints2, Network, and ComDlg32/OpenSavePidlMRU; native registry hives now also prefer bounded hbin cell walking and emit best-effort key-tree link validation plus key-recovery and value-recovery candidates, but transaction-log replay, binary value decoding, and report-grade deleted-value testimony still require a dedicated registry parser.
- OS/account group membership rows are exported registry hints with SID/name source typing and validation blockers; native SAM group rows are bounded group/alias key candidates only. Full native SAM alias-member reconstruction and SECURITY secret decryption remain roadmap items, and `commercial_grade_ready` stays false for these rows.
- Full native MFT attribute-list extension resolution, report-grade nonresident data-run decoding, full USN replay/correlation, direct VSC mounting from evidence images, service-side AI transcript acquisition, and deeper LotL command correlation are roadmap items. Browser cache/session/extension/sync/cookie/credential stores are inventoried with strict privacy/legal warnings and bounded sample hashes, but RapidTriage does not decrypt or extract raw secret values and does not yet perform full cache-entry/session-restore/schema decoding. Browser-storage AI prompt/answer candidates can be extracted and paired with completeness scoring, source storage provenance, offset candidates, pairing confidence, and orphan counts, but source services should still be validated before report conclusions. MFT/USN CSV/JSON/JSONL exports can be imported and normalized; native `$MFT` and `$J` files currently provide bounded inventory, MFT FILE/header/common-attribute/timestamp/sequence validation pivots with explicit `commercial_grade_ready=false` blockers, path pivots, and recoverable v2/v3 USN rows with cursor/next-cursor metadata, large-record sizing, structural/name/timestamp validation, reason/source/file-attribute flags, delete/rename hints, parser confidence, and USN-specific `commercial_grade_ready=false` blockers. Mounted/exported VSC folders can be compared with `rapidtriage vsc-compare`, and selected deleted/modified snapshot files can be copied with hashes using `rapidtriage vsc-extract`.
- APK inventory/risk triage works on exported `.apk` files and now records component summaries, entry hashes, native architectures, bounded string pivots, validation checks, and explicit commercial blockers. Android app-data export files are inventoried by inferred package/category, but app-specific schemas, encrypted stores, cookies, tokens, and deleted records are not decoded. Cellebrite/XRY/GrayKey/AXIOM-style mobile CSV/JSON/JSONL exports can be normalized into message, contact, call, app, file, account, media, browser, and source-summary rows with source hashes and validation blockers. KakaoTalk, WhatsApp, Telegram, Signal, WeChat, LINE, Discord, and Instagram support is limited to authorized export row normalization and app DB inventory; RapidTriage does not bypass encryption, recover deleted chat rows, or decrypt protected stores. Authorized iOS backup support inventories `Manifest.db`, `Info.plist`, `Status.plist`, and keychain SQLite table/column/count metadata only; RapidTriage does not decrypt keychain or expose secrets. Volatility/Volatility3 JSON/JSONL memory output import and bounded direct memory dump indicator scans are supported.
- Google Takeout-style location/activity JSON and Apple/general account JSON imports are supported. Authorized API collection from analyst-provided request manifests is supported for bounded JSON responses, but RapidTriage does not manage OAuth consent flows, provider-specific pagination semantics, or account acquisition authority.
- Full direct memory process reconstruction, password cracking, live USB collection, and remote-agent collection are deferred until the security and validation model matures. Bounded memory scans can surface process string candidates and checksum-validated BitLocker recovery-key candidates, but Volatility/Volatility3 or equivalent validation is still required for report-grade process reconstruction.
- Image perceptual hashes, similarity buckets, OCR sidecar language hints, translation-needed markers, and rule-based visual classifications are triage hints only; they do not replace full media forensics, OCR quality validation, translation review, visual similarity review, deepfake analysis, or ML classifier validation.
- Parser output should be verified against source evidence before report inclusion.

## Search And OCR

- Case DB search currently uses SQLite FTS5 for documents and artifact metadata, plus metadata scans for file/timeline/review filters.
- Unified search analysis clusters, entities, graph nodes, timeline anchors, and workbook hypotheses are bounded triage aids derived from the returned search matches. They are not a full-case semantic index yet, and every report item still needs source-row, hash, and parser-limitation verification.
- Keyword matching (docs search, docs index v2, unified search, rules, file name/path filters, case DB FTS5) compares Unicode NFC + casefolded text, so NFD (macOS) Korean names/text match NFC keywords and `ß`/`ss` fold together; regex search uses NFC + `IGNORECASE` only, and FTS5 uses NFC with `unicode61` simple case folding (no `ß`→`ss`). Case DBs imported before this change keep NFD text in their FTS indexes and need re-import to make NFD content searchable; new imports store `indexed_document` title/body as NFC (canonically equivalent text), while other case DB tables keep original values. Docs-index v1 files still load, but their NFD terms only match after the index is rebuilt.
- Run unified search (`/api/runs/{id}/search`) uses the run-local case DB `rapidtriage-case.db` (built by the run's `persist` step; `--no-case-db` skips it) and reports `backend: "fts"`. FTS5 narrows candidates by word-prefix tokens and every candidate is re-verified with the scan matchers, so a keyword that occurs only inside a word (`shell` in `powershell`) is not found through the index; fuzzy mode requires the first half of the word to match; regex patterns without a fixed leading word (or with top-level `|`) and keywords without word characters walk the index tables in row order under the time budget. Indexed artifact text is the per-row varying data (per-type profile boilerplate is not indexed); file rows index path/extension/hashes; timeline rows index event type/time/path/summary/source. The index is about 3x the artifact output size (2.9 GB for the 281k-row bsh-subset run).
- Without a case DB (older runs, `--no-case-db`, failed persist) search scans the outputs with `backend: "scan"`: unrequested sources are skipped, each source stops at the remaining `limit`, and a wall-clock budget (`RAPIDTRIAGE_SEARCH_SCAN_BUDGET_SECONDS`, default 20 s, `0` = unbounded, split across the requested sources) ends the scan with `truncated: true` and per-source `scanned` counters, so results can be partial. Re-run the case, or build the index for an existing run with `rapidtriage case-db <output_dir>/rapidtriage-case.db --import-run <output_dir> --case-id <id>` (re-extracts document text and re-hashes files, so it is slower than the persist step).
- OCR depends on local Tesseract availability and quality varies by image.
- Large-case performance must be tracked with `rapidtriage benchmark`.

## Reporting

- Markdown, browser-friendly HTML, portable DOCX, dependency-free PDF, and report export hash manifests are available from the web API and reviewer bundle.
- Reviewer bundles are review packages, not source evidence. They include selected evidence metadata, hashes, review notes, report exports, audit JSON, and a bundle manifest, but they intentionally do not copy the original evidence image.
- Digital signing, notarization, and court-specific certification packets still require external release infrastructure and independent validation.
- Reports should include analyst review notes and hash manifests for defensibility.
- The validation package can attach known-answer manifests, fixture coverage, parser FP/FN notes, independent report hashes, and generated artifact hashes, but it still does not replace actual third-party legal validation, signed installer infrastructure, or a maintained support program.

## Security

- The web UI is designed for localhost use.
- Remote binding requires explicit auth-token configuration. `rapidtriage web --remote` is the supported remote-bind path: it requires an API token (`--token`/`--auth-token` or `RAPIDTRIAGE_TOKEN`/`RAPIDTRIAGE_AUTH_TOKEN`), keeps `/api` token auth and the Host/Origin gates on, and prints a bind warning on non-loopback hosts. `--remote` and `--allow-remote-without-auth` are mutually exclusive.
- Remote mode is still localhost-tool-grade: traffic is plaintext HTTP with no TLS. For real remote access put a TLS-terminating reverse proxy in front, and set `RAPIDTRIAGE_ALLOWED_HOSTS` to the serving hostname so the Host header gate accepts remote requests.
- `--allow-remote-without-auth` sets `RAPIDTRIAGE_DISABLE_AUTH=1` process-wide and disables all `/api` authentication for the server process; when the server is bound to a non-loopback host the CLI prints a warning because any client that can reach the port can read evidence metadata, run scans, and write case databases. Prefer `--auth-token`.
- `/api/case-db/*` endpoints only open or create databases under allowed case-db roots: run output directories known to the job store, the server working directory, `~/.rapidtriage`, and extra roots listed in `RAPIDTRIAGE_CASE_DB_ROOTS` (separated by the platform path separator — `:` on POSIX, `;` on Windows). Out-of-root paths are rejected with HTTP 403. Set `RAPIDTRIAGE_CASE_DB_UNRESTRICTED=1` to restore the previous unrestricted behavior.
- `/api/case-catalog*` endpoints accept a `catalog` path that is confined to the same allowed case-db roots. There is no separate `RAPIDTRIAGE_CATALOG_ROOTS` variable — catalog JSON files are case-management state, so they share `RAPIDTRIAGE_CASE_DB_ROOTS` and `RAPIDTRIAGE_CASE_DB_UNRESTRICTED`. Out-of-root catalog paths are rejected with HTTP 403.
- Do not expose RapidTriage directly to the internet.

## Web Console

- `RAPIDTRIAGE_CONSOLE=v1|v2` (default `v2` since 2026-10-12) selects the console served at `/`: `v2` serves the redesigned console at `/` and keeps the legacy v1 console at `/legacy` for one release before it is removed; `v1` restores the legacy console at `/` with the v2 bundle at `/v2`. Token, Host, and Origin gates are unchanged in both modes.
- Artifact grids sort whole kinds on the server (`GET /api/runs/{id}/artifacts?sort=timestamp|details.<key>&order=asc|desc`, one `kind=` per request). The index is built in a background thread and kept only in process memory (LRU of 8 / 256 MB, at most 2 builds at once, `RAPIDTRIAGE_SORT_MAX_RECORDS` default 5,000,000, `RAPIDTRIAGE_SORT_MAX_TEXT_BYTES` default 256 MB); a restart rebuilds it (about 10 s per 216k-row eventlog). List/object values, inline (non-JSONL) outputs and over-limit kinds answer `status: "unsupported"` with a Korean reason. Multi-key columns (e.g. 실행 파일) sort on their first key, so rows filled from a fallback key sort last; the header hint names the key. Every artifact row carries `record_index` (0-based JSONL record number; blank lines and lines not starting with `{` use no index) and row locators use it; the core bookmark resolver in `case.py` counts every non-blank line instead, so the two only diverge on JSONL files containing non-object lines, which run writers never emit.
- Analysis workbench jobs (`POST /api/runs/{id}/analyses`) never follow symlinks or NTFS junctions/reparse-point directories while walking evidence (carve, VSC discover/compare/extract, memory import); skipped links are counted (`summary.skipped_link_count`, VSC `link_skipped_count`), so content reachable only through a link is not analysed. Carve also prunes `rapidtriage-run*` folders and the run's own output directory. `ntfs-meta` parses at most 8,000,000 MFT records (`MFT_MAX_PARSE_RECORDS`, about 45 bytes plus the UTF-8 name per record for path reconstruction); a larger `$MFT` is extracted but not parsed (`summary.parse_status = "too_large"`). The files-grid NTFS join only uses fully reconstructed MFT paths and skips paths shared by two or more in-use records. Result rows of a queued/running analysis cannot be server-sorted (`sort.status = "unsupported"` until it finishes).
- Analysis workbench path roots: `RAPIDTRIAGE_ANALYSIS_ROOTS` lists extra **input** roots only (evidence; never an output target). Extract outputs (`vsc-extract output_dir`) must be under the run output directory or an extra **output** root in `RAPIDTRIAGE_ANALYSIS_OUTPUT_ROOTS` (same parsing: platform path separator, quotes stripped, relative/UNC/`~` entries ignored with a warning), and are still refused (403) inside any snapshot/scan/source/stage/input root unless that root contains the run output directory and the destination is inside it. `ntfs-meta` accepts an already-extracted raw `$MFT` (`image_path` whose offset 0 holds a FILE record with a 1024/2048/4096-byte allocated size dividing the file size, or `source: "mft"`): it is parsed in place without Sleuth Kit, so there is no `$UsnJrnl`, no partition and no extraction hash (`summary.outputs.mft.sha256 = null`). Carve: structurally rejected header matches (`false-positive-rejected`, length 0) never count toward `max_candidates`; they are counted in `summary.rejected_count` and only listed with `include_rejected: true` (capped at `max_candidates` rows of their own). Cancel is checked per 8 MB scan chunk and per candidate. VSC compare/extract counts are exact over the whole change set; the row listing is capped by `max_records` with deleted, then modified, then added, and a cap hit sets `summary.truncated` with a Korean `truncated_reason` (the CLI `vsc-compare`/`vsc-extract` share the order and exact counts and print a warning). OCR batch ends `failed` (Korean `error`) when the OCR engine is unavailable instead of writing one failed row per image.
- Run plan cancel/skip (R4 V1, plan P2): cancellation is cooperative. A running provider stops at its next row check (every 200 rows or 1 s while it yields rows; a provider that parses for a long time before yielding its first row stops only then). The docs, files, carve, extract, timeline, indicators, persist, triage-flags and derived stages are cancelled only at stage boundaries; a cancel request that arrives while one of them runs lets it finish. `finish` cancels queued providers only. Tasks are one per provider kind or stage (no per-log-file subtasks yet). `--resume` reuses completed provider outputs only; stage outputs are rebuilt after a partial or cancelled run.
- 특이사항(triage flags, `rapidtriage/core/triage_rules/`, catalogue `catalog/*.yaml`) are triage cues, not findings: every flag cites `<rule id>@<version>` and the evidence fields that triggered it, and `provisional` rules are not yet validated on real data. A new run computes them in the `triage-flags` step into a fresh `analyses/run-triage-flags-<time>/` generation (a failure is isolated to that step; older generations are removed best effort); existing runs use the `triage-flags` analysis kind. A source that cannot be read to its end makes the set `partial` (`flags_join.coverage = "partial"` with the incomplete sources): its unread rows carry no flags. The file listing used by "target missing" rules is folded for at most 1,000,000 files rows (`summary.files_context`); beyond that it is treated as unknown and those rules stay silent. EXIF time rules use `OffsetTimeOriginal` when the media parser recorded it (`exif_gps_profile.offset_time_original`) and otherwise assume UTC+9; runs made before that field existed (e.g. run-subset10) always assume +9. Rules read only what the run parsed: NTFS rules ($SI<$FN, ADS) need a completed `ntfs-meta` analysis, policy-dependent sources (4688, 4104, USB device logs, Sysmon) are reported as `policy` counts because absence is not non-occurrence, and "target missing" style rules depend on the files listing (a subset/collection run makes them noisy). The API joins only the newest completed flag set; a `flags.jsonl` over 256 MB is not joined (`flags_join.status = "too_large"`), at most 200,000 flags per rule and 2,000,000 flagged rows are kept (`summary.suppressed`). Server `flag`/`flag_grade` filters and `sort=flags` read the flagged rows by a forward pass over the kind's JSONL (no byte-offset index yet).
- Promoted record-field columns (`cols=` in the URL, per-kind localStorage) are limited to keys without whitespace, `,` or `:`. Meta-tab values longer than 600 characters are folded behind "전체 보기"; copy and search use the full text.
- WER `Report.wer` files (UTF-16 LE with BOM) and the other small key/value sources read by the windows-system provider are decoded with BOM / NUL-interleave detection, so `wer-report` rows carry app, path, fault module and event time; the windows-system default columns show them.
- `/case-db/ensure` on a run recorded before the persist step imports the whole run into the case DB synchronously (minutes for large runs); review marks made meanwhile are queued and applied when it completes, with a status notice.

## Parser-quality r1: core limits (W4)

- Folder inputs are acquisition copies: file host times are copy times. They are kept as `source_file_*` and are not timeline events; filesystem times appear only when a listing (E01 `fls-rpl.txt`) or the NTFS metadata join provides them. The API files join (`api/app/files_ntfs.py`) still adds `$SI`/`$FN` times per page; it is not written back into files.json.
- Timeline coverage is the explicit `TIMELINE_FIELD_MAP` plus the row-level timestamp contracts; artifact types with timestamp-like fields but no mapping are listed in `summary.unmapped_artifact_type_counts` (no event). `registry-key-tree-node` (bulk key inventory) is excluded. EXIF / ZIP DOS times are local wall-clock (`timezone: local-unknown`). PE link times (Amcache `link_date_raw`) are build stamps and may be arbitrary (reproducible builds).
- Indicator extraction caps at 1,000 rows by default (`summary.truncated`, `total_before_cap`); per-indicator sources cap at 10. YARA is not an engine here: `.yar` files import as string rules only. With no rule loaded the output is labelled `지표 후보`.
- Document text: encrypted/DRM documents (HWP password or distribution, encrypted OOXML, PDF `/Encrypt`) are flagged, not decrypted; HWP `PrvText` preview text is indexed when the body is encrypted. Image-only PDFs need OCR (no Tesseract integration in this step). CID fonts without ToUnicode yield no text. Text over 20 % non-printable is rejected (`binary-rejected`). Fuzzy text duplicate grouping compares the first 200 eligible text files (`fuzzy_text_duplicates_truncated`).
- The docs API (`GET /api/runs/{id}/docs`) still pages `results` (keyword hits); listing every candidate needs the route to page `candidates` with a `matched` filter.
- The silent-failure target inventory stops at 20,000 files and then reports `target-inventory-truncated`.

## 통합 보기 (derived tables) and derived columns (axiom-adoption E2)

- 통합 보기 (`rapidtriage/core/derived/`, `GET /api/runs/{id}/derived/{table}`) gathers the values of catalogue columns with a `semantic:` tag; a value appearing under the same normalised form is grouped, which does not mean it is the same person/device. Only columns the grids show are read (no free-text extraction from documents or EventData names the catalogue does not list). Per table at most 200,000 distinct values and an estimated 320 MB for all tables (`capped`, `cap_reason`, `dropped_values`); each value keeps at most 20 sample rows (spread over row source × family), counts are complete. Phone numbers starting with `0` are read as Korean national numbers (+82); a digit string without `+`, `00` or a leading `0` groups as a phone number only with at least 9 digits and phone punctuation (`-`, `.`, space, brackets), so employee numbers and dates (`20240501`, `2024-05-01`) stay separate text values. Paths with a drive letter, UNC prefix or any `\` are Windows paths (case and `/`-vs-`\` ignored); every other `/` path (POSIX, Android `/data/...`) keeps its case and `/`, so `/sdcard/A.jpg` and `/sdcard/a.jpg` are two values, and a bare file name without separators is treated as Windows (casefolded). URL examples keep only `scheme://host[:port]/first-segment` (no user name/password, query, fragment or later segments, which carry share/reset tokens). The table search reads at most 512 characters of each value (value and normalised form, 255 each). A new run builds the tables in the `derived` step (failure isolated, `analyses/run-derived-<time>/`); existing runs use the `derived` analysis kind ("통합 보기 다시 만들기").
- Credentials are never stored in clear: the 자격 증명/토큰 table keeps the masked value (all `•` under 10 characters, else the first two and the last character), the length and the SHA-256 (the parser's own digest/length when it gives one, e.g. browser autofill `value_sha256`). Browser autofill only feeds the table for `mask_reason = secret-field-name`; the parser already keeps no clear autofill value, so those rows group by the parser's digest. The digest and length are taken over the full value (not the 2,048-character display text). The SHA-256 is unsalted on purpose (it matches the parsers' own `*_sha256` values and the same secret across runs and tools), so a short or common secret can be recovered from it by offline guessing: keep a derived set under the same access control as the run output it came from.
- URL 분류 (`core/derived/url_classes.yaml`) is a static domain list with sources; "악성 의심" means a domain often abused (tunnels, paste sites, shorteners), not a malicious verdict. Unlisted hosts are "분류 없음".
- Event-log rows whose parser projects EventData `Owner` into `user_name` (Kernel-WHEA 42, Partition 1006) put numbers / GUIDs into 사람 식별자 under 계정; this is the parser's projection, shown as the grids show it.
- 요약 문장 (`summary_ko`) covers the 60 event IDs of the plan per channel/provider; any other ID reads "요약 없음 (ID n)" and a record without an event ID "없음 — 이벤트 ID 없음". RDP 방향: 원격 데스크톱(rdp-*) rows have no parser yet (the column exists, no rows); event-log rows show the direction in the "RDP 방향" auxiliary column. SAM 계정 "자동 로그온" reads "없음 — 파서 미지원(Winlogon AutoAdminLogon 값이 계정 행에 연결되지 않음)": the registry value is not joined to account rows. EXIF 상태: 동영상·오디오 rows read "없음 — 동영상·오디오에는 EXIF 추출을 하지 않음"; rows of a parser without `exif_gps_profile` read "없음 — 파서가 EXIF 추출 상태를 남기지 않음".

## Windows desktop messengers (`windows-messenger`, r2-communication M1)

- Inventory only, by design (no decryption, key extraction or password cracking — project policy): Telegram Desktop `tdata` (local-key encrypted chats and media cache; only `Downloads\Telegram Desktop` files are listed), WeChat PC `Msg\*.db` / `Multi\*.db` and 4.x `xwechat_files\<wxid>\db_storage` (SQLCipher; only `FileStorage\File` / `msg\file` files are listed; the 4.x layout is from public write-ups and not yet verified on a sample), LINE PC `Data\*.edb`/`*.db` unless the file is plaintext SQLite, the new (Store) WhatsApp Desktop session DBs, and Zoom `*.enc.db`. These apps show a `chat-app-inventory` row with `inventory_only=true` and the Korean reason; no message rows.
- Teams, Slack, Discord, the Electron WhatsApp Desktop and Skype for Desktop keep chats in Chromium IndexedDB/Local Storage (LevelDB). RapidTriage does not decode the IndexedDB record structure (object stores, key paths, Blink/V8 object graphs): it carves V8-serialized `"key" value` runs and JSON fragments by field name (`recovery_method=carved`, `confidence=low`). Field attribution can be wrong when objects nest (a nested `id` keeps the first value), values compressed by newer Chromium IndexedDB value compression or stored as external blob files are not read, and brotli-encoded cache bodies are not decompressed (gzip is, up to 64 gzip members per cache file). Carved rows are candidates for review, not report-grade records.
- `deleted_state` of carved rows is `deleted` only when a newer LevelDB deletion tombstone for the same key was seen; otherwise `unknown` (a carved value may be live or a superseded copy). Slack/Teams/Discord rows rarely carry an owner flag, so `direction` is mostly `unknown`; the late-night and external-transfer rules only read rows whose direction is known.
- Message times: epoch and ISO values with an offset are converted to UTC; a time without an offset is never turned into an instant. Zoom `meeting_saved_chat.txt` lines keep `local_timestamp` (folder date + wall-clock time) and an empty `timestamp`.
- Caps per app folder: 400 files per store directory, 64 MiB read per file, 768 MiB read in total, 50,000 data rows, 20,000 rows per SQLite table, 2,000 saved files listed, files above 64 MiB listed without a hash, 300 JSON decode attempts per value. A cap hit is listed in `caps_hit` and in the kind summary's `collection_notes`.
- The Skype `main.db` mapping follows the legacy schema (Accounts/Contacts/Conversations/Messages/Transfers); other plaintext SQLite DBs (Zoom `zoomus.db`, LINE when unencrypted) are mapped by column names only. LevelDB `.log` CRC32C checksums are verified for the first 1 MiB of each file (pure Python); later records report `leveldb_checksum_ok=null`.

## Desktop cloud sync clients (R2 M4)

- Kind `cloud-sync` (`rapidtriage/artifacts/cloud_sync.py`) reads OneDrive, Dropbox, Google Drive for desktop (DriveFS; legacy Backup and Sync), Naver MYBOX and iCloud for Windows from their local folders only. Nothing is collected from the cloud service, and the files inside the sync folder itself are not re-listed (the files output covers them).
- None of the client databases or logs has a vendor-published schema. Column meanings follow public research and synthetic fixtures (`tests/cloud_sync_fixtures.py`); state values are kept raw (`sync_state_semantics: unvalidated-raw-value`, e.g. OneDrive `fileStatus`) and every row is `validation_required`. Validate against the client version on the evidence before reporting.
- OneDrive: `settings\<Personal|BusinessN>\*.ini` gives the CID, e-mail, tenant and the `library` sync roots; `SyncEngineDatabase.db` (and any settings `*.db`/`*.dat` with a SQLite header) gives `od_ClientFile_Records` rows with paths rebuilt through `od_ClientFolder_Records` (at most 64 levels; a cycle or depth cut sets `path_truncated` and the path stays relative). Legacy binary `<CID>.dat` files are listed, not decoded. An e-mail under an e-mail / UPN key names the account; other e-mails in the ini files (support addresses) stay in `account_emails`. The NTUSER `Software\Microsoft\OneDrive\Accounts` values are not joined to the account rows.
- OneDrive logs (`.odl`, `.odlgz`, `.odlsent`, `.aodl`): gzip bodies are inflated (at most 128 MB per file, 64 MB on disk, 400 files and 512 MB per run). Records are located by the `CC DD EE FF 00 00 00 00` block signature; only the record time (first plausible Unix-millisecond value at +8/+16/+12/+24) and its length-prefixed ASCII / UTF-16 (ASCII + Hangul) strings are read (`recovery_method: log-record-carved`, confidence low). An event is emitted only when the code function name names upload / download / delete / rename / share; a parameter that merely mentions "upload" is not an event. `ObfuscationStringMap.txt` is applied when present. Newer clients encrypt parameters with `general.keystore`; RapidTriage does not decrypt them (policy), so paths and file names are often empty and the rows are then not counted by `cloud.bulk_upload` (`bulk_rule_eligible: false`). ODL sizes are not recovered.
- Dropbox: `info.json` gives the sync root, host id and plan (no e-mail; the account column stays empty rather than invented); `host.db` is used only when `info.json` is absent. `.dbx` stores (config, filecache, ...) are encrypted SQLite and are inventoried only. `instanceN\sync_history.db` is read when it is plain SQLite (`file_event_type` / `direction` / `local_path` / `timestamp` / `other_user`, tolerant column match); `nucleus.sqlite3` and other Dropbox SQLite files get a table inventory only.
- Google Drive (DriveFS): `metadata_sqlite_db` `items` + `stable_parents` give cloud-relative paths (`My Drive/...`), trashed, shared-with-me and owner flags; the older protobuf-only `items` schema is reported as not parsed. `mirror_sqlite_db` `mirror_item` rows carry the file name only. `content_cache` files are counted and sized, never read. The account e-mail comes from key/value tables and `root_preference_sqlite.db` `roots` (a bare drive such as the DriveFS virtual drive `G:` is a mount point and is not reported as a sync root); DriveFS text logs (`Logs\drive_fs*.txt`) are not parsed, so DriveFS has no event rows.
- Naver MYBOX and iCloud for Windows: path signatures plus a SQLite table inventory (no row semantics). MYBOX is recognised only under an install anchor (`AppData`, `Program Files`, `ProgramData`) in a `NAVER\MYBOX` / `NaverMYBOX` / `NDrive` folder, so a browser profile's `https_mybox.naver.com` storage is not a client. An `iCloudDrive` folder under a user profile is reported as the iCloud sync root, volume-relative (`\Users\<user>\iCloudDrive`), because the evidence copy's own location is not the machine's path.
- A client that left only a `Windows\Prefetch\<CLIENT>.EXE-*.pf` file gets one `cloud-sync-inventory` row `executable-trace-only`; with no client at all the kind summary says so (`collection_notes`).
- 증분 실행: 바뀐 파일만 다시 수집하는 delta scope에서는 계정(.ini)·SyncEngineDatabase·로그가 서로를 참조하므로, 일부 파일만 바뀌면 재수집 행에 계정 e-mail·동기화 루트 접두사가 빠질 수 있고(item_path가 sync-root 상대 경로로 남음) 클라이언트 단위 `cloud-sync-inventory` 행은 delta 파일만으로 다시 계산됩니다. 정확한 결과가 필요하면 cloud-sync 종류는 증분 없이 전체 재수집하십시오. `cloud.bulk_upload`는 재사용·재수집 행을 합친 뒤 실행되므로 창 판정 자체는 영향받지 않습니다.
- Caps: 512 MB per SQLite file, 50,000 file rows and 20,000 event rows per source, 5,000 events per log file, 20,000 listed files per client instance and 250,000 rows per run. Each cap and every unreadable source is disclosed on the client's `cloud-sync-inventory` row (`inventory_reasons`, `source_errors`); one corrupt source never stops the other sources or clients.
- `cloud.bulk_upload` (A, provisional) counts one account's distinct uploaded items within 60 minutes (≥ 50 items, or ≥ 2 items totalling ≥ 500,000,000 bytes with each item's size counted once) across `cloud-sync-event`, `cloud-audit` and `cloud-activity` rows. A window made only of carved log records is emitted at grade B with a note (`grade_cap`). Initial sync of a new PC and photo/backup auto-upload are its documented false positives. `cloud.sync_folder_outside_user_profile` (C, provisional) flags a sync root outside `X:\Users\<user>` (Public / Default count as outside), including UNC shares and other drives.
- The older browser-side `desktop-cloud-sync-db` / `desktop-cloud-sync-row-candidate` rows (웹·브라우저 › 클라우드 저장소 동기화) still exist; the same OneDrive/DriveFS database can therefore appear in both places, and a path can be counted twice in 통합 보기.

## KakaoTalk PC messages and Outlook PST/OST, ICS (r2 M2)

- KakaoTalk PC `kakaotalk-message` rows exist only for legacy (pre-2025-08) `chatLogs_*.edb` databases (AES-128-CBC per 4 KiB page) and only when key material the parser already recovers fits: registry `DeviceInfo` (`sys_uuid`/`hdd_model`/`hdd_serial`) + `talk_user_id`-style user-id candidates, stored pragma values, PK strings in collected memory dumps, or operator values in `RAPIDTRIAGE_KAKAO_KEY_HEX`/`_IV_HEX`/`_PRAGMA`/`_USER_ID`. Each candidate is a deterministic derivation checked against the SQLite header of the first page; there is no password cracking, no key search and no user-dir brute force in the run. At most 512 key candidates and 20 user-id candidates are tried, and PK strings are read from at most 2 memory dumps.
- Post-2025-08 (SQLCipher) databases and every case without a fitting key give one `kakaotalk-app-inventory` row per profile with the Korean reason ("복호 키 없음 — …", "대화 DB 없음 — …", "크기 상한 초과 — …", "복호 오류 — …"); key values never appear in rows (counts and SHA-256 of user ids only). Decryption runs in-process with the pure-Python AES (about 1 MB/s; no external program, so the key never appears on a command line): at most 32 MB per database, 128 MB and 300 s of decryption per evidence root; databases beyond a budget, or after the 100,000-message cap (`message_rows_truncated`), get status `budget` ("복호 예산 소진 — …"). Failures carry a fixed Korean reason and `reason_code`, never exception text. The plaintext SQLite is a 0600 temporary file deleted after reading (retried); a failed delete is disclosed as `plaintext_temp_cleanup_failed`.
- Message columns are read by name hints on the `chatLogs` table (`logId`, `chatId`, `authorId`, `type`, `sendAt`, `message`, `attachement`); the room title is not decoded (대화방 = chat id), and the sender is the numeric author id. 방향 is "발신" when the author id hashes to the user id whose key opened the database, else "수신". 삭제 여부 reads "deleted" only from an explicit deleted column; a `type` ≥ 16384 reads "확인 필요(type ≥ 16384 표식)" and is not counted as a deletion.
- `kakaotalk-shared-picture` lists `KakaoTalk_<yyyymmdd>_<hhmmssSSS>[_nn].<ext>` saved/downloaded files anywhere, media in a `카카오톡 받은 파일` folder and media under `AppData\…\Kakao…` (app cache; `.cng` cache files are opaque). The 저장 시각 comes from the file name (local wall clock, time zone unknown); file-system times of folder inputs are copy times and are not used. A picture links to a message only when a decrypted attachment checksum (`cs`) matches its SHA-1/SHA-256/MD5 (`checksum`) or its file name matches an attachment name (`basename`, weaker). At most 20,000 picture rows; files over 64 MB are listed without a hash.
- Outlook PST/OST rows (`email-message`, `email-attachment`, `calendar-event`, `contact`) require libpff `pffexport` or libpst `readpst` on PATH (`/doctor` → `tools:email-pst`). Running the tool is opt-in (project policy: no external programs by default). When it is disabled (the default), the run does not execute pffexport/readpst and each container gets one `email-container-inventory` row with status `disabled` and a reason that says how to enable it ("외부 도구 실행 꺼짐(기본값) — …"). When it is enabled with `RAPIDTRIAGE_EMAIL_EXTERNAL_TOOLS=1`, the run executes the installed pffexport/readpst into a temporary folder (timeout `RAPIDTRIAGE_EMAIL_TOOL_TIMEOUT`, default 900 s) and deletes the export afterwards, so attachment rows keep name, size and SHA-256 but no file. If neither tool is on PATH, the container gets status `tool-missing` ("외부 도구 없음 — …") whatever the setting. In both the `disabled` and `tool-missing` cases the inventory row sits next to the existing bounded string inventory (`email-mailbox`). The pffexport text labels (`OutlookHeaders.txt`, `Recipients.txt`, `Appointment.txt`, `Contact.txt`) are matched by English label aliases and were validated on synthetic trees only; a localized or newer pffexport build may need more aliases. 읽음 comes from `MSGFLAG_READ` (pffexport) or the mbox `Status` header (readpst). Items in `<name>.recovered` read `deleted_state = recovered`, Deleted Items / 지운 편지함 folders `deleted-folder`. Up to 100,000 items per container; unreadable item folders are counted in `item_error_count` and skipped.
- ICS files are parsed in pure Python (RFC 5545 VEVENT: unfolding, escapes, `TZID` through the bundled `zoneinfo` data, all-day `VALUE=DATE`); recurrence rules are kept as text and not expanded, `VALARM`/`VTIMEZONE` are skipped, an unterminated `VEVENT` is dropped. Floating times (no `Z`, no `TZID`) are local wall clock. Files over 32 MB or with more than 20,000 events are cut at the cap.
- `email.external_bulk_attachments` counts attachments per local day (`tz_offset_hours`, default +9) from the mailbox owner's domain (the most common From domain of the mailbox) to recipients outside it; partner exchanges look the same. `email.deleted_folder_recent` measures "recent" against the newest message of the same mailbox, not the acquisition time.

## 브라우저 심화: 캐시 항목·레거시 Edge/IE·업로드 후보 (r2 M3)

- Chromium 캐시(`browser-cache-entry`)는 Simple Cache(`<hash>_0`), 블록파일(`index`·`data_0..3`·`f_*`), Service Worker CacheStorage를 디코드한다. 블록파일은 `index` 해시 표에서 닿는 할당 항목만 읽는다(`recovery_method=parsed`); `index`가 손상되면 `data_1`을 훑어 그럴듯한 항목만 복구한다(`carved`). 해시 표에서 빠진 삭제·축출 항목 잔여물, Simple Cache `_1`(스트림 2)·`_s`(희소) 파일, 미디어 희소 항목(`sparse-entry-not-hashed`), `Code Cache`·`GPUCache`는 읽지 않는다.
- 본문은 저장하지 않는다: 크기, SHA-256(4 MiB까지 전체; 넘으면 `body_sha256` 없이 앞 4 MiB 다이제스트 `body_prefix_sha256`), 앞 256바이트의 SHA-256과 매직 바이트 형식만 남긴다. 해시는 저장된 바이트 기준이라 `Content-Encoding`(gzip·br …)이 걸린 본문은 서버 원본 파일 해시와 다르다. 헤더·본문이 들어 있는 블록 파일(`data_3` 등)이나 `f_` 파일이 취득에서 빠지면 행은 남고 `headers_status`/`body_status`가 `missing-file:<이름>`이다(BSH 서브셋은 `data_3`이 없음).
- 요청 방식은 캐시 키의 업로드 id로 추정한다(0이 아니면 POST/PUT 계열 → `POST`, `method_basis=cache-key-upload-id`); 실제 메서드가 PUT인지는 구분하지 않는다. CacheStorage 항목만 저장된 요청 메서드를 쓴다. 상한: 실행당 캐시 항목 200,000개(공유), 항목별 본문 읽기 4 MiB, 메타데이터 512 KiB, 키 16 KiB, 해시 사슬 64. 손상 항목은 격리되고 디렉터리마다 `browser-parse-error`(`cache-entries-corrupt`, 개수·표본 20개) 한 행으로 남는다.
- 레거시 Edge/IE `WebCacheV01.dat`는 내장 ESE 리더로 `Containers` 표와 `Container_N` 표를 읽어 History·MSHist*→`browser-history`, Content→`browser-cache-entry`, Cookies→`browser-cookie`, iedownload→`browser-download`로 낸다(브라우저 `ie-edge-legacy`). 트랜잭션 로그(`WebCacheV01.jfm`·`V01*.log`)는 재생하지 않아 더티 DB는 최신 행이 빠질 수 있고(요약 `limitations`에 표시), 512 MiB를 넘는 파일은 행 디코드를 건너뛴다(인벤토리 행만). 쿠키 이름·값, DOMStore·feedplat 등 다른 컨테이너 내용은 행으로 내지 않고 요약에 개수만 남긴다. iedownload의 원본 URL·대상 경로는 `ResponseHeaders` 블롭의 UTF-16 문자열에서 고르는 휴리스틱이다. Content 행의 캐시 파일은 `INetCache\IE\<보안 디렉터리>\<파일 이름>`에 있을 때만 해시한다.
- 프로필 경로: Chrome·Edge·Brave·Naver Whale·Vivaldi(`User Data\<프로필>`), Opera·Opera GX(`Roaming\Opera Software\Opera Stable`이 곧 프로필, 캐시는 `Local\…\Opera Stable`). 그 밖의 Chromium 파생 브라우저는 경로를 아직 모른다.
- 업로드 후보(`web-upload-candidate`)는 캐시 항목·방문 기록 URL을 `artifacts/windows/web_upload_patterns.yaml`(서비스·경로 패턴·근거 강도·출처)에 대어 본 단서다. 업로드 흐름의 페이지·엔드포인트가 요청됐다는 뜻이지 어떤 파일이 나갔는지는 말하지 않는다. 웹메일 첨부 업로드 경로 대부분은 공개 문서가 없어 `basis: heuristic`이고, Gmail `attid`는 첨부 열람과 같은 모양이라 `weak`(규칙 `browser.webmail_upload`·`browser.filesharing_upload`는 기본 `medium` 이상만 표시). 업로드 요청은 대개 캐시되지 않으므로 행이 없다고 업로드가 없었다는 뜻은 아니다. 같은 프로필·URL·시각의 행은 한 번만 낸다(실행당 50,000개 상한).

## R2 parser hardening (adversarial review)

- LevelDB: keys over 64 KiB, more than 262,144 entries per block, or a per-block decode budget of max(8× block, 1 MiB) raise a parse error for that block; table decompression is charged at most 256 MiB per table to the app byte budget (`app-byte-cap`); tombstone keys are capped at 200,000 (`leveldb-tombstone-cap`).
- Cache bodies that are gzip with several members are read whole up to the cap or marked `cache_body_truncated`.
- URL fields emitted by messenger, browser and cloud parsers have token-like query values (`access_token`, `sig`, `X-Amz-Signature`, `tempauth`, …) replaced with `[가림]`; the raw value's SHA-256 is kept in `<field>_sha256` for matching (`url_tokens_redacted`).

## Prefetch full decoding and event-log channel nodes (R3 O2)

- MAM-compressed Prefetch (`MAM\x04`, Windows 8+) is decompressed by a pure-Python XPRESS Huffman decoder on every host (`artifacts/windows/xpress_huffman.py`); the ntdll dependency is gone. Output is capped at 16 MB (checked against the declared size before any allocation); a corrupt Huffman table, a truncated stream or a declared size above the cap makes the row `prefetch-invalid-content` with `prefetch_decompression.status` (`decompress-error`, `declared-size-out-of-bounds`, `unsupported-algorithm-<n>`, `crc-mismatch`). Only algorithm 4 (XPRESS Huffman) is handled. Pure-Python speed is about 40 ms per typical PF (≈19 s for 473 compressed PFs on the reviewed subset).
- Trace chains are counted and bounds-checked only (`trace_chain_count`, `trace_chain_status`); their entries (block load counts, flags) are not interpreted. Per-file trace spans come from the file-metrics entries.
- `referenced_files` (decoded file-metrics entries: path, MFT entry/sequence, flags, trace-chain count, `source_offset`) is capped at 1,000 per PF (`referenced_files_truncated` / `referenced_files_total`); every referenced path still becomes its own `prefetch-reference` row. `source_offset` of a MAM-compressed PF points into the decompressed SCCA stream (`source_offset_space = "decompressed-scca"`), not into the file on disk.
- Decoded values are not yet diffed against a PECmd known-answer corpus (`prefetch-trusted-parser-diff-required` stays a report blocker).
- Hardening caps (R3 adversarial review): a `.pf` over 64 MB is not read (`prefetch-invalid-content`, `prefetch_parse_status=size-exceeded`); at most 64 volumes and 4,096 directory strings per volume are decoded (largest on the reviewed subset: 286) (`volume_information_status=declared-count-implausible`, `directory_strings_truncated`), the volume section must declare its size and lie in the file, and a directory table overlapping one already decoded is not decoded again (`directory_table_status=overlapping-table-rejected`); a PF emits at most 65,536 `prefetch-reference` rows (`reference_rows_truncated`); one provider run decodes at most 256 MiB of MAM output in total (`prefetch_decompression.status=run-budget-exhausted`; the reviewed subset needs about 60 MiB), and a declared size needing more 64 KiB blocks than the stream has tables is rejected (`declared-size-exceeds-stream`). The executable's own path is picked from every decoded file-metrics path before the 1,000 cap (`executable_reference_path`); a 29-character header name prefers an `.exe`/`.com`/`.scr` prefix match.
- 이벤트 로그 channel nodes count rows by exact `details.channel` from the kind summary (`channel_counts`, written at collection time). Event-log outputs written before this change have no channel counts: the nodes are hidden with a reason until the eventlog kind is collected again. 기타 채널 holds every channel outside the eleven named groups (e.g. SMBServer, Store, GroupPolicy) and is often the largest group.
- 서비스(SCM) is a view inside 시스템 (System-channel rows whose provider is the Service Control Manager), so it is not part of the channel partition; the console opens every channel node with the server `channel_group=` filter, so page totals equal the node counts.
- The server `channel=` filter is an exact, case-sensitive match on the whitespace-stripped `details.channel` (rows without a channel never match it); `channel_group=` uses the case-insensitive group table of `core/eventlog_channels.py` (`none` = event-log rows without a channel; rows of other kinds never match it, also across kinds). Both are OR-ed when given together.
- `channel_counts` keeps at most 1,000 distinct channel names (each cut to 256 characters); rows of further names are counted per group in `channel_overflow_group_counts` (the group node counts include them, the `channel=` names do not) and `channel_counts_truncated` is set.

## 레지스트리 심화·안티 포렌식 (r3 O1)

- 하위 키 목록의 중복·자기 자신·조상 항목은 건너뛰고, 디코더 하나가 출처당 펼치는 키는 200,000개까지다(`registry_depth.key_budget_exhausted_decoders`). 유형 상한에 닿은 디코더는 그 자리에서 멈춘다. `.reg` 값 하나(이어진 줄 합)는 16 MiB까지이며 넘으면 버리고 `oversized_export_values`로 알린다. `.reg` 인코딩은 BOM이나 UTF-16 NUL 모양이 있을 때만 UTF-16이고, 그다음 UTF-8, CP949 순이다. PCA·심화 행의 `timestamp_kind`: 키 마지막 기록은 `last-written`(PCA Store/Persisted 포함), `last-connected`·`first-connected`·`last-opened`, PcaAppLaunchDic는 `run`, PcaGeneralDb는 `pca-event`.
- 레지스트리 심화 행(`registry_depth.py`)은 하이브(SOFTWARE·SYSTEM·NTUSER.DAT)와 `.reg` 내보내기에서 같은 계약으로 나온다: `registry-network-profile`·`registry-network-share`·`registry-wlan-profile`·`registry-office-mru`·`registry-known-dll`·`registry-default-browser`·`registry-install-state`·`execution-pca`·`execution-feature-usage`. 내보내기 행에는 키 마지막 기록 시각이 없고(`key_last_written_at` 빈 값) `source_offset`은 줄 번호(`source_offset_unit=line`)다. 유형별 상한은 출처(하이브·내보내기)당 50,000행이고, 디코더 하나가 실패해도 나머지는 계속된다(하이브 행 `native_walk.registry_depth`에 오류·상한 기록). 트랜잭션 로그는 재생하지 않는다.
- NetworkList `DateCreated`/`DateLastConnected`는 SYSTEMTIME **현지 시각**이라 오프셋 없이 둔다(`timestamp_timezone=local-unknown`, 타임라인도 `local-unknown`). 서명 키(`Signatures\Managed|Unmanaged`)는 `ProfileGuid`로 프로필과 합치고, 프로필 키가 지워져 서명만 남은 항목은 `profile_key_missing=true` 행이다. Wlansvc 이벤트(8001·8003 등)와의 연결은 하지 않는다(이벤트 로그 행으로 따로 확인).
- WLAN(`WlanSvc\Interfaces\<if>\Profiles\<p>`)의 SSID는 `MetaData\Channel Hints`의 길이+SSID 앞부분으로만 읽는다(그 밖의 구조는 해석하지 않음). 인증·암호화 방식은 프로필 XML(`wifi-profile`)에서 본다. NetworkList의 무선(NameType 71) 프로필은 `registry-wlan-profile`(`source_kind=networklist-wireless`)로도 낸다.
- `registry-network-share`는 MountPoints2 하위 키 전부(`##서버#공유`=네트워크 공유, `{GUID}`=볼륨, 드라이브 문자; `share_kind`로 구분)와 `Map Network Drive MRU`, `Network\<드라이브>`를 낸다. MountPoints2의 시각은 하위 키 마지막 기록(마지막 마운트 근사), MRU는 0번 항목에만 키 시각을 붙인다.
- Office MRU는 `Software\Microsoft\Office\<버전>\<앱>\File MRU|Place MRU`와 `User MRU\<계정>\…`의 `Item N` 값만 읽는다(`[T…]` FILETIME = 마지막 열기). `Item Metadata`·Reading Locations·Backstage 캐시는 읽지 않는다.
- Known DLLs의 기본 목록은 Windows 10/11 x64·ARM64 기본 설치 기준 참고 목록이다: 목록 밖 항목(`known-dll-not-in-baseline`)은 검토 단서이지 변조 판정이 아니다. 기본 브라우저 시각은 UserChoice 키 마지막 기록(설정 시각 근사)이고 `Hash` 검증은 하지 않는다.
- PCA: 레지스트리(`Compatibility Assistant\Store|Persisted`)는 값 이름(경로)과 값 해시만 남긴다(바이너리 구조 미해석, 시각은 키 단위). `PcaAppLaunchDic.txt`·`PcaGeneralDb0/1.txt`(Windows 11 22H2+)는 UTC 시각으로 읽고 64 MiB·200,000줄 상한, 해석 못 한 줄은 `malformed_line_count`로만 센다. FeatureUsage 횟수는 누적 값이며 개별 시각이 없다.
- `registry-install-state`는 App Paths와 MSI `Installer\UserData\<SID>\Products\…\InstallProperties`만 낸다. `Uninstall` 키는 기존 `windows-installed-program` 행으로 남아 중복 행을 만들지 않는다.
- 안티 포렌식 규칙 `antiforensics.tool_present`(B)·`antiforensics.wiper_run_after_incident`(A)는 `catalog/antiforensics.yaml`의 시그니처 목록(도구별 출처 URL)과 정확히 일치할 때만 표시한다: 제품명은 단어 경계 정규식, 실행 파일·서비스는 이름 전체. 이름을 바꾼 도구·포터블 실행 파일의 내용 기반 탐지(해시·버전 정보)는 하지 않는다. 명령줄 정규식은 명령 구간(`&`·`;`·`|`·줄바꿈으로 나눔, 앞의 `&`·`call`·`start`·`cmd /c`·`powershell -command` 제거, 따옴표·경로를 뗀 실행 파일 이름부터)의 **시작**에서만 맞춘다: 다른 명령 안에서 이름만 언급한 경우(`Write-Host "…sdelete…"`)는 표시하지 않는다. 파일 이름 행은 Program Files·Windows 아래에 있어도 표시한다(내장 도구 서명만 파일 이름으로 표시하지 않음). Windows 구성 요소(cipher.exe·BitLocker 마법사)는 파일 이름으로는 표시하지 않고 명령줄(`cipher /w`, `manage-bde -on`)이나 실행 흔적에서만 본다. 와이퍼 규칙은 실행 시각이 있는 행(Prefetch 8회·BAM·UserAssist·PCA·4688)만 쓰며 Amcache·설치 행과 PowerShell 기록(파일 수정 시각뿐)은 실행 시각으로 쓰지 않는다. 사건 시간대(실행 옵션 또는 규칙 params `incident_start`/`incident_end`, 종료 후 `grace_days` 30일)가 없으면 동작하지 않는다.
- BitLocker 복구 키 파일(`bitlocker-recovery-key-file`)은 파일 이름(`BitLocker Recovery Key <GUID>.TXT`, `BitLocker 복구 키 …`, `<GUID>.BEK`)으로 찾으므로 이름을 바꾼 키 파일은 놓친다. 행에는 키 값이 없다(가린 값 `XXXXXX-…-XXXXNN`, 식별자, 정규화한 키의 SHA-256, 파일 SHA-256만). `.BEK`는 메타데이터 머리(식별자·생성 시각)만 읽고 외부 키 바이트는 읽거나 해시하지 않는다.
- 문서 추출(docs 출력·`rapidtriage-docs-index.json`·케이스 DB `indexed_document`)은 파일 이름과 관계없이 **내용으로** 복구 키를 찾아 행과 같은 마스크(`XXXXXX-…-XXXXNN`)로 가린다: 6자리 8묶음(구분자 없음·하이픈·유니코드 대시·공백)이면서 각 묶음이 720885 이하이고 11의 배수인 값(BitLocker 체크섬)만 가린다(일반 긴 숫자는 그대로). 인식된 키 파일 이름이면 체크섬이 틀린 8×6자리 값도 가린다. PowerShell 기록(`ConsoleHost_history.txt`)과 이벤트 로그 행(4688·4104·Sysmon 명령줄, 메시지, EventData)도 행을 쓰기 전에 같은 규칙으로 가린다. `--extract`는 키 파일(인식된 이름·`.BEK`)과 1 MiB 이하이면서 유효한 키가 적힌 파일을 복사하지 않고 매니페스트에 `secret-redacted` 사유와 SHA-256만 남긴다. 식별자(GUID)는 가리지 않는다. 1 MiB보다 큰 파일·압축 안의 파일 원본은 `--extract`가 그대로 복사한다(문서 텍스트는 가림).

## NTFS 타임스탬프 불일치·$LogFile·카빙 확장 (r3 O3)
- 타임스탬프 불일치(`ntfs-timestamp-mismatch`, `ntfs-meta` 분석의 `source=timestamp-mismatch` 행)는 MFT 파서가 낸 ISO 시각(마이크로초 정밀도)으로 판정한다. 1마이크로초 미만 틱(100 ns 단위 1~9)만 있는 FILETIME은 "초 미만 0"으로 읽힐 수 있다. 사유 네 가지(`si_created_before_fn` 60초 초과, `zero_subsecond`, `fn_after_si_modified` $FN 생성·수정이 $SI 수정과 $SI MFT 수정 모두보다 60초 초과 늦음, `future_time` 기준 시각 + 1일 초과; 기준은 이미지(또는 추출한 $MFT) 파일의 수정 시각 = 획득 시각 근사, 미래면 분석 시작이며 `summary.timestamp_mismatch_reference_basis`에 기록)는 선별 단서다. 9999년을 넘는 FILETIME(`0x7FFF…` 등 타임스톰핑 도구 값)은 빈 값 대신 `9999-12-31T23:59:59.999999+00:00`으로 표시되고(`timestamps_out_of_range`) `future_time`에 걸린다. `si_created_before_fn` 기준 초는 카탈로그 규칙 `ntfs.si_before_fn`의 `min_delta_seconds`를 그대로 쓴다: 이동·복사·설치기·압축 해제도 같은 모양을 만든다. 첫 번째 `$FILE_NAME`(선호 이름공간) 하나만 비교하며, 행은 200만 건에서 멈춘다(`summary.timestamp_mismatch_capped`; `timestamp_mismatch_reason_counts`는 쓴 행 기준, `_all`·`timestamp_mismatch_total_count`는 상한 뒤까지 센 값). `ntfs.si_before_fn`·`ntfs.zero_subsecond` 지표는 불일치 행이 아니라 그 행이 가리키는 MFT 행(`mft_row_index`)에 붙는다.
- `$LogFile`(`ntfs-logfile-transaction`)은 RSTR/RCRD 페이지의 픽스업을 검증한 뒤 레코드를 읽는다. 다음 페이지로 이어지는 레코드는 다음 페이지(들)의 데이터 영역에서 이어 붙여(`spans_pages=true`, `spanning_reassembled=true`) 디코드하고, 그 페이지의 자기 레코드는 이어진 부분(8바이트 정렬) 뒤부터 읽는다. 이어지는 페이지가 깨졌거나 없으면 읽은 부분까지만 디코드한다(`spanning_reassembled=false`, `redo_undo_data_partial`, `summary.logfile_unresolved_spanning_record_count`). 픽스업·서명이 맞지 않는 페이지는 건너뛴다(`summary.logfile_corrupt_page_count`, 사유 50건 표본). 첫 재시작 페이지가 깨졌으면 두 번째 재시작 페이지를 쓴다. 재시작 영역 뒤 앞쪽 34개 페이지(LFS 1.1 꼬리 사본·2.0 버퍼 페이지)의 LSN은 기억해 같은 LSN이 뒤에 다시 나오면 한 번만 낸다(`logfile_duplicate_lsn_record_count`). 열린 속성 테이블·트랜잭션 테이블을 재생하지 않으므로 `target_mft_entry`는 후보 값이다: 클러스터 크기는 원시 이미지의 파티션 부트 섹터나 추출 폴더의 `$Boot`에서 읽고(`cluster_size_basis=boot-sector`), 없으면(E01 등) 4096을 가정한다(`assumed-default-4096`); 레코드 크기는 1024바이트 가정이다. 파일 이름·`time_estimate`는 redo/undo 데이터에서 찾은 `$FILE_NAME` 구조(후보)에서 나온다. 이미지 입력은 Sleuth Kit `icat`으로 inode 2를 추출하며, 추출한 `$MFT` 입력은 같은 폴더의 `$LogFile`/`LogFile.bin`(또는 `logfile_path`)을 쓴다. 상한: 1 GiB, 262,144페이지, 200만 행.
- 카빙 서명(wav·mp3·m4a·mp4·docx·xlsx·pptx·hwp·hwpx·eml·pe·evtx)은 구조 검증기와 형식별 최대 길이를 쓰지만 내용 무결성(오디오 디코드, Office 부분 XML, OLE 스트림 전체, PE 서명, EVTX 레코드 체크섬)은 검증하지 않는다. 다른 형식으로 판정된 일치(Office가 아닌 ZIP, HWP가 아닌 OLE, PE 헤더 없는 `MZ`, 프레임 1개뿐인 MP3 동기)는 행 없이 버린다(거부 수에도 넣지 않음). ZIP 하위 형식 판정은 시작 256 KiB 안의 로컬 헤더로 하고, 첫 구성원이 256 KiB보다 커서 판정할 수 없으면 카빙 창의 중앙 디렉터리로 판정한다(중앙 디렉터리가 창 밖이면 형식을 정하지 못해 일반 zip). 중앙 디렉터리의 첫 항목이 후보 자신(오프셋 0, 같은 이름)이 아니면 큰 압축 파일 중간의 구성원이라 버린다. HWP는 카빙 창(`max_carve_bytes`) 안의 FAT·디렉터리·미니 스트림만 보며, FileHeader를 확인하기 전에 창 밖을 가리키면 행 없이 버리고(잘린 .doc 등) 확인한 뒤의 짧은 창은 `length-field-truncated`다. FAT 섹터 수가 창이 담을 수 있는 섹터보다 많거나 DIFAT 항목이 중복·범위 밖이면 거부한다. eml은 `Return-Path:`·`Received: from`·`Delivered-To:`로 시작하는 메시지만 찾고(`From:`부터 시작하는 메시지는 놓침), 끝은 첫 NUL 바이트나 다음 메시지 구분자(빈 줄 뒤의 `Return-Path:`·`Received: from`·`Delivered-To:`, mbox `From 주소 요일 월 일 시:분:초` 줄, 빈 줄 없이 바로 이어진 완전한 머리글 블록; multipart 메시지는 닫는 경계 뒤에서만 찾음)이고(`text-boundary`, 신뢰도 중간) 본문이 잘리거나 뒤 텍스트가 붙을 수 있다. 끝나지 않은 머리글 블록(`eml-header-unterminated`)은 읽은 범위를 점유해 그 안의 `Received:` 줄을 다시 해석하지 않는다. MP3는 ID3 태그가 없으면 Layer III 프레임이 4개 이상(8개 미만은 거부 행) 이어질 때만 후보다. 길이를 스스로 밝히는 서명(walker)은 카빙 창 앞 64 KiB를 먼저 걸어 보고 거부되지 않을 때만 창 전체를 읽는다. 잘렸거나 끝 표지가 없는 후보는 확인한 구조까지만(ZIP 마지막 구성원, BMFF 마지막 완전한 상자, MP3 걸은 프레임) 범위를 점유하고, 선언 길이가 창을 넘는 그 밖의 잘린 후보는 점유하지 않아 뒤 파일이 별도 후보로 나온다. 파일 끝에서 잘린 머리글(`truncated-…`)은 거부 행 없이 버린다. 분석 API(거부 행이 상한에 들지 않음)는 한 소스에서 같은 서명 종류의 거부가 2,000건을 넘으면 그 종류를 그 소스에서 더 평가하지 않는다. 선언 길이 검사: WAV RIFF 크기는 fmt 청크 끝 이상, BMFF 크기 0 상자 앞에 moov/mdat 필요, PE SizeOfHeaders는 첫 섹션 원시 위치 이하·64 KiB+정렬 이하, 창을 넘는 ID3 크기는 프레임 확인 불가로 버림, 청크 0개 EVTX 거부, 창을 넘는 ZIP 주석은 EOCD에서 자름. 카빙 행은 `recovery_method=carved`(거부 행은 `rejected`)와 계열(`family_kind`/`family_artifact_type`)을 갖고, 트리 계열 노드 "복구됨(카빙)"은 카빙 분석 결과를 서버 `signature_kind=`·`recovery_method=` 필터로 보여 준다(아티팩트 출력에 합쳐 쓰지 않음).
- 트리 노드 "타임스탬프 불일치"는 사용 중인 MFT 레코드의 행만 보여 준다(행 API `in_use=true`, 잘못된 값은 한국어 422). 실제 이미지에서는 불일치 행 대부분이 삭제된 레코드의 남은 값이라(검토 이미지 299,652행 중 202,678행) 별도 노드 "타임스탬프 불일치(삭제된 레코드)"(`in_use=false`)로 나눈다. 이 변경 전에 만든 ntfs-meta 작업에는 `source_in_use_counts`가 없어 두 노드의 건수가 "—"로 보인다(행 필터는 그대로 동작).

## 뷰·필터: 행(카드)·지도 대체·연결 그래프·행 조건 (r4 V3)
<!-- r4 V3 (views, filters): start -->
- 지도 대체 보기는 지도 타일과 외부 지도 서비스를 쓰지 않는다(정책). 위치 행은 좌표 표와 0.01° 격자 근접 묶음(약 1.1 km)으로만 보이며, 격자 경계에 걸친 두 점은 다른 묶음이 된다. 묶음을 고르면 그 칸의 상자(`geo=`)로 거른다. 상자는 아래·왼쪽 경계 포함, 위·오른쪽 경계 제외(90°·180°만 포함)라 경계 위 점은 한 칸에만 든다. 경도최소 > 경도최대인 상자는 날짜 변경선(180°)을 넘는 상자로 읽는다. `geo`는 `/artifacts`에서만 받고 `/files`·`/timeline`은 한국어 422로 답한다(파일·이벤트 행에는 좌표가 없다).
- 좌표는 `details.gps_latitude/gps_longitude`, `latitude/longitude`, `lat/lon|lng`, `exif_gps_profile.latitude/longitude`에서만 읽는다. (0, 0)은 좌표 없음으로 본다. 전체 아티팩트 노드의 지도 보기는 서버가 모든 kind를 훑어(요청당 20만 행) 위치 행만 돌려주므로 위치 행이 드문 큰 런에서는 수십 초 걸린다(run-subset10 약 64만 행 → 38 s).
- 업무 외 시간·요일·시간대 조건은 행 시각을 표시 시간대(`tz`)로 바꿔 판정한다. 시각이 없는 행, 그리고 그 시간대로 옮기면 1년·9999년 범위를 벗어나는 행(0001-01-01, 9999-12-31 근처)은 시간 조건을 통과하지 않는다. 오프셋이 없는 행 시각(naive 텍스트)은 `tz`와 상관없이 UTC로 읽는다(콘솔 `parseInstant`와 같음). 아티팩트 행 시각은 `TIME_KEYS` 가운데 처음으로 해석되는 값이다(해석 안 되는 값은 다음 키로 넘어감; 그리드 시각 열은 처음 있는 값을 그대로 보여 주므로 그 값이 해석 불가면 열과 판정 기준이 다를 수 있다). 파일 목록의 시각은 수정 시각이며, 취득 사본(`modified_at_origin=acquisition-copy`)은 NTFS 조인(`ntfs-meta` 분석)이 `joined`일 때의 `$SI` 수정 시각만 쓴다 — 조인이 없으면 시간 조건에 걸리는 파일이 없다. `$SI` 시각은 목록 전체를 조인하지 않고 필터가 취득 사본 행을 판정할 때만 행마다 조인 색인에서 찾는다.
- `to`는 적힌 단위 전체를 포함한다: 날짜만(`2025-05-30`)이면 그날 끝까지, 분까지(`…T09:00`)면 그 분 끝(09:00:59.999999)까지, 초까지면 그 초 끝까지, 소수 초가 있으면 그 시각까지. 콘솔의 시간 범위 입력(분 단위)과 최근 n일 프리셋은 분 단위로 보내므로 끝 분 전체가 포함된다. 시작이 종료보다 늦으면 콘솔은 두 값을 바꿔 보내고 안내한다(서버는 422). `weekday`는 `mon`..`sun` 또는 영어 요일 전체 이름만 받는다. `tz` 오프셋은 ±14:00까지, IANA 이름은 zoneinfo 데이터가 필요하다(Windows는 `tzdata` 패키지 — 의존성에 포함). 읽지 못하는 이름(`Asia` 같은 디렉터리 포함)은 ±HH:MM 오프셋을 권하는 한국어 422다.
- 부분 결과는 행이나 `details`의 `parser_error`=true, 읽기·스캔 상한으로 원본을 덜 읽었음을 뜻하는 잘림 키(`truncated`, `scan_truncated`, `stream_truncated`, `cache_body_truncated`, `key_truncated`, `message_rows_truncated` 등 허용 목록)=true, 실패·잘림·무효·미인식·범위 밖을 뜻하는 `parse_status`(단어 단위, `parsed-no-errors`처럼 부정된 단어는 제외), 성공·`unknown`이 아닌 `decrypt_status`, `coverage=partial`, 유형 이름의 `invalid`/`unreadable`/`parse-error`/`scan-error`로 판정한다. 다 읽은 값을 표시용으로 자른 키(`message_text_truncated`, `value_truncated`, `event_data_truncated`, `event_message_truncated` 등)는 부분 결과가 아니다. 공급자가 이 필드를 쓰지 않는 손상은 잡지 못한다.
- 콘텐츠 유형은 파일 행이면 스캔 범주(영상·음성은 확장자), 아티팩트·타임라인 행이면 유형(`media-image` 등)과 행이 가리키는 파일(`target_path`·`local_path`·`file_path`·`attachment_name` 등)의 확장자로 정한다. 파서가 읽은 컨테이너(`source_path`, 브라우저 기록의 places.sqlite·History, .evtx, 레지스트리 하이브)는 보지 않는다. 행 자신의 경로로 대신 정하는 것은 경로가 곧 내용인 유형(`media-*`, `document-*`, `synthetic-media-*`, `file`, `email-attachment`, `ios-backup-file`, `cloud-sync-file`, `kakaotalk-shared-picture`, `android-apk`, `file-signature-mismatch`)뿐이다.
- 한 kind 노드에서 행 조건을 걸면 서버가 그 kind를 처음부터 훑어 페이지를 만든다(경로 필터와 같음). 행 수가 정해지기 전에는 "n건 이상"으로 보인다. 정렬과 함께 쓰면 조건에 맞는 레코드 집합을, 타임라인 조건은 맞는 이벤트 위치를 (출력 파일 경로·크기·수정 시각, 조건) 키의 작은 LRU(16개, 전체 800만 위치 상한)에 두어 다음 페이지부터는 다시 훑지 않는다 — 첫 페이지는 여전히 전체를 판정한다(합성 50만 이벤트: 첫 페이지 약 5 s, 다음 페이지 0.00 s). 파일 목록 조건은 아직 페이지마다 목록을 훑는다(50만 행 약 1.3 s). 타임라인 히스토그램(`/timeline-histogram`)은 행 조건을 받지 않으며, 콘솔은 "조건 미적용"이라고 표시한다.
- 연결 그래프는 값마다 저장된 표본 원본 행(최대 20행, 계열마다 고르게)만 첫 단계로 쓴다. 표본 밖의 행에 있는 값은 둘째 단계에 나오지 않으며, 노드는 200개(값 노드는 행마다 40개)까지다. 통합 보기 표에서 상한으로 빠진 값은 노드에 나오지만 표로 열리지 않는다.

## R5 L1 — 통신·미디어 앱 (휴대폰과 연결·미디어 플레이어·메일 클라이언트·Viber·Signal·QQ·Facebook Messenger·PSD)

- **휴대폰과 연결(Phone Link/Your Phone, `windows-phone-link`)**: `Microsoft.YourPhone_8wekyb3d8bbwe\LocalCache\Indexed\<GUID>\System\Database\*.db`만 읽는다(평문 SQLite). 앱 버전마다 표·열 이름이 달라 고정 스키마 대신 표 이름(`message`/`messages`/`sms`, `mms`+`mms_part`, `conversation`, `call*`, `contact`+`phonenumber`/`emailaddress`, `photo`/`media`, 이름에 `device`가 든 표)과 열 별칭으로 맞춘다. 공급사 스키마 문서가 없어 열 의미는 공개 연구와 합성 픽스처(`tests/r5_l1_fixtures.py`) 기준이며 실제 표본으로 확인하지 않았다(검증 필요). 정수 시각은 크기로 Windows FILETIME·Unix 초/밀리초/마이크로초를 고르고 고른 인코딩을 `timestamp_encoding`에 남긴다. 오프셋 없는 문자열 시각은 시점으로 바꾸지 않는다. 방향(`type`/`msg_box`)과 통화 유형 코드는 앱이 따르는 Android `Telephony.Sms`·`CallLog.Calls` 상수로 읽고 원래 값을 함께 둔다. 동기화된 사진 파일 자체(캐시)는 열지 않고 메타데이터 행과 기기 폴더 파일 수만 낸다. 상한: DB 512 MiB, 기기당 DB 64개, 표당 50,000행, 기기당 200,000행. 손상 DB는 `phone-link-parse-error` 한 행으로 격리한다. 문자 행은 메신저·메일 › 휴대폰과 연결 문자가 기본 노드이고 모바일 › 휴대폰과 연결에도 교차 노드로 보인다.
- **미디어 플레이어 재생 기록(`media-player`)**: VLC는 VLC 소스로 문서화된 `vlc-qt-interface.ini` `[RecentsMRU]`의 `list=`·`times=`(밀리초)를 읽고 `vlcrc`에서는 `snapshot-path`·`input-record-path`만 인벤토리 행에 적는다. 팟플레이어·곰플레이어·KMPlayer는 값 이름을 공급사 문서나 실제 표본으로 확인하지 못했다(`verification: unconfirmed`). 그래서 값 이름을 가정하지 않고 이름이 recent·remember·history·MRU·playlist·last-play인 키·섹션·값 아래에서 경로나 URL처럼 보이는 문자열만 모은다(`extraction: path-like-value-scan`, 신뢰도 낮음). 그 밖의 위치에 기록하는 버전은 놓치고, 설정 경로가 이 이름 아래에 있으면 재생 기록으로 잘못 잡힐 수 있다. 실제 NTUSER 한 건(bsh-subset)에서 곰플레이어 `Software\GRETECH\GomPlayer\OPTION`의 `sRecentFolder`(최근 폴더)와 `_RECENTMEDIANAME###`(32자리 16진 식별자)·`_RECENTMEDIAPOS###`(이어보기 위치)를 확인했다. 식별자는 경로가 아니라서 `location_kind: hash-only`·`media_hash` 행으로 내며, 해시 알고리즘·입력과 위치 단위는 확인하지 못했다(후보 경로의 해시와 대조 필요). 같은 `GRETECH` 아래 `GOMEncoder` 등 다른 제품의 경로 값은 `product_key`로 구분한다. 팟플레이어 `.dpl` 재생목록은 `N*file*경로` 줄만 읽는다. 행의 `list_last_written`(ini·재생목록 수정 시각, 레지스트리 키 마지막 기록)은 목록 전체의 기록 시각이라 최신 항목의 상한일 뿐 항목별 재생 시각이 아니며, 행 `timestamp`는 비워 둔다. 재생 위치는 VLC(`times=`, 밀리초)와 곰플레이어(`_RECENTMEDIAPOS###`, 단위 미확인 원래 값)만 낸다. 레지스트리 행의 키 시각 타임라인 연결과 곰 `_RECENTMEDIAAUDIOINDEX*`는 아래 `## R6 S1` 참고. `.reg` 내보내기와 곰·KMPlayer의 ini 파일은 읽지 않는다. 상한: ini 4 MiB, 재생목록 8 MiB·200개, 플레이어당 20,000행, 레지스트리 루트당 키 5,000개·깊이 4.
- **메일 클라이언트(`email-clients`)**: Thunderbird는 `Mail`·`ImapMail` 아래의 확장자 없는 mbox(같은 이름의 `.msf` 짝, 짝이 없으면 첫 줄이 `From `인 파일)를 스트리밍으로 읽는다. 빈 줄 뒤의 `From ` 줄만 메시지 경계로 보므로 `>From` 이스케이프 없이 본문 빈 줄 뒤에 `From `으로 시작하는 줄이 있으면 메시지가 갈린다. `X-Mozilla-Status`의 0x0008(expunged)은 압축(compact) 전까지 남은 삭제 메일로 `deleted-or-recovered-candidate`, 0x0001은 읽음이다. 파일당 512 MiB·프로필당 2 GiB·메시지 50,000개·메시지당 32 MiB까지 읽고, 끝까지 읽은 mbox만 SHA-256을 남긴다. `global-messages-db.sqlite`(Gloda)는 파싱한 mbox에 같은 Message-ID가 없는 메시지만 `deleted_state: index-only`(색인에만 있음) 행으로 내며 본문은 색인 텍스트(`messagesText_content`)뿐이다. `abook.sqlite`·`history.sqlite`는 읽고 구형 Mork `abook.mab`는 읽지 않는다(목록만). `calendar-data\local.sqlite` 일정은 PRTime(µs)을 UTC로 바꾸며 `floating` 시간대는 현지 벽시계 시각이다. `prefs.js`는 `mail.identity.*`·`mail.server.*`·`mail.account.*`·`mail.smtpserver.*`만 읽고 이름에 password·token·oauth 등이 든 값은 버린다. `logins.json`·`key4.db`·`key3.db`·`signons.sqlite`는 열지 않고 이름·크기·시각만 프로필 행에 적는다(정책: 자격 증명 비추출).
- Windows 메일(메일 및 일정, 2024-12 지원 종료)은 `LiveComm\<계정>\<버전>\Mail\*.eml`을 읽고, `store.vol`(ESE)은 `ese_native`로 256 MiB까지 표 목록·행 수(최대 200,000행 셈)와 앞 16 MiB의 메일 주소 문자열 후보만 낸다(`email-client-store`, 메시지 행으로 해석하지 않음, 트랜잭션 로그 재생 없음). 그래서 Windows 메일의 폴더 이름(받은 편지함·보낸 편지함 등)과 읽음·플래그는 알 수 없고 폴더는 `Mail`로 남는다. Windows Live Mail은 계정 폴더 아래 `.eml`과 `*.oeaccount` XML의 서버·주소·사용자 이름 태그만 읽고 이름에 `Password`가 든 태그는 건너뛴다. `Mail.MSMessageStore`는 같은 ESE 인벤토리다.
- 같은 메일이 두 번 나오지 않도록 `email` 공급자는 Windows 메일·Live Mail 루트 아래의 `.eml`과 Thunderbird 프로필 아래의 확장자 없는 mbox를 건너뛴다(사용자 홈 판정은 `iter_windows_user_homes`와 같은 규칙). 프로필 밖에 복사된 Thunderbird 폴더(`.msf` 짝이 있는 확장자 없는 파일)는 `email` 공급자가 일반 mbox로 읽고(256 MiB 초과는 문자열 인벤토리), 메일 클라이언트 귀속(`mail_client`·`account`)은 없다. 메일 클라이언트 루트당 메시지 상한(50,000)을 넘은 `.eml`·mbox 메시지는 어느 공급자도 읽지 않으며 프로필 행의 `caps_hit`(`message-cap`)과 kind 요약 `collection_notes`에 남는다. Windows 메일·Live Mail `.eml`에는 읽음·삭제 표시가 없어 `deleted_state`를 비워 둔다(삭제 폴더 이름이면 `deleted-folder`).
- **Viber·Facebook Messenger·Signal·QQ(`windows-messenger` 추가)**: Viber PC `ViberPC\<번호>\viber.db`는 공개 분석 자료의 `Events`·`Messages`·`Contact`·`ChatInfo` 표를 이어 붙인다. `Events.Direction`의 0=수신·1=발신은 공급사 문서로 확인하지 못해 원래 값을 `viber_direction_raw`로 함께 둔다. 통화·시스템 이벤트(메시지 행이 없는 이벤트)는 내지 않는다. Facebook Messenger 데스크톱(2025-12 종료)의 `msys_*.db`는 스키마가 버전마다 크게 달라 `messages`(text·timestamp_ms)·`contacts`·`threads`가 있을 때만 최선 노력으로 매핑하고(`schema_confidence: best-effort-msys`), 없으면 DB 목록·크기만 인벤토리로 낸다. 보낸 사람 이름 외에 소유자를 알 수 없어 방향은 `unknown`이다. Signal Desktop(`sql\db.sqlite` SQLCipher, 암호화된 `attachments.noindex`)과 QQ(`Msg3.0.db`, NTQQ `nt_qq\nt_db\*.db`)는 정책상 인벤토리 전용이다: 키 읽기·복호를 하지 않고, Signal `config.json`은 열지 않은 채 이름·크기·시각만 `key_material_files`에 적는다. QQ `FileRecv`(받은 파일)는 파일 목록 행으로 낸다.
- **PSD 메타데이터(`media-image`)**: `.psd`·`.psb`는 `8BPS` 머리글(크기·채널·비트 깊이·색상 모드)과 이미지 리소스 블록만 읽는다: 0x0424 XMP(CreatorTool, 생성·수정 시각, 문서 ID, `xmpMM:History` 최대 200개, `photoshop:DocumentAncestors` 최대 50개 표시), 0x040C 썸네일(JFIF, 64 KiB 이하만 인라인 미리보기), 0x0422 EXIF. XMP는 XML 파서 없이 정규식으로 읽으므로 비표준 직렬화(중첩 rdf:Description 등)는 놓칠 수 있다. 픽셀·레이어는 해석하지 않아 pHash·디코드 썸네일이 없고 `coverage_status: container-metadata-only`다.

## R5 L3

- URL 분류 `webmail`·`torrent`와 social의 Flickr는 `core/derived/url_classes.yaml`의 대표 도메인 목록이다(분류마다 출처 URL). 토렌트 사이트(특히 국내 사이트는 숫자 접미가 붙은 도메인이 수시로 바뀜)는 목록에 없으면 분류되지 않는다 — 갱신 절차: 공개 목록(TorrentFreak 순위·위키백과 비교표)으로 도메인을 확인해 YAML에 추가하고 `python -m unittest tests.test_r5_l3_web`으로 형식을 검증한다. 같은 도메인을 두 분류에 넣을 수 없다(`mail.naver.com`은 웹메일, `search.naver.com`은 검색). 사내 Outlook Web App은 경로 접두어 `/owa/`로 잡는다: 통합 보기 URL 표는 호스트 단위라 그 호스트의 URL 하나라도 `/owa/`면 호스트 전체가 웹메일(`url_class_basis=path`)이 되고, 도메인으로 분류된 호스트는 도메인 분류가 우선한다. `magnet:` 링크는 info-hash(`btih`/`btmh`)로 `magnet:<해시>` 키가 되며 해시가 없는 magnet은 세지 않는다. 분류는 조사 단서이지 판단이 아니다.
- 지도 URL 위치 후보(`location-url-candidate`)는 Windows 브라우저 공급자의 방문 URL·방문 기록·북마크 행에서만 만든다(macOS·모바일 브라우저 행은 아직 안 봄). 좌표는 URL이 담은 값(장소 핀 `!3d…!4d…`, 없으면 지도 화면 중심 `@위도,경도`, 네이버 `c=` 웹 메르카토르 → WGS84 변환, 카카오 `/link/…,위도,경도`)이며 기기 위치가 아니다(`coordinate_basis`). 새 네이버 지도(`map.naver.com/p/…?c=15.00,0,0,0,dh`)는 확대 수준만 있어 좌표가 없다(검색어만). 카카오 `urlX`/`urlY`(WCONGNAMUL 평면 좌표)는 변환하지 않고 문자열로만 둔다. 단축 URL(`goo.gl/maps`, `naver.me`)은 펼치지 않는다(외부 요청 금지). 후보 행은 원본 행을 다시 적은 것이라 통합 보기 URL 표에 URL을 한 번만 세고(`location_candidates`는 URL 표의 호스트 행에 붙는 개수), 위치(geo)·검색어 열만 의미 태그를 단다. 같은 (브라우저, 프로필, URL, 시각)은 한 행이다. 행 상한 50,000건.
- Chromium 루트 추가(360 Safe Browser `AppData\Roaming\360se6\User Data`, 360 Chrome `AppData\Local\360Chrome\Chrome\User Data`, Yandex, Chromium, Cốc Cốc `AppData\Local\CocCoc\Browser\User Data`, QQ Browser `AppData\Local\Tencent\QQBrowser\User Data`)는 공개 자료 기준 경로이며 실기기 표본으로 확인하지 않았다. 360·QQ 브라우저의 자체 확장 DB(독자 즐겨찾기·클라우드 동기화)는 읽지 않는다.
- Google Analytics 쿠키(`browser-analytics-cookie`, 결정 r5 §2)는 이름 허용 목록 `__utma`·`__utmz`·`_ga`만, 값에서 방문 시각(첫/이전/현재)·세션 수·유입 출처·매체·캠페인·검색어·참조 경로만 꺼낸다. 방문자 ID(클라이언트 ID)·도메인 해시·광고 클릭 ID(`utmgclid`)는 저장하지 않는다. 최신 Chrome·Edge는 쿠키 값을 `encrypted_value`(DPAPI/v10)에만 두므로 대부분 `value_status=encrypted-not-read`(존재만)이다 — 복호화하지 않는다(정책). Firefox `cookies.sqlite`는 평문이라 해석된다. GA4 세션 쿠키(`_ga_<측정 ID>`)와 `_gid`는 읽지 않는다.
- EGG(알집) 목록은 ESTsoft 공개 명세의 헤더 배치(EGGA 머리, 파일·파일 이름·Windows/POSIX 정보·암호화·분할·솔리드 확장 헤더, 블록 헤더)를 따르지만 **실제 알집 생성 표본으로 대조하지 않았다**(합성 픽스처만). 특히 LZMA 블록의 앞 4바이트+속성 5바이트 배치는 추정이다(실패하면 `decompress-failed`로 목록만). 저장·Deflate·bzip2·LZMA 블록은 암호화·솔리드가 아닐 때 메모리에서만 풀어 CRC를 확인하고 64 MiB 이하 항목(최대 200개)의 SHA-256을 낸다(디스크에 쓰지 않음). AZO·암호화(ZIP 2.0·AES·LEA)·솔리드 항목은 목록만 낸다. 분할 압축은 R6 S1부터 형제 볼륨을 이어 읽는다(아래 `## R6 S1`). 파일 이름 헤더가 암호화된 항목은 이름 없이 `header_encrypted`로 표시한다. 압축 폭탄 방지: 블록 비율 1,000배·항목 64 MiB·항목 20,000개 상한.
- ALZ는 `unalz` 구현의 배치(`ALZ\x01`, `BLZ\x01` 로컬 헤더, `CLZ` 중앙 디렉터리)로 목록만 낸다(이름 cp949, DOS 시각=로컬 시각). 분할 ALZ(`.a00`…)와 압축 해제는 하지 않는다.
- ISO는 ISO 9660 기본 볼륨 서술자와 Joliet 보조 서술자(UCS-2 이름 우선)의 디렉터리 레코드만 걷는다. Rock Ridge(POSIX 이름·권한), El Torito 부팅 이미지, 멀티세션, UDF 디렉터리는 해석하지 않으며 UDF는 있음만 표시한다(UDF 전용 이미지는 항목 0). 항목 20,000개·디렉터리 5,000개·깊이 24 상한, 자기 자신을 다시 가리키는 디렉터리는 건너뛴다. ISO 안 파일의 MOTW 우회는 같은 ISO 경로의 Zone.Identifier 행과 직접 대조해야 한다(자동 연결 없음).
- P2P(`p2p` kind): qBittorrent `BT_backup\*.fastresume|*.torrent`, µTorrent·BitTorrent `resume.dat`(경로에 uTorrent/BitTorrent가 있을 때), FrostWire 폴더의 `.torrent`·`.resume`, 그 밖의 모든 `.torrent`(5,000개 상한), eMule `known.met`·`*.part.met`·`AC_SearchStrings.dat`·`config\preferences.ini`. 클라이언트 버전별 키 이름은 공개 문서·소스 기준이며 실제 사용 표본으로 확인하지 않았다. 업로드·다운로드 양은 클라이언트 누적 통계라 상대·시각별 전송 내역이 아니다(유포 규칙 B는 누적 업로드량이 있다는 정황). 트래커 URL은 `스킴://호스트[:포트]`만 남긴다(비공개 트래커의 passkey 비추출). eMule 사용자 해시·서버 목록·`cancelled.met`·`clients.met`, LimeWire(`downloads.dat` 자바 직렬화)와 Shareaza·Vuze는 읽지 않는다. `AC_SearchStrings.dat`에는 검색 시각이 없다(목록 순서만).
- adb 백업(`.ab`)은 헤더 → zlib → tar를 메모리에서 흘려 읽어 `android-backup`(헤더·항목 수·앱 수)과 `android-backup-member`(앱 패키지·영역·경로·크기·시각·SHA-256) 행을 낸다. 항목 파일을 디스크에 풀어 두지 않으므로 기존 `android-app-data` 행이나 모바일 메신저 파서는 백업 안 DB를 직접 읽지 않는다 — 64 MiB 이하 SQLite 항목(최대 200개)만 임시 사본으로 스키마·행 수를 목록화한다(값 미추출). (R6 S2에서 런 출력 폴더 사본 → 기존 앱 파서 전달이 추가됨: 아래 `## R6 S2` 참조.) AES-256 암호화 백업은 존재·헤더(PBKDF2 반복 수)와 사유만 낸다: 솔트·IV·마스터 키 블롭은 행에 넣지 않고 비밀번호 대입은 하지 않는다. 상한: 항목 50,000개, 해제 8 GiB, 비율 200배.
- Google 문서 바로가기(`.gdoc`·`.gsheet`·`.gslides`·`.gdraw`·`.gform` 등)는 JSON의 문서 ID·계정·URL만 `cloud-sync-file` 행(`recovery_method=stub-json`, `google_doc_type`, `google_doc_url`)으로 낸다. 문서 내용은 클라우드에만 있다. 링크 공유용 `resource_key`는 복사하지 않는다(있음만 `resource_key_present`). DriveFS 항목은 `mime_type`이 `application/vnd.google-apps.*`일 때 같은 종류·URL을 붙인다.
- URL 카빙(`url-carve` 분석, `carved-url-candidate`)은 파일 이름으로 소스를 고른다: `pagefile.sys`·`swapfile.sys`, 이름에 `unalloc`·`blkls`·`freespace`가 든 미할당 덤프(`.unalloc`), 선택 시 `.dmp`·`.mem`·`.vmem`·`.raw`·`.lime` 메모리 덤프. 이 파일 소스들은 이미지에서 미할당 영역을 직접 잘라내지 않는다(blkls 등으로 만든 덤프를 입력에 두거나, R6 S2의 `image-unallocated` 소스를 쓴다 — `## R6 S2`). `hiberfil.sys`는 압축되어 있어 보지 않는다. ASCII URL과 ASCII 범위 문자로 된 UTF-16LE URL만 찾는다(한글이 그대로 든 UTF-16 URL·퍼센트 인코딩 안 된 IDN은 잘림). 호스트가 `a.b` 형식(마지막 이름 2자 이상 영문)이거나 IP일 때만 후보이며 같은 (URL, 인코딩)은 한 행(첫 오프셋, 소스 안 출현 수)이다. 주변 바이트(페이지 본문)는 저장하지 않고, 토큰 질의 값은 가리며 원본 URL SHA-256만 남긴다. 오탐(코드·문서 속 URL, 인증서 URL)이 많다 — 방문 증거가 아니다. 후보 50,000건(최대 500,000) 상한.

## R5 L2
<!-- r5 L2 (OS, system, policy presence): begin -->
- 공통: 새 행(`startup-item`·`registry-logon-banner`·`ssh-known-host`·`ssh-authorized-key`·`ssh-client-session`·`ssh-key-file`·`ssh-server-config`·`office-identity`·`office-backstage-item`·`desktop-wallpaper`·`vm-config`·`crypto-wallet-presence`·`credential-store-presence`·`av-detection-log`·`ntfs-volume-information`)은 레지스트리 심화(`registry_depth.py`, 하이브·`.reg` 내보내기)와 파일 모듈(`system_extras.py`, `windows-system` kind; 볼륨 정보만 `windows-filesystem` kind)에서 나온다. 파일 모듈은 유형별 20,000행, 설정 파일 4 MiB, JSON 16 MiB, 로그 64 MiB·50만 줄, 키 파일 1 MiB까지 읽고, 해석하지 못한 파일은 `parse_status=error` 행 하나로 남기고 다음 파일로 넘어간다. 파일 수정 시각(`source_file_mtime`)은 취득 사본의 시각일 수 있어 행 시각으로 쓰지 않는다.
- 시작 프로그램(`startup-item`): `Explorer\StartupApproved\{Run,Run32,StartupFolder}`(NTUSER·SOFTWARE)의 첫 바이트가 `02`/`06`이면 사용, `03`/`07`이면 사용 안 함이고, 그 밖의 값은 `알 수 없음`으로 원래 바이트(`state_byte_hex`)와 함께 둔다(검토 이미지에서 `01`이 Teams 제거 항목에 나타났으나 의미를 확인하지 못함). 사용 안 함 시각은 4–12바이트 FILETIME(`disabled_at`, `timestamp_kind=disabled`), 사용 중 항목의 시각은 키 단위 마지막 기록이다. 명령은 같은 이름의 `Run` 값으로만 잇는다(`run_value_found=false`는 Run 값이 지워진 잔존 승인 항목). `StartupFolder` 값은 파일 이름뿐이라 시작프로그램 폴더 파일 행과 이름으로 대조해야 한다. 폴더 파일 행의 시각은 LNK에 기록된 대상 파일 시각이며 폴더에 추가된 시각이 아니다. 작업 스케줄러·서비스·WMI 구독·RunOnce는 기존 행에서 본다. 규칙 `execution.startup_user_path`(B)는 사용 안 함 항목을 표시하지 않는다.
- 로그온 배너(`registry-logon-banner`): `Policies\System`과 `Winlogon`의 `legalnoticecaption`/`legalnoticetext`가 둘 다 비면 행이 없다. 본문은 4,000자에서 자른다(`banner_text_truncated`). GPO 적용 이력은 보지 않는다.
- SSH: OpenSSH `known_hosts`의 해시 항목(`|1|…`)은 호스트 이름을 복원하지 않는다. `config`의 `Include`는 따라가지 않고 `Match` 블록은 세션 이름으로만 보인다. PuTTY·WinSCP의 `SshHostKeys` 값은 PuTTY 형식이라 SHA256 지문을 계산하지 않고 값의 SHA-256만 둔다. 개인키 파일(`id_*`, `ssh_host_*_key`, `.ppk`, `.pem`/`.key` 중 개인키 머리글)은 존재·형식·암호화 여부·**공개키** 지문만 남긴다: OpenSSH 형식은 암호 방식과 공개키 부분까지만 디코드하고 개인 부분은 읽지 않으며, 개인키 파일은 내용 해시도 저장하지 않는다. PEM은 `Proc-Type: 4,ENCRYPTED`, PKCS#8은 머리글로 암호화를 판정한다.
- 비밀번호 값: WinSCP `Password`, PuTTY/WinSCP `ProxyPassword`·`TunnelPassword` 등은 행에 복사하지 않고 `password_saved`/`proxy_password_saved`만 낸다. 같은 값은 하이브 문자열 피벗(`registry-hive-strings`), `.reg` 내보내기 행(`values`, 자리 표시 `(비밀번호 값 — 저장하지 않음)`), 문서 추출(docs 출력·색인·케이스 DB의 `WinSCP.ini`/`.reg` 본문)에서도 지운다. 삭제된(빈 셀) 값 복구 후보(`registry-value-recovery-candidate`)에 남은 **과거** 비밀번호 값은 현재 값과 다르면 거르지 못한다.
- Office: `Office\<버전>\Common\Identity\Identities\<id>`만 읽는다(`Roaming\Identities`, 라이선스·토큰 캐시는 읽지 않음). `BackstageInAppNavCache\**\*.json`은 공개 자료로 스키마를 확인하지 못해 키 이름(`Url`/`Path`/`DisplayName`/`LastModified`/`LastModifiedBy` 등, 대소문자 무시)으로 항목을 찾는다(`field_extraction=heuristic-keys`, 파일당 5,000항목·깊이 32). Office 버전이 바뀌면 열이 비거나 다른 객체가 행이 될 수 있다.
- 네트워킹 이벤트 채널(`evt-ch-networking`, 채널 그룹 `networking`): NetworkProfile·WLAN-AutoConfig·Dhcp-Client·Dhcpv6-Client·DNS-Client·Bits-Client·VPN-Client·RasAgileVpn·NCSI 채널이다. 10000/10001 등 이벤트 ID별 해석은 기존 이벤트 행 그대로이며, RasClient는 응용 프로그램 채널(공급자 RasClient)에 기록되므로 `응용 프로그램`에 남는다. 이전에 `기타 채널`이던 Bits-Client 행은 `네트워크`로 옮겨진다.
- NTFS 볼륨 정보(`ntfs-volume-information`): 증거 트리에 있는 `$Boot`(VBR 512바이트)와 같은 폴더의 `$MFT` 3번 레코드(`$Volume`: `$VOLUME_NAME`, `$VOLUME_INFORMATION` 버전·플래그)만 읽는다. 이미지를 직접 열지 않는다(R6 S2부터 `ntfs-meta`가 `$Boot`를 추출해 분석 행을 내고, 다음 런에서 분석 폴더도 읽는다 — `## R6 S2`). MFT 레코드 크기는 `$Boot`에서 읽고 없으면 1,024바이트로 가정한다. `volume_serial_number`는 8바이트 VSN의 하위 4바이트(`%08X`, LNK·Prefetch와 같은 표기)이며 의미 태그 `device`로 통합 보기 › 장치 식별자에서 LNK 볼륨 시리얼과 만난다. 검토 서브셋에는 `$Boot`/`$MFT`가 없어 행이 0이다.
- LogMeIn: 경로에 `logmein`·`lmiguardian`·`lmi_rescue`가 들어간 파일을 기존 원격 제어 행(`third-party-remote-control-artifact`, `product=logmein`)으로 낸다. 로그 줄은 공통 세션 후보 추출(시각·IP·ID 문자열)만 하며 LogMeIn 전용 로그 형식은 해석하지 않는다. 국내 원격 지원(알서포트 RemoteCall)은 경로를 확인하지 못해 넣지 않았다.
- 백신 로그(`av-detection-log`): McAfee Endpoint Security `*_Activity.log`와 VirusScan Enterprise 8.x(`OnAccessScanLog.txt`·`OnDemandScanLog.txt`·`AccessProtectionLog.txt` 등)만 읽는다. 실제 로그로 형식을 대조하지 못했다: 줄 첫머리 시각(`MM/DD/YYYY`·`YYYY-MM-DD`, AM/PM·오전/오후, 현지 시각·시간대 없음)과 탐지 단어(detected·quarantined·deleted·cleaned·blocked·infected·trojan·탐지·격리·차단·삭제; 모듈 이름에 흔한 threat·virus는 쓰지 않음, "no threats found"류 제외)가 있는 줄만 행이 되고, 탭 구분 줄은 열 순서로, 그 밖은 텍스트 패턴(`contains …`, `Threat Name:`)으로 위협명·경로를 찾는다(`field_extraction`). 원문(`message`)과 함께 검토해야 한다. **AhnLab V3 로그는 넣지 않았다**: 탐지 기록 위치·형식(제품 버전별 DB/암호화 여부)을 공개 자료로 확인하지 못했다(미확인, 후속 과제).
- 가상 머신(`vm-config`): `.vmx`는 허용 목록 키(표시 이름·게스트 OS·디스크·MAC·공유 폴더·UUID·암호화 표시)만, `preferences.ini`(`pref.mruVM*`), `inventory.vmls`(`vmlist*`), `VirtualBox.xml`(`MachineEntry`), `*.vbox`(Machine·HardDisk·Adapter·SharedFolder·Snapshot)를 읽는다. 가상 디스크(`.vmdk`/`.vdi`) 내부와 Hyper-V `.vmcx`(이진 형식, 존재·GUID만)는 해석하지 않는다. 규칙 `antiforensics.vm_present`(C)는 Docker Desktop·WSL·Windows Sandbox 유틸리티 VM을 이름으로 제외한다.
- 암호화폐 지갑(`crypto-wallet-presence`, 정책 제외 행): 키·시드·xprv·키스토어 내용은 행·문서 색인·`--extract` 어디에도 남기지 않는다. Bitcoin Core `wallet.dat`(이름으로 어디서나 찾음; BDB/SQLite 머리글, 앞 16 MiB에 `mkey` 레코드가 있으면 암호화로 표시하는 근사), Electrum(평문 JSON이면 `addresses`의 공개 주소만, 최대 20개; `keystore`는 행에 넣지 않음; `BIE1` base64는 암호화), Ethereum keystore(파일 이름의 공개 주소), Exodus·Ledger Live·Atomic·Wasabi·Monero·Coinomi·Guarda·Jaxx는 존재·파일 수·크기만이다. 브라우저 확장 지갑은 Chromium 계열 프로필의 `Local Extension Settings`·`Sync Extension Settings`·`Extensions`·`IndexedDB\chrome-extension_<id>_0.indexeddb.*`에서 확장 ID 목록(MetaMask·Phantom·Kaikas·Coinbase·Trust·Binance·TronLink·Ronin·Keplr·OKX·Rabby·Exodus Web3, Chrome 웹 스토어 ID)으로만 찾는다. Firefox 확장은 프로필별 무작위 UUID라 대응하지 않는다. 규칙 `antiforensics.crypto_wallet_present`(C)는 빈 폴더(설치만 함)를 표시하지 않는다.
- 저장된 자격 증명(`credential-store-presence`, 정책 제외 행): 사용자(`AppData\{Roaming,Local}\Microsoft\{Credentials,Vault,Protect}`), systemprofile·LocalService·NetworkService, `ProgramData\Microsoft\Vault`, `System32\Microsoft\Protect`의 파일마다 존재·크기·GUID·SID·파일 해시만 낸다. DPAPI 복호, blob 구조(마스터 키 GUID·설명) 해석, `Preferred` 해석은 하지 않는다(정책).
- 바탕 화면(`desktop-wallpaper`): `Control Panel\Desktop`의 `WallPaper`와 `TranscodedImageCache`(0x18부터 UTF-16 원본 경로), `Explorer\Wallpapers\BackgroundHistoryPath<N>`(0번에만 키 시각), `Themes\TranscodedWallpaper`·`Themes\CachedFiles`(형식·크기·JPEG/PNG/BMP 해상도)만 본다. 바탕 화면 아이콘 배치(`Shell\Bags\1\Desktop` IconLayouts)와 슬라이드쇼 설정은 해석하지 않는다(연기).
- 문서 추출 정책(R5 L2): 지갑 저장소·지갑 확장 저장소·Credentials/Vault/Protect 파일·SSH 개인키(기본 이름 `id_rsa`·`id_ed25519` 등, `ssh_host_*_key`, `.ppk`)·`wallet.dat`은 문서 본문을 `(비밀 값이 든 파일 — 정책상 본문을 저장하지 않음)`으로 대신하고, 다른 문서 안의 PEM/OpenSSH/PuTTY 개인키 블록과 `WinSCP.ini`·`.reg`의 비밀번호 값 줄은 가린다(일반 문서의 `password=` 줄은 그대로 둔다). `--extract`는 같은 파일을 복사하지 않고 매니페스트에 `secret-redacted`와 SHA-256만 남긴다.

### R5 적대적 리뷰 후속 수정 (브랜치 `fix/r5-backend-review`)

- **삭제·이전 비밀번호 값**: 하이브의 free/삭제 vk 셀 중 이름이 `Password`·`ProxyPassword`·`TunnelPassword`·`Passphrase`·`EncryptedPassword`인 값은 부모 키와 상관없이 `registry-value-recovery-candidate`에서 `(비밀번호 값 — 저장하지 않음)`으로 가리고 `decoded_data_preview_sha256`을 비운다. 그 데이터 문자열은 현재 PuTTY/WinSCP 비밀번호가 없어도 `registry-hive-strings` 피벗에서 뺀다. 이름이 지워졌거나 다른 이름으로 남은 값의 데이터는 알아볼 수 없어 가리지 못한다.
- **문서 본문·추출의 비밀 파일**: Signal `config.json`, `logins*.json`·`key3.db`·`key4.db`·`signons.sqlite`, Chromium `Login Data`·`Login Data For Account`, FileZilla `sitemanager.xml`·`recentservers.xml`은 본문을 저장하지 않는다. `[Sessions\…]`/`[Sessions]` 절이 있는 모든 `.ini`의 비밀번호 줄, FileZilla `<Pass>` 값, `.reg`의 `hex(1):` 줄 이어짐까지 포함한 비밀번호 값, `PRIVATE KEY( BLOCK)` 형식의 모든 개인키(PGP 포함)를 가린다. `extract`는 이런 파일(1 MiB 이하 텍스트는 내용으로 판단)을 복사하지 않고 `secret-redacted`로 해시만 남긴다. 이름·내용이 이 규칙에 없는 비밀 파일은 여전히 문서로 읽힌다.
- **URL 자격 증명**: `redact_url`은 `scheme://user:pass@` 사용자 정보를 `[가림]@`으로 바꾸고 `password`·`passwd`·`pwd`·`pass`·`passkey`·`refresh_token`·`id_token`·`client_secret`·`api_key`·`apikey`·`secret`·`resourcekey`·`otp` 질의 값을 가린다(URL 카빙, `location-url-candidate`, 미디어 플레이어 스트림 URL·원래 값, Google 문서 바로가기 `stub_url`). 원래 URL의 sha256은 `*_sha256`에 남는다. 목록에 없는 이름의 토큰 질의 값은 가리지 못한다.
- **자원 한도**: PSD XMP는 앞 256 KiB만 `str.find`로 걷는다(`xmp_truncated`). adb 백업 해제는 요청 크기 + 64 KiB씩만 풀어 압축 폭탄이 메모리를 키우지 못한다. PAX `mtime` 같은 범위 밖 시각은 `member_mtime`이 비우고, 구성원 하나의 예외는 그 구성원만 건너뛴다(`member_error_count`); 해제 전체 실패도 모바일 공급자를 멈추지 않고 `android-backup` 한 행(`unreadable`)으로 남는다. EGG는 압축 블록이 구성원 상한(64 MiB)을 넘으면 읽지 않고, 아카이브당 해제 합계 512 MiB 이후 구성원은 목록만 낸다. ISO 9660은 이미지당 디렉터리 익스텐트 읽기 합계 64 MiB에서 멈추고(`directory-read-cap-reached`) 레코드 건너뛰기에 논리 블록 크기를 쓴다.
- **메일 중복 제거**: `email` 공급자는 Windows 메일/Live Mail 루트의 `.eml` 가운데 `email-clients`가 실제로 읽은 것(루트당 메시지 상한·걷기 상한 안)만 건너뛰고 나머지는 직접 읽는다. Thunderbird `News/` 뉴스그룹 폴더도 메일 클라이언트 공급자가 읽는다. 확장자 없는 mbox 후보의 `.msf` 확인은 캐시·임시 폴더와 16자 이상 16진 이름을 건너뛴다.
- **기타**: 네이버 지도 `x`/`y` 대체 좌표는 한반도 주변(위도 30–45, 경도 120–135) 밖이면 버린다(TM128/KATECH 값 오배치 방지). `/place/<숫자 ID>`는 검색어로 쓰지 않는다. v2 전용 토렌트(BEP 52, `pieces` 없음)는 v1 `info_hash`를 내지 않고 `torrent_version`(`v1`·`v2`·`hybrid`)을 둔다. eMule BOOLARRAY 태그 길이는 eMule과 같이 `len/8+1`로 건너뛴다. - **경로 안전**: 파일 이름은 tar 이름이 아닌 구성원 경로의 기본 이름만 쓰고 영숫자·`._-` 밖 문자는 `_`(드라이브 `C:`·NTFS 스트림 `:`·NUL·제어 문자 제거), 앞쪽 점 제거(`..`·숨김 이름 불가), Windows 장치 이름(`CON`·`NUL`·`COM1`…)은 `_` 접두, 길이 120자 이하(확장자 유지). 같은 이름은 `-<n>`, 기존 파일은 덮어쓰지 않는다(배타적 생성). 정규 파일 구성원만 쓰고 심볼릭·하드 링크·장치 구성원은 읽지 않는다. 패키지 폴더는 해시 이름이라 패키지 문자열이 경로가 되지 않는다.

### `$Boot` 추출 · 이미지 미할당 URL 카빙 (갈래 C)

- **`$Boot` 추출**: `ntfs-meta`(이미지 입력)는 Sleuth Kit `icat` inode 7로 `ntfs/$Boot`를 추출한다(512바이트 미만이면 `skipped`, 8 KiB를 넘으면 흘려 쓰는 중에 `icat`을 멈춰 8 KiB만 남기고 `extraction_mode=first-8KiB`·`stream_capped_at_bytes`; `$Bitmap` `icat`도 512 MiB를 넘는 순간 멈추고 한국어 오류; 실패해도 `extraction_status`는 바뀌지 않는다). 추출한 `$MFT` 입력(`source=mft`)은 같은 폴더의 `$Boot`·`Boot.bin`·`$Boot.bin`을 쓰거나 `boot_path` 옵션으로 지정한다. 이때 `$Boot`의 MFT 레코드 크기와 `mft_lcn`이 `$MFT` 0번 레코드의 `$DATA` 첫 런과 맞지 않으면(다른 볼륨) 그 `$Boot`는 `skipped`에 사유를 남기고 쓰지 않으며, 0번 레코드에 런이 없어 확인할 수 없으면 쓰되 요약 `boot_volume_check=unverified`로 표시한다. 분석 끝에 `$Boot` VBR + `$MFT` 3번 레코드(`$Volume`)로 `ntfs-volume-information` 행을 **한 개** 쓰고(`details.source=volume-information`, 행 출처 필터 `source=`의 값은 아님) 요약에 `volume_serial_number`(`%08X`, LNK 표기)·`cluster_size`·`volume_label`을 둔다. VBR·`$Volume` 둘 다 해석되지 않으면 행이 없다(`volume_information_status`). 두 함수는 `core/ntfs_volume.py`로 옮겼고 `system_extras`가 다시 내보낸다.
- **Sleuth Kit이 없을 때**: 파티션 첫 섹터(512바이트)만 직접 읽어(`core.e01_native.dump_boot_sector`; raw는 표준 라이브러리, E01/Ex01은 pyewf) `extraction_status=boot-only-native`로 볼륨 행만 낸다. `$MFT`·`$UsnJrnl`·`$LogFile`은 여전히 Sleuth Kit이 필요하다(`skipped`에 사유). 부트 섹터도 못 읽으면 기존 한국어 Sleuth Kit 안내와 직접 읽기 실패 사유로 실패한다.
- **통합 보기 연결**: `windows-filesystem` kind의 볼륨 정보 수집은 증거 루트 바로 아래 `rapidtriage-run*/`와, 증거 루트가 런 출력 폴더 안에 있을 때(E01 추출 루트, 위로 3단계까지 `rapidtriage-run-summary.json`이 있는 폴더) 그 출력 폴더의 `analyses/*/ntfs/`(분석 폴더 64개 상한) `$Boot`/`MFT.bin`도 읽어(단, 이 프로세스에서 실행 중인 런의 출력 폴더일 때만 — 증거 안에 심은 `rapidtriage-run*` 폴더는 읽지 않음; CLI `artifacts` 단독 실행은 분석 폴더를 읽지 않음) `volume_source=ntfs-meta-analysis` 행을 낸다. 증거 트리나 앞선 분석 폴더에 이미 나온 VSN, VSN이 없는(`$Boot` 없는) 분석 폴더는 행을 만들지 않는다. 따라서 E01의 볼륨 시리얼이 LNK 볼륨 시리얼과 만나는 것은 **분석이 있는 같은 출력 폴더로 다시 실행한 런부터**이고(적대적 리뷰 후: 다른 런의 출력 폴더나 그 밖의 위치에 있는 분석은 보지 않음), 분석 행은 콘솔에서 바로 보인다.
- **이미지 미할당 URL 카빙**: `url-carve`의 소스 `image-unallocated`(기본값 아님)는 `image_path`(비우면 런의 소스 파일; `ntfs-meta`와 같은 입력 허용 루트 규칙, 추출한 `$MFT`는 거부)의 NTFS 파티션(`partition_start_sector`, 비우면 볼륨 이미지·MBR/GPT에서 NTFS 부트 섹터로 찾음)에서 `$Bitmap`이 비어 있다고 한 클러스터만 읽는다(`core/ntfs_unalloc.py`). `$Bitmap`은 Sleuth Kit이 있으면 `icat` inode 6, 없으면 MFT 6번 레코드의 이름 없는 `$DATA` 런 목록을 직접 읽는다(속성 목록·확장 레코드로 흩어진 `$Bitmap`은 해석 못 함). 이미지는 raw면 `open`, E01/Ex01이면 pyewf로 읽으며 pyewf가 없으면 한국어로 실패한다(다른 파일 소스와 함께면 그 소스 행은 남고 요약 `image_unallocated_error`). 미할당 구간은 인접 클러스터를 합쳐 최대 200만 구간(`image_unallocated_runs_truncated`; 0x00·0xFF 바이트는 통째로, 그 밖은 바이트별 표로 계산하고 구간이 다 차면 빈 클러스터 수만 블록 popcount로 셈, 블록마다 취소 확인), 8 MiB 창·8 KiB 겹침(한 구간 안에서만 — 떨어진 두 구간에 걸친 조각 URL은 찾지 못함), `max_scan_bytes`(기본 4 GiB)까지 읽고 넘으면 `source_truncated=true`. 행: `source_kind=image-unallocated`, `source_kind_label=이미지 미할당 영역`, `source_path=<이미지>`, `offset`/`source_offset`=**이미지(미디어) 절대 바이트 오프셋**, `cluster`, `partition_start_sector`. E01에서 이 오프셋은 E01 파일 안의 위치가 아니라 콘솔의 원본 위치 열기(파일 오프셋)로는 바로 갈 수 없다. 슬랙 공간·VSS·NTFS 밖 영역·NTFS가 아닌 파일 시스템은 읽지 않는다. `$Bitmap` 런의 LCN이 음수이거나 볼륨 밖이면 한국어 오류(`NtfsUnallocError`)이고, 스캔 중 이미지 읽기 오류(E01 청크 등)는 그때까지 찾은 후보를 남기고 `image_unallocated_status=partial`·`image_unallocated_error`로 기록한다. 4Kn 원시 이미지(GPT `EFI PART`가 4096바이트 위치, 또는 MBR LBA를 4096바이트 섹터로 읽어야 NTFS가 나오는 경우)는 4096바이트 섹터로 파티션을 찾고, `icat -o`에는 512바이트 단위 오프셋을 넘긴다. 파일 카빙(`carve`, `core/carving.py`)은 이 반복자를 쓰지 않는다(후속 후보).
- **실데이터 미검증**: 위 경로는 합성 이미지(MBR + 손으로 만든 `$Boot`·`$Bitmap`·MFT 6번 레코드)와 가짜 `icat`으로만 시험했다. `BSH.E01`(250 GB)에서의 `$Boot` VSN과 서브셋 LNK `volume_serial` 일치, `$Bitmap` 구간 계산 시간, 4 GiB 상한 카빙 시간·후보 수는 사용자 승인 후 측정한다.

## R6 S3 — 색인 파일과 메모리

- 오래된 런을 처음 열 때 API는 타임라인 조건 색인(`rapidtriage-timeline-index.bin`)과 위치 행 색인(`rapidtriage-geo-index.json`)을 만들어 런 출력 폴더에 쓴다(쓸 수 없으면 메모리만). 런 폴더를 바꾸면 안 되는 경우(검토용 사본, 측정) `RAPIDTRIAGE_INDEX_PERSIST=0`으로 서버를 띄우면 새로 쓰지 않고 메모리에만 둔다(이미 있는 색인 파일은 읽는다). `scripts/perf-r6.py --run`은 이 설정으로 돌고 "색인 파일 있음" 경우는 임시 사본에서 잰다.
- 파싱한 출력 JSON 캐시는 원본 크기 기준 200 MB 예산을 두되, 예산보다 큰 출력 **2개**(실제 타임라인 약 280 MB, 큰 파일 목록 등)는 따로 캐시에 남긴다(`OUTPUT_JSON_CACHE_MAX_LARGE_ENTRIES`, 1개일 때는 큰 출력 둘을 번갈아 열면 매번 다시 파싱했다). 예산은 **파일 바이트**를 센다: 파싱한 파이썬 객체는 파일의 약 5–8배(280 MB 타임라인 ≈ 2 GB)라서 실제 메모리 상한은 대략 (200 MB + 큰 출력 2개) × 5–8, 실제 런에서 약 5 GB(+ 진행 중인 파싱 1개)다. 메모리가 작은 기계는 이 값을 1(또는 0)로 낮춘다. 처음 한 번의 파싱은 실측 3–5 초다.
- **`/files` 페이지의 비행(非行) 섹션**: `limit > 0` 페이지는 이제 행·페이지 정보·작은 머리 필드만 싣고, 중복 묶음(`duplicate_content_groups`)·중복/해시 캐시 목록·평가·시그니처 불일치 후보 같은 큰 섹션(실제 런 약 1.9 MB)은 `sections_available`(이름·바이트·항목 수)로만 알린다. 필요하면 `sections=이름,…`/`sections=all` 또는 `GET /files/sections?name=`으로 따로 받는다(`tests/test_r6_files_sections.py`). `limit=0` 전체 내보내기는 그대로다. 페이지마다 이 섹션을 읽던 외부 클라이언트는 `sections=all`을 붙여야 예전과 같은 응답을 받는다.
- 적대적 리뷰 후속 수정(단계 3 백엔드, `tests/test_r6_s3_backend_review.py`):
  - **근접 묶음 상자**: 칸 경계는 `round6(번호 × cell)`이고 첫 칸은 정확히 -90°/-180°, 마지막 칸(90·180을 나누어떨어지지 않는 cell의 남는 폭 포함)은 정확히 90°/180°에서 끝난다. 행은 자기 칸 상자(반열림)에 들어가는 칸으로 배정되어(1e-9 보정 없음) 묶음의 `box`로 다시 조회하면 정확히 `count`행이 나온다. 콘솔 `geo.ts`의 서버 없는 대체 묶음(`clusterRows`, 0.01° 고정)은 아직 1e-9 보정을 쓰므로 칸 경계에서 1e-9° 이내인 점은 서버와 다른 칸에 들어갈 수 있다.
  - **배경 색인 작성과 요청**: 요청이 기다리는 열이 있으면 배경 작성(512행 조각 + 1 ms 쉼)은 쉼 없이 돈다. 결과 열은 동기 작성과 같다.
  - **색인 파일 검증**: `rapidtriage-geo-index.json`의 행은 위도 -90–90·경도 -180–180의 유한한 수, `record_index` ≥ 0, `offset` ≥ -1, 범위 안 종류 번호, 행 수 ≤ `GEO_INDEX_MAX_ROWS`여야 하고, 아니면(깊은 중첩·NaN·1e308 포함) 파일을 무시하고 다시 만든다(500 없음). 빌드 실패는 60초(`GEO_INDEX_RETRY_SECONDS`) 동안 `unavailable`, 그 뒤 다시 시도한다.
  - **스탬프 시점**: `/timeline`은 타임라인을 읽기 **전에** 스탬프를 찍고 그 스탬프로 캐시 키·열 색인을 만든다; 읽은 뒤 파일이 바뀌었으면 색인은 메모리에만 두고 파일로 쓰지 않는다. 위치 행 색인도 스캔 전에 찍은 스탬프를 쓰고, 스캔 중 원본이 바뀌면 파일로 쓰지 않는다.
  - **내용 다이제스트**: 타임라인 색인 머리(형식 버전 2 — 버전 1 파일은 한 번 다시 만든다)와 위치 행 색인 파일에 원본의 처음·끝 64 KB SHA-256(`head_tail_digest`)을 둔다. 크기·수정 시각이 같은 재작성도 양 끝이 바뀌면 알아챈다(가운데만 바뀐 같은 크기·같은 시각 재작성은 여전히 못 알아챈다). 메모리 캐시 키는 계속 (경로, 크기, mtime)이다.
  - **그 밖**: 규칙 지문에 부정어(`_NEGATIONS`)·부분 결과 키·소수 자릿수 규칙 포함; `GeoEntry`는 `slots`(50만 행 실측 155 → 136 MB), `GEO_INDEX_CACHE_RUNS` 8 → 4; 같은 런의 늦게 끝난 옛 스탬프 빌드는 새 스탬프 항목을 밀어내지 않는다(`SingleFlightIndexCache`); 색인 파일 쓰기는 어떤 오류에도 `.tmp`를 지운다; `perf_r6_timeline`의 `no_index_file`은 배경 작성이 끝난 뒤에만 환경을 되돌린다.

## R6 타임라인·그리드 가독성 (검사관 사용성 리뷰 후속)

- **점프 목록 중복 제거(C1 규칙 1)**: `.automaticDestinations-ms`·`.customDestinations-ms` 한 파일에서 컨테이너 행(`jumplist-automatic`·`jumplist-custom`의 `destinations[]`)과 DestList 항목 행(`jumplist-entry`)이 같은 내장 LNK의 시각을 각각 냈다. 이제 두 이벤트의 레코드 식별을 그 LNK로 맞춘다 — 자동 대상은 OLE 스트림 이름(DestList 항목 번호의 16진), 사용자 지정 대상(스트림이 `container-scan` 하나)은 LNK 오프셋, LNK가 없는 DestList 항목은 DestList 오프셋. 같은 파일·같은 LNK·같은 시각이면 한 이벤트가 되고 `jumplist-entry` 이벤트(DestList 메타 포함)를 남기며 컨테이너 행은 `also_in`에 둔다(`summary.jumplist_lnk_merges`). 자동 대상 LNK는 모두 스트림 안 오프셋 0이라 오프셋만으로는 식별하지 않는다. 다른 파일(다른 앱의 점프 목록)이나 같은 파일의 다른 LNK는 합치지 않는다 — 아래 표시 묶음이 다룬다. 실제 런(32만 이벤트): 같은 파일의 컨테이너+항목 중복 묶음 3,343(+사용자 지정 44) → 0, 이벤트 323,543 → 318,733.
- **표시 묶음(C1 규칙 2, `GET /timeline?group=1`, 콘솔 기본)**: 같은 대상(`target_path` → `executable_path` → `url`, 소문자)·같은 UTC 초(오프셋 있는 시각과 없는 지역 시각은 따로)·같은 시각 종류 계열(생성 = created/target-created/item-created…, 수정 = modified/target-modified/item-modified/file-last-modified/last-modified, 접근 = accessed/target-accessed/item-accessed/last-accessed, 그 밖은 종류 그대로)인 이벤트를 한 행으로 보인다. 대상이 없는 이벤트(이벤트 로그 등)와 시각이 없는 이벤트는 묶지 않는다. 행에는 `group_id`, `source_count`(서로 다른 (아티팩트 유형, 경로) 수), `sources`(최대 20개), `group_members`(이벤트 `record_index`, 최대 50개)가 붙고 이벤트 자체는 그대로 남는다(콘솔 메타 탭에서 출처 목록). 묶음은 행 조건·`q`로 고른 위치에 적용하므로 `matched`는 보이는 행 수이고, 묶음 구성원도 조건에 맞는 이벤트만 센다. 묶음 번호는 타임라인 열 색인의 네 번째 열(`group`, 색인 형식 버전 3 — 버전 2 파일은 한 번 다시 만든다)로 저장된다. 같은 초라도 1초 경계를 넘는 두 기록(10:00:00.9와 10:00:01.1)은 다른 행이다. 묶음·검색·조건이 걸린 목록에서 `row=/events/<n>` 링크는 `locate=<n>`으로 그 이벤트가 든 행 위치를 서버에 물어 그 행(묶음 구성원이면 묶음 행)으로 간다. 검토 표시(관련·제외·태그)를 묶음 행에서 하면 대표 이벤트(`record_index`)에 저장된다. 묶음 행은 자기 표시가 없으면 구성원(`group_members`, 조건에 맞는 것만) 중 하나에 저장된 표시를 보여 주므로 조건이 바뀌어 대표가 바뀌어도 표시가 남는다(UX 라운드 리뷰). 조건에서 빠진 구성원의 표시는 보이지 않는다. `group_id`는 묶음 키의 다이제스트다(계산 경로·색인 재작성과 무관).
- **서버 검색(C3, `GET /timeline?q=`)**: 모든 이벤트의 요약·대상(경로·실행 파일·URL·키)·원본 경로·이벤트 유형·한국어 이벤트명에서 대소문자 무시 부분 일치(행 조건과 AND). 콘솔 검색 상자는 타임라인에서 이 서버 검색을 쓰고 불러온 행을 다시 거르지 않는다(바닥줄 "서버 검색"). 검색 텍스트 열은 메모리에만 있고 런의 첫 검색 때 만든다(실제 31.8만 이벤트 약 1 s, 이벤트당 요약 글자 수만큼 메모리 — 한국어가 섞이면 글자당 2바이트). 대소문자는 `str.lower`(독일어 ß ↔ ss 같은 casefold 동치는 보지 않음), 정규화는 검색어의 NFC·NFD 두 형태로 찾는다 — 한 텍스트 안에 NFC·NFD가 섞인 경우는 놓칠 수 있다. 검색어의 제어 문자는 공백으로 바뀐다.
- **요약 문장(C2·C5)**: 이벤트 로그 요약은 한국어 이벤트명(포괄 이름 "일반 이벤트"는 제외) → 없으면 렌더링된 메시지 앞 120자 → 없으면 "제공자 이벤트 ID"이고, 뒤에 계정(주체 → 대상)·컴퓨터·원격 주소·명령줄(120자)을 붙인다. 메시지는 요약에만 쓰고 이벤트 `details`에 복사하지 않는다(`level`·`event_label_ko`는 둔다). 아티팩트 요약은 "Artifact event: <유형>" 접두어 없이 대상 자체(URL은 "제목 — URL", 쿠키는 "호스트 · 이름", 자동 완성은 입력 필드, 프로그램 이름)다.
- **성능(실제 런 32.3만 이벤트, `scripts/perf-r6.py --timeline --run`, 3회 중앙값, 부하 있는 측정 기계)**: `q=liveupdate.exe` 첫 페이지 약 1.0 s(2건), 다음 페이지 약 0.01 s; `group=1` 첫 페이지는 색인 파일 있음 약 0.10 s, 없음 약 0.84 s(시각 열 + 묶음 열 작성). 여러 열을 처음 만드는 조합은 1 s를 넘는다 — `q` + 시간 + 부분 결과(파일 없음 약 1.4 s, 있음 약 1.5 s), `group=1` + `q` + 시간(없음 약 2.2 s, 있음 약 0.9 s). 검색 열은 색인 파일에 저장하지 않으므로 런을 연 뒤 첫 검색은 늘 검색 열 작성(약 0.8–1 s)을 포함한다.
- **UX 라운드 적대적 리뷰 후속(fix/r6-ux-review)**: 묶음 열이 없는 큰 타임라인(오래된 런, 이벤트 5만 초과)은 `group=1` 첫 요청에서 시각·묶음 열 전체를 만들지 않는다 — 열은 다른 열처럼 배경에서 만들고, 요청은 조건·`q`로 고른 위치 중 대상 키가 있는 이벤트만 자기 시각으로 묶는다(대표·구성원 동일, 다음 페이지는 일치 키별 캐시). `q`와 조건을 함께 처음 요청하면 검색 적중에만 조건 열을 만든다. 실측(run-subset10 32.3만 이벤트, 색인 파일 없음, 3회 중앙값): `group=1` 첫 페이지 0.80 → 0.24 s, `group=1`+`q`+시간 1.78 → 0.81 s, `q`+시간+부분 결과 1.08 → 0.68 s, 다음 페이지 ≤ 0.013 s. 큰 JSON을 메모리에 둔 프로세스에서는 Python 전체 GC(실측 약 0.4 s)가 어느 요청에나 끼어들 수 있다. 타임라인 작성기는 요약·대상 필드(`target_path`·`url`·`command_line` 등)의 `password=`·`token=`·`sharedAccessToken=`·OAuth `state=`·URL 사용자 정보를 `[가림]`으로 바꿔 저장한다(`summary.secret_redacted_events`); 이미 만든 타임라인은 다시 만들어야 적용된다. 문장 속 `state=running`·`key=HKLM\…`은 그대로이고, 키 이름 없이 값만 있는 비밀(`-p 비밀번호`, `/p:…`)은 가리지 않는다. 요약에 `jumplist_lnk_merges`가 없는 이전 형식 타임라인은 그리드에 "이 런의 타임라인은 이전 형식입니다 — 다시 생성하면 요약·중복 제거가 적용됩니다"가 나온다(콘솔에 다시 생성 동작은 아직 없음, 자동 재작성 없음).
- **콘솔 기본 열(C4)**: 시각 · 시각 종류 · 영역·유형 · 대상 · 상세 · 출처 수 · 특이사항 · 출처 행. 상세는 원본 행 계열의 카탈로그 핵심 열을 이벤트 `details`에서 읽은 한 줄이라, 타임라인 이벤트가 담지 않은 필드(긴 목록 등)는 보이지 않는다 — 메타 탭의 "원본 아티팩트 행으로 이동"이 원본 행을 연다. 출처 행은 타임라인의 수집 루트(`root`)를 뗀 경로의 마지막 두 폴더 + 파일 이름이다.

## R7 검색 결과 행·그리드 선택

- **검색 결과 행(`GET /api/runs/{id}/search`)**: 모든 적중은 `title`·`display_path`(취득 루트 `scan_scope_root`를 뗀 경로, 전체 경로는 `path`에 그대로)·`artifact_type`·`timestamp`·`snippet`(일치 문맥 200자 이하, 일치 앞 40자까지, `snippet_highlights` 강조 구간)·`locator`(`{run_id, collection, kind, pointer, record_index, output_index, output_name, artifact_id?}`)를 가진다. `preview`는 이제 `snippet`과 같다(이전에는 아티팩트·타임라인·지표 적중에서 레코드 JSON 앞 240자). 레코드에서 일치 문맥을 찾을 때는 봉투·프로필 키(`artifact_record`·`commercial_*`·`legal_limitations` 등)를 건너뛰고 값 20,000개까지만 본다 — 그 뒤에만 일치가 있으면 문맥 대신 첫 값이 나온다. 정규식·유사 검색 적중은 글자 그대로의 일치가 없을 수 있어 강조 없이 첫 값이 나온다.
- **시각**: 아티팩트 적중은 상세(`details`)의 대표 시각 키(`timestamp`·`last_visited_at`·`modified_at`·`last_seen_at` 등) 첫 값, 파일·문서는 `modified_at`이다. 집계 행(브라우저 히스토리·다운로드 집계, 저장소 목록처럼 여러 기록을 묶은 행)은 한 기록의 시각이 없어 비어 있다.
- **검토 표시**: 문서 적중은 docs-index 결과에 없어도 `docs` `/candidates/<n>` 로케이터로 표시된다. 일괄 표시에서 로케이터가 없는 행(원본 레코드가 없는 행)은 건너뛰고 나머지에 적용하며, 건너뛴 행 제목을 알림에 적는다. 서버가 로케이터를 케이스 DB 행으로 풀지 못하면(런 산출물이 케이스 DB를 만든 뒤 바뀐 경우 등) 요청 전체가 이전처럼 실패한다.
- **그리드 선택**: 행 클릭은 포커스 행만 옮기고 체크 표시를 바꾸지 않는다(이전에는 클릭한 행 하나만 선택). 체크박스 클릭은 그 행만 토글, Shift+클릭(행 또는 체크박스)은 기준 행부터 범위를 더하고, Ctrl/Cmd+클릭은 토글, Esc는 전체 해제, 바닥줄에 "선택 N건". 키보드 Shift+화살표 범위는 이전처럼 선택을 범위로 바꾼다. 선택은 행 키로 저장되어 스크롤·가상화·다음 페이지에도 남지만 다른 컬렉션·폴더·런으로 옮기면 비워진다.

## R7 S1 갈래 L2 — 그리드 열·경로·범위 정직성

- **파일 목록 서버 정렬·검색(`GET /files?sort=name|path|size|mtime|ctime&order=asc|desc`, `q=`)**: 파일 열 색인(메모리)에서 목록 전체를 정렬해 페이지로 나눈다 — 파일 출력 개정·컬렉션·키·방향(`mtime`·`ctime`은 NTFS 조인 상태까지)마다 한 번 만들고 다음 페이지는 자른다. 값이 없는 행은 두 방향 모두 끝, 같은 값은 목록 순서. 이름·경로는 `casefold` 코드 포인트 순서라 콘솔이 불러온 행을 정렬할 때 쓰는 한국어 자연 정렬(숫자 인식)과 순서가 다를 수 있다. `mtime`은 콘솔 "수정" 칸과 같은 값(`fs_modified_at` → 취득 사본이면 조인된 NTFS `$SI` 수정, 없으면 사본 시각 → `modified_at`)이고, `ctime`은 "NTFS 생성" 칸(NTFS 조인 `created_at`)이라 NTFS 메타 분석이 조인되지 않은 런(폴더 입력 포함)에서는 모든 행이 값 없음 = 목록 순서다. 인벤토리 행은 `modified_at`이 없어 `mtime`도 값 없음이다. `q=`는 이름·경로에 모든 단어(공백 구분, 대소문자 무시)가 있는 행만 남기며 범주·행 조건·폴더·특이사항 필터와 AND다. 실측(af54 후보 4,814행, b5fa 후보 4,935행·인벤토리 14,094행): 다섯 키 × 두 방향 모두 전체 목록의 Python 정렬과 순서가 행 단위로 같고, 첫 페이지 45–131 ms.
- **아티팩트·타임라인 정렬**: 서버 정렬은 이전처럼 유형 하나의 색인 열(`sortKey`)만이다. 그 밖의 열(전체 아티팩트·범주 노드의 모든 열, 목록 값 열, 타임라인의 모든 열)은 이제 비활성 대신 불러온 행만 정렬하고, 불러온 행이 전체보다 적으면 "정렬·필터는 불러온 행 기준" 배너가 뜬다. 조건 줄의 "불러온 N / 전체 M" 뱃지는 목록형 그리드에 항상 있다(교차 유형 목록처럼 전체를 아직 세지 못했으면 "전체 미확인").
- **머리 클릭 = 정렬만**: 포커스 행·선택·뷰어 대상·`row=`가 그대로다. 서버 정렬로 포커스 행이 불러온 페이지 밖으로 나가면 그 행이 다시 불러와질 때까지 포커스 표시가 없고(뷰어·`row=`는 그 행 그대로), 행을 누르거나 키로 움직이면 끝난다. 정렬·열 필터 중인 열은 폭·빈 값 때문에 숨지 않는다.
- **열 폭·숨김**: 시각 열 최소 180px, 남는 폭은 항목(3)·경로/URL/대상(2)·제목/메시지/상세(1) 가중치로 나눈다. 값이 없는 기본 열은 파일 목록처럼 아티팩트(계열 핵심 열 포함, 맨 앞 시각 열 제외)·문서·분석 결과에서도 숨고 "값이 없어 숨김"으로 열 설정에 남는다 — 불러온 행 기준이라 다음 페이지에 값이 있으면 그때 나타난다. NTFS 열의 "→ 실행" 안내는 입력이 이미지(E01·raw·VHD 등, 런 요약 `source.type` 또는 요청 경로 확장자)일 때만 있다. 판별할 수 없는 런은 이미지가 아닌 것으로 본다.
- **경로 표시**: 그리드 경로 칸·뷰어 머리·랜딩 최근 케이스 경로는 파일 이름과 상위 폴더 2개를 남기고 앞부분을 줄인다. 아주 긴 파일 이름 하나가 칸보다 넓으면 이름 끝이 잘린다(전체는 도움말).
- **조건 팝오버**: `document.body`에 고정 위치로 그려 뷰어·드로어 위(z 750, 명령 팔레트 같은 모달 오버레이 800 아래)에 뜨고, 아래 공간이 모자라고 위가 더 넓으면 위로 뒤집힌다. 조건 줄은 그리드 패널 폭 640px 미만에서 조건·조건 저장·조건 지우기를 아이콘만으로 보인다(이름은 접근성 이름에 남음).
- **트리 자동 접기**: 창 폭 1600px 미만에서 뷰어가 열리면 트리를 레일로 접고(저장하지 않음) 뷰어를 닫으면 다시 편다. 그 사이 검사관이 트리를 직접 펴면 이후에는 건드리지 않는다.
- **통합 보기 표**: 원본 행 패널은 표 아래(연결 그래프 모드는 오른쪽)에 있고, 표는 열 최소 폭 아래로 줄지 않고 가로로 스크롤한다. 불러온 값은 200개씩 보이며 "더 보기"로 늘린다(무한 스크롤로 불러오는 페이지 수는 바뀌지 않음).

- **페이지**: 적중 순서는 출처 순서(문서 → 파일 → 아티팩트 → 지표 → 타임라인 → OCR), 그 안에서 출력/케이스 DB rowid 순서로 고정이다. `pagination = {offset, limit, returned, has_more, next_offset, total}` — `has_more`는 한 건 더 찾아 본 결과, `total`은 검색이 끝까지 간 때(더 없음, 시간 예산 미도달)만 숫자이고 아니면 `null`. `offset` 페이지는 앞 페이지 적중을 다시 찾으므로 뒤 페이지일수록 느리다(커서 없음). 콘솔은 250건씩 받고 끝에 가까이 스크롤하면 다음 페이지를 받으며, 바닥줄에 "불러온 N건 / 전체 M건"(또는 "더 있음"), 시간 예산에 걸리면 "검색이 시간 제한에 도달해 찾은 결과의 앞부분만 표시합니다 …"를 보인다. 상단 바 Enter 제출은 그대로다. 검색 옵션의 "OCR 텍스트 포함"은 이제 실제로 `ocr=1`을 보내며 기본은 꺼짐이다(이전에는 화면 값과 무관하게 서버가 늘 OCR 사이드카를 읽었다).
- **시간 예산**: `RAPIDTRIAGE_SEARCH_SCAN_BUDGET_SECONDS`(기본 20 s)를 출처별로 나눈다. 케이스 DB(FTS) 백엔드는 SQLite progress handler(4,096 VM 명령마다)로 문장 안에서도 멈춘다 — 이전에는 행과 행 사이에서만 확인해 FTS 접두어 병합·차가운 디스크 읽기 중에는 예산을 넘겼다(157 s, 300 s 시간 초과). 예산에 걸린 결과는 고정 순서의 앞부분이며 `truncated: true`; 그래서 같은 검색이라도 기계 부하에 따라 건수가 다를 수 있다(446 대 500 같은 차이는 이것). 클라이언트가 연결을 끊어도 서버 검색은 예산까지 계속된다(동기 라우트는 연결 끊김을 보지 않음).
- **정규식**: 패턴은 글자·숫자 2자 이상의 고정 단어로 시작해야 한다(`Live.*Update`, `\bpowershell\.exe`, `^cmd`). `.*Update`·`\d{6}-\d{7}`·`a|b`·`[A-Z]+` 같은 패턴은 422(한국어 이유) — 색인이 단어 앞부분으로만 후보를 좁힐 수 있어 전체 행을 훑어야 하기 때문이다. 주민등록번호 같은 형식 검색은 v2 검색 색인(`/search/query`)이나 지표 탭을 쓴다.
- **출력 행 캐시**: FTS 적중의 `files.json`/`docs.json` `candidates` 순번 조회, docs 결과 색인, 추출 오류를 출력 리비전(경로·크기·mtime)별로 메모리에 둔다(행당 압축 JSON 문자열, 합계 `RAPIDTRIAGE_SEARCH_ROW_CACHE_MB` 기본 256 MB, 16개 항목; 예산보다 큰 출력은 이전처럼 스트리밍).
- **아티팩트 경로 필터(`/artifacts?path_contains=`)**: 종류별 경로 색인(서로 다른 경로 목록 + 행별 경로 번호 + JSONL 바이트 위치)으로 답한다. 의미는 이전 스캔과 같다(`path` 없으면 `source_path`, NFC + casefold 부분 일치, 프로필 펼침). 메모리에만 두고(종류 24개 LRU) 파일을 쓰지 않는다. 한 종류 요청은 처음에 색인을 만든다(29.4만 행 이벤트 로그 약 3.5–4 s, 부하 시 10 s — 이전에는 매 요청 8–10 s), 여러 종류 요청은 준비된 색인만 쓰고 나머지는 배경에서 만든다(그동안 그 종류는 스캔). 진행 중인 런은 스캔. 스캔은 이제 같은 시간 예산에서 멈추고 `truncated`·`budget_stopped`를 낸다. 다른 종류(`q`/텍스트) 필터는 바뀌지 않았다 — 타임라인 `q=`는 이미 색인(≤ 30 ms)이다. 응답 `pagination.path_index`: `ready` | `scan`.

## R7 단계 1 L1 — 런 시각·처리 단계·상대 날짜

- **런 대표 시각**: `GET /api/runs`·`/api/runs/{id}`의 `run_times`(`api/app/run_times.py`)는 런 출력 폴더의 진행 기록(`rapidtriage-run-progress.json`)의 `started_at`/`completed_at`이다. 여기서 시작한 런은 진행 기록이 이 런의 것(시작 ≥ 런 생성)일 때만 쓰고 아니면 런 기록(`started_at`/`completed_at`)을 쓴다. 불러온 런은 진행 기록이 있으면 그것을, 없으면 처리 시각이 없다(`source: "none"`) — 콘솔은 시작 자리에 "가져옴 <불러온 시각>"을, 소요에 "—"를 둔다. 요약의 `generated_at`은 시간대 없는 로컬 시각이라 쓰지 않는다. 런 목록은 진행 기록을 크기·수정 시각 기준으로 캐시해 읽는다(런 40개 기준 첫 목록 요청에 파일 40개 읽기).
- **소요**: 완료 − 시작(실행 중이면 지금 − 시작). 처리 단계표의 "단계 소요 합계"는 모든 단계가 소요를 기록했을 때만 보인다 — 이전 형식 요약은 35단계 중 2단계만 소요를 남겨 합계가 런 소요와 맞지 않는다. 접수 상태 줄의 총 소요는 "34분 9초"(반올림), 처리·런 칩은 "34:08"(버림)로 형식이 다르다.
- **결과 우선 처리 화면**: 완료·실패·취소·중단된 런(계획이 살아 있지 않을 때)은 처리 단계표 → 공개 사항 → 처리 설정 스냅샷 → 추가 분석 추천 순서이고 계획표는 읽기 전용 "처리 계획 기록"(접힘, 건너뛰기·취소 열 없음)으로만 남는다. "계획 기록 없음(이전 형식)"은 완료 런의 계획에 대기·실행 중 태스크가 남았거나, 실패·취소·중단 런의 계획이 시작 기록 없이 아무것도 끝내지 않았거나, 계획이 없을 때(404) 보인다. 실패·취소 런의 정상 계획에 남은 대기 태스크는 "이어서 실행"이 돌리는 일이라 기록으로 그대로 보인다.
- **상대 날짜 기준**: 조건 패널의 "증거 기준 최근 N일"은 런 상세의 `timeline_max_ts`에서 거꾸로 센다. 이 값은 저장된 타임라인 색인(`rapidtriage-timeline-index.bin`, 타임라인과 머리가 맞을 때)의 시각 열 최대값(지금+1일·2100년 이후 값은 버림), 색인 파일이 없으면 입력 지문의 가장 늦은 파일 수정 시각(`safety.input_fingerprint.summary.latest_mtime_epoch` — 증거 이미지 파일 하나면 취득 사본의 시각)이다(`timeline_max_source`). 메모리에만 있는 색인(`RAPIDTRIAGE_INDEX_PERSIST=0`)은 보지 않는다. 둘 다 없으면 "런 시작 기준", 런도 없으면 벽시계 "최근 N일"이다. 범위 값은 기존처럼 브라우저 로컬 `YYYY-MM-DDTHH:mm`로 URL에 남는다. 실측(읽기 전용, 2025년 증거): af54 "증거 기준 최근 7일" 97,463건, b5fa 97,297건(이전 벽시계 기준 0건).
- **증거 시스템 시간대 항목**: 상태 막대 시간대 선택에 런의 `evidence_timezone`(레지스트리 Windows 시간대 이름 · bias)이 있으면 "증거 시스템(KST −540)" 항목이 맨 위에 생긴다. Windows 이름 → IANA 대응표는 15개뿐이고, 표에 없으면 bias가 정시(60분 배수)일 때 고정 오프셋 `Etc/GMT±N`(서머타임 없음), 아니면 항목이 생기지 않는다. 기본 표시 시간대를 증거 시간대로 바꾸지는 않는다.
- **타임라인 히스토그램**: 자동 단위는 막대 영역 폭 4 px당 막대 1개 이하가 되도록 1·3·6·12시간·1·2·7·14·30·91·365일 중 가장 가는 폭(서버 버킷보다 좁을 수 없음)을 고르고, 막대 경계·이름은 표시 시간대(데이터 시작 시점의 오프셋 하나 — 서머타임 전환은 반영 안 함)다. 시간 범위 조건이 있으면 그 범위에 걸친 서버 버킷만 센다 — 범위 경계에 걸친 버킷은 통째로 들어간다(서버 버킷 안은 나눌 수 없음). 요일·시간대·부분 결과·콘텐츠·위치 조건은 여전히 막대에 적용되지 않는다(머리에 알림).
- **이 갈래 밖**: 레지스트리 "마지막 기록"·뷰어 메타의 ISO 원문 시각, 교차 케이스 대화상자의 "현재 케이스 … (id)" 표기, 팔레트 명령 이름 "케이스 전환/삭제…"는 L4 갈래가 같은 헬퍼(`formatRunTime`·`formatTimestamp`)로 바꾼다.

## R6 S1 — 기존 증거 점검 후속 수정

근거: `docs/validation/r6-sample-validation-2026-10-19.md` §5.5(D 드라이브 기존 증거 읽기 전용 점검). 테스트는 합성 픽스처만 쓴다(`tests/test_r6_s1_dcheck_gaps.py`).

### EGG 분할 볼륨 · 확장자만 .egg인 ZIP

- **분할(다중 볼륨) EGG**: 볼륨마다 자기 EGG 머리가 있고 분할 확장 헤더에 이전·다음 볼륨의 머리 ID가 있다(0 = 없음, ESTsoft 명세). 같은 폴더의 `.egg` 형제(최대 1,024개 머리만 읽음)에서 이 ID로 볼륨을 잇고, ID가 이어지지 않을 때만 알집식 이름 `이름.volN.egg`의 번호로 잇는다(`split_link`: `header-id`·`file-name`). 첫 볼륨은 파일 전체, 다음 볼륨들은 각자 머리 뒤의 데이터를 하나의 연속 스트림으로 읽으므로 볼륨 경계에 걸친 헤더·블록도 읽고 CRC를 확인한다(볼륨 256개, 기존 항목·스캔·해제 상한 그대로). 결과: `split_volumes`(볼륨 파일 이름)·`volume_count`·`missing_volumes`.
- **빠진 볼륨**: 이어지지 않는 지점에서 목록을 멈추고 `egg-partial` + `missing_volumes`(`volume_index`·`header_id`·이름 규칙으로 추정한 `expected_name`) + 한국어 `reason_ko`를 낸다. 빠진 볼륨 뒤의 볼륨은 데이터가 항목 중간에서 시작하므로 읽지 않는다.
- **첫 볼륨이 아닌 파일**: 같은 세트를 두 번 세지 않도록 항목 없이 `egg-split-member`, `split_first_volume`, `reason_ko`="분할 볼륨(첫 볼륨에서 목록)"을 낸다. 같은 폴더에 첫 볼륨이 없으면 `egg-partial` + `missing_volumes`(1번) — 목록은 만들 수 없다. 압축 파일 인벤토리(`archive-file-inventory`)도 첫 볼륨 행에만 항목이 있다.
- **잘린 항목**: 스트림이 항목 중간에서 끝나면(잘린 파일·빠진 볼륨) 12바이트 파일 헤더를 다 읽은 항목은 버리지 않고 `data_truncated: true`·`truncated_at`(`filename`=이름 미상 자리 표시 항목·`name_known: false` / `file-extra` / `block-header` / `block-data`)과 읽은 만큼의 크기(블록 헤더 전이면 `compressed_size: null`)로 내며, 해제·CRC는 하지 않는다(`crc_ok`·`sha256` null, `extract_note: truncated-not-extracted`); 압축 파일 인벤토리는 `data_truncated_entry_count`를 더한다. 크기 필드가 파일 끝을 넘는 손상도 같은 방식으로 `block-data` 잘림으로 표시된다.
- **미확인**: 실제 알집 분할 표본(§5.5의 5개)으로 다시 돌려 보지 않았다(코드 변경 뒤 증거 미열람). 볼륨이 머리 바로 뒤 데이터로 이어진다는 점, 볼륨 끝의 별도 표지 유무, 알집 이름 규칙(`.vol1.egg`, `.vol2.egg`…)은 명세·기억 기반 추정이다. ID 연결이 실패해도 이름 규칙이 맞으면 `split_link=file-name`으로 이어 읽는다.
- **확장자만 .egg인 ZIP**(파이썬 egg 등): `list_egg`가 예외 대신 `egg-format-mismatch` + `format_mismatch: "zip"` + 한국어 사유를 돌려준다(ALZ 서명이면 `alz`). 압축 파일 인벤토리는 `.egg`·`.alz` 파일이 ZIP 서명(`PK\x03\x04` 등)이면 기존 ZIP 중앙 디렉터리 목록으로 내고 프로필에 `format_mismatch: "zip"`·`format_mismatch_reason_ko`를 둔다(`archive_format`은 확장자 기준 `egg` 유지). 그 밖의 서명은 이전처럼 `egg-open-failed`.

### 곰플레이어 기록 행 시각 · 동반 값

- 곰 `_RECENTMEDIANAME#` 행은 이미 `list_last_written`(키 LastWrite, 목록 시각 상한)을 가졌지만 타임라인에 연결되지 않아 "시각 없음"으로 보였다. 이제 레지스트리에서 읽은 모든 `media-player-recent` 행(곰·팟플레이어·KMPlayer)에 `key_path`·`key_last_written_at`(= `list_last_written`)을 두고, 타임라인은 다른 레지스트리 키 시각과 같이 **키당 한 이벤트**(`last-written`, `scope="key"`)로 낸다. 행 `timestamp`는 계속 비운다(항목별 재생 시각 아님). VLC·팟플레이어 ini·재생목록 행(파일 수정 시각)은 타임라인에 연결하지 않는다.
- 같은 번호의 동반 값을 해당 항목 행에 붙인다: `_RECENTMEDIAPOS#` → `resume_position_raw`(정수일 때)·`resume_position_raw_value`(어떤 형식이든 원값 문자열, 이진은 16진)·`resume_position_value_name`; `_RECENTMEDIAAUDIOINDEX#` → `audio_index_raw`; `_RECENTMEDIAAUDIOINDEXDVD#` → `audio_index_dvd_raw`. 번호는 정수로 맞춘다(`000`과 `0`). 의미·단위는 미확인이며 원값만 보존한다.

- **실데이터 근거 범위(2026-10-21 측정)**: A등급 7개 규칙(`antiforensics.wiper_run_after_incident`, `cloud.bulk_upload`, `eventlog.rdp_external_ip`, `eventlog.log_cleared`, `ntfs.si_before_fn`, `ntfs.ads_executable`, `rdp.external_ip`) 중 **실데이터 참양성이 확인된 규칙은 없다**. `eventlog.log_cleared`·`eventlog.rdp_external_ip`·`rdp.external_ip`는 run-subset10 이벤트 로그 292,370행에서 0적중(음성 대조 통과)뿐이고, `antiforensics.wiper_run_after_incident`는 사건 기간이 없어 미평가, `cloud.bulk_upload`·`ntfs.ads_executable`은 입력 행이 없어 해당 없음이다. D: 드라이브의 다른 런(r6-s1-run·qa-case1·r4-v1)은 같은 증거를 다시 처리한 것이라 독립 근거가 아니다. 이벤트 로그·RDP·와이퍼·클라우드 A 규칙의 참양성 검증은 공개 데이터셋·일회용 VM 생성(사용자 승인 대기)이 필요하다. 카탈로그 `validation.real`에 출처별 수치와 `result`(positive·negative·not_applicable·unevaluated)를 적었고, 콘솔 근거 팝오버는 양성·음성만 세어 "검증: 실데이터 음성 n건 · 양성 0건 · 합성 픽스처"(해당 없음·미평가만이면 "실데이터 해당 없음"/"실데이터 미평가")로 보인다. `false_positives`는 검토 표본(`sample_size`) 안의 수다. 규칙별 표: `docs/validation/triage-rules-a-grade-2026-10-19.md`.
- **음성 대조만 가능한 소스**: 서브셋(run-subset10)에는 `$MFT`·Security 1102·외부 IP 로그온이 없어 `eventlog.log_cleared`·`eventlog.rdp_external_ip`·`rdp.external_ip`는 0적중(오탐 없음)만 확인할 수 있다. 양성은 공개 데이터셋·일회용 VM 생성(사용자 승인 대기)이 필요하다. VM NAT는 사설 주소라 외부 IP RDP 양성은 만들기 어렵다.
