상위: `docs/plans/maestro-gap-review-2026-10-12.md` §5 P2. 전제: P1(`analyses/` 러너, 처리 단계 페이지, 단계 레일)과 P4가 main에 있음. 브랜치 `feat/run-model-p2`.
범위: 코어 런 스케줄러(`rapidtriage/core/run/`), 런 잡 스토어(`core/jobs.py`), 런 API(`api/app/routes_runs.py` + 새 `routes_run_plan.py`), CLI `run`/새 `run-plan`·`run-control`, 콘솔 처리 단계·상태 바·탐색 단계 라이브 모드. 파서·수집기 알고리즘, DB 스키마, 기존 출력 파일의 키는 바꾸지 않는다(추가만). 제외: 원격 시스템 연결, 암호 크래킹, 외부 프로그램 직접 실행.

## 1. 최종 사용자가 보는 문제

검사관이 BSH.E01(수백 GB)을 `hacking` 모드로 돌린다. 3일짜리 런이다.

1. **진행이 안 보인다.** 상태 바는 "artifacts · provider 7/36 · 실행 중: eventlog, windows-filesystem"뿐이다(`frontend/src/shell/StatusBar.tsx:28-38`). 이벤트 로그 파싱이 10시간 걸리는 동안 진행 파일은 한 글자도 바뀌지 않는다 — `RunProgress`는 상태 전이 때만 쓰고(`core/run/progress.py:140-166`) 심장박동이 없어서, 느린 런과 죽은 런을 구별할 수 없다. 준비(E01 `tsk_recover` 추출)·파일 인벤토리·문서 검색·타임라인·persist 단계는 진행 보고 자체가 없다(`core/run/__init__.py:452-459, 795-857, 753-793, 942-971, 1011-1030`).
2. **취소가 되지 않는다.** 콘솔 "런 취소"는 `RunJobStore.cancel`이 `cancellation_requested=True`만 세우고(`core/jobs.py:517-548`), `run_triage_mode`는 그 플래그를 한 번도 읽지 않는다. 실행 중인 런은 서버를 죽이기 전에는 멈출 수 없다. 제한 문서는 `running_cancel_policy: cooperative-stage-boundary`라고 적고 있지만(`docs/rapidtriage-known-limitations.md:945-966`) 코드에 그 경계가 없다. CLI는 Ctrl+C 하면 `progress.fail`로 끝난다(`core/run/__init__.py:493-496`) — 요약·보고서·감사 기록이 없는 "실패"다.
3. **일부만 돌릴 수 없다.** `--mode` 4개 + `--carve` 같은 플래그가 전부다. 24개 공급자 중 이 사건에 필요 없는 것(카카오톡·안드로이드·macOS)을 끌 수 없고, 한 공급자가 12시간을 먹어도 그것만 건너뛸 수 없다.
4. **끝난 것부터 볼 수 없다.** 공급자 출력은 완료 즉시 `artifacts/rapidtriage-artifacts-<kind>.json(.jsonl)`로 써지는데(`core/run/__init__.py:1558-1561`), 모든 열람 API는 `job.summary is None`이면 409 "완료된 런이 아닙니다"다(`routes_runs.py:417-418`, `tree.py:160-161`, `routes_search.py:167`, `helpers.py:237`). 대시보드도 `enabled: completed`일 때만 트리·요약을 읽는다(`features/dashboard/useDashboardData.ts:35-47`). 3일 중 2일 반을 아무것도 못 본다.
5. **중단되면 처음부터다.** 서버 재시작 시 `_load_state`가 running 런을 `failed`("server restarted…")로 만들고(`core/jobs.py:638-644`), "재시도"는 같은 요청을 `resume=False`로 다시 낸다(`core/jobs.py:550-566`). 이미 끝난 공급자 출력을 재사용하는 `--resume` 경로(`collect_artifact_stages` 1403-1421)가 있는데 콘솔에서는 닿을 수 없다.
6. **상태 철자가 어긋난다.** 잡 스토어는 `"canceled"`를 쓰고(`core/jobs.py:528, 578`), 콘솔은 `"cancelled"`만 안다(`api/runs.ts:3`, `components/Badge.tsx:18`, `commands/builtin.ts:343`). 취소된 런은 배지가 영문 원문으로 나오고 "런 다시 실행" 버튼이 비활성이다.

마에스트로는 같은 런을 "Groups 43 / Tasks 414, 그룹별 막대, Running/Pending/Partial, 그룹별 ×, CANCEL ALL / FINISH, 0 of 55 tasks completed, 55 skipped"로 보여 준다.

## 2. 이상 상태

- **U-P2-1 처리 계획표**: 런을 시작하면 `rapidtriage-run-plan.json`이 생기고, 처리 단계 중앙에 그룹 → 태스크 표가 뜬다. 머리에 "그룹 n / 태스크 m · 시작 · 경과 · 완료 a · 부분 b · 건너뜀 c · 취소 d · 실패 e". 그룹 행은 진행 막대(완료 태스크/전체)와 상태 배지, 펼치면 태스크 행(상태·건수·소요·메시지). 실행 중 태스크는 "행 12,340 · 03:12 경과"가 1초마다 움직인다.
- **U-P2-2 개별 취소·건너뛰기**: 대기 중 태스크/그룹에 "건너뛰기", 실행 중에 "취소". 취소된 공급자 태스크는 그때까지 쓴 행을 남기고 `partial`로 끝나며, 그 행은 바로 열람할 수 있다. 상단에 "모두 취소"(남은 것 전부 취소, 실행 중인 것도 멈춤)와 "마치기"(대기 중만 취소, 실행 중은 끝까지 두고 요약·보고서·케이스 DB까지 마무리) 두 버튼. 모두 한국어 사유와 함께 비활성 조건이 있다.
- **U-P2-3 런 시작 전 선택**: 실행 대화상자에 그룹 체크 목록(모드 기본값 미리 체크). 끈 그룹은 계획표에 `skipped`로 남는다("0 of 3 tasks completed, 3 skipped").
- **U-P2-4 완료된 그룹부터 열람**: 런이 돌고 있어도 탐색 단계 트리에 완료된 공급자 노드가 건수와 함께 나타나고, 그리드로 열린다. 아직 안 끝난 노드는 흐리게 + "처리 중 (그룹 X, 대기 3번째)". 상단에 "런 진행 중 · 완료된 그룹만 표시 · 검색/타임라인은 마무리 후" 배너.
- **U-P2-5 느린 런 ≠ 죽은 런**: 진행 파일에 15초 심장박동과 실행 중 태스크의 행 수가 있다. 런 프로세스가 죽으면(서버 재시작) 콘솔은 그 런을 "중단됨 · 서버 재시작"으로 보여 주고 "이어서 실행" 버튼(완료된 태스크 재사용, 부분·취소·건너뜀 태스크만 다시)을 준다.
- **U-P2-6 취소·건너뛰기의 흔적**: 요약 `steps`, 체크포인트, 매니페스트 공급자 행, 감사 기록(`rapidtriage-run-audit.json`), 마크다운 보고서, 처리 계획표 모두에 "누가(web/cli) 언제 무엇을 취소/건너뛰었는지"가 남는다. 부분 출력으로 만든 타임라인·지표·케이스 DB에는 `inputs_partial: true`가 붙는다. 어떤 취소도 이미 쓴 바이트를 지우지 않는다.
- **U-P2-7 CLI 동등성**: `rapidtriage run --skip-group … --skip-task … --print-plan`, `rapidtriage run-plan <output_dir>`, `rapidtriage run-control <output_dir> cancel|skip|finish [--target …]`. CLI 런의 Ctrl+C = "모두 취소"(부분 출력 + 요약 + 감사 기록을 남기고 종료 코드 130).

**상태**: 태스크 `queued | running | completed | partial | failed | skipped | cancelled`. `reused: bool`(resume 재사용). `partial`은 "실행 중 취소되어 일부 행만 남음" 또는 "격리된 파서 오류와 함께 행이 있음"(`failed_isolated`+행>0). 그룹 상태는 파생(우선순위): 하나라도 `running` → `running`; 전부 `queued` → `queued`; 전부 `completed`(reused 포함) → `completed`; 전부 `skipped` → `skipped`; `completed` 0이고 `cancelled`>0 → `cancelled`; `completed` 0이고 `failed`만 → `failed`; 그 외 섞임 → `partial`.

**태스크 레코드**:

  "duration_ms": null, "artifact_count": null, "rows_so_far": 12340,

### 3.2 영속·심장박동·소유자

- `rapidtriage-run-progress.json`을 `run-progress-v2`로 올린다: 기존 키 전부 유지(`docs/rapidtriage-output-schemas.md:303` 계약) + `plan`(위 구조) + `heartbeat_at`(15초) + `_owner {pid, boot_id, heartbeat_at}`(analyses와 같은 모양, `api/app/analyses.py:170-193` 재사용; API 응답에서는 `_`키 제거). `RunProgress`에 `plan` 갱신 메서드(`task_running/task_rows/task_finished/task_skipped/task_cancelled`)와 데몬 심장박동 스레드(`AnalysisRunner._beat` 패턴, `analyses.py:852-858`)를 붙인다. 쓰기는 지금처럼 원자 교체(`progress.py:226-246`), 행 수 갱신은 1초 스로틀.
- `rapidtriage-run-plan.json`은 진행 파일의 `plan` 블록을 런 종료 시 따로 떼어 쓴다(요약 `outputs.plan`, 감사 `output_files`). 실행 중에는 진행 파일 하나만 쓴다(두 파일 정합성 문제 회피).
- **제어 파일** `rapidtriage-run-control.json`: 독자(API/CLI) → 런 프로세스 방향. `{version:"run-control-v1", requests:[{seq, action:"cancel"|"skip"|"cancel_all"|"finish", targets:[{group?|task?}], actor, at}]}`. API는 추가(append) 후 원자 교체; 런 프로세스는 워처 스레드가 mtime을 1초마다 보고 새 요청을 `threading.Event`/집합에 반영한다. 같은 프로세스(웹)에서는 잡 스토어가 이벤트를 직접도 세우지만, 파일을 거치므로 **CLI 런도 콘솔·다른 터미널에서 제어할 수 있고**, 요청 이력이 증거로 남는다. 런이 끝난 뒤의 요청은 런 프로세스가 아니라 API가 409로 거른다.
- **크래시 복구**: 잡 스토어 `_load_state`(`core/jobs.py:638-644`)는 `queued|running` 런을 `failed` 대신 `interrupted`(새 상태; `error="서버 재시작으로 중단"`, `interrupted_reason`)로 기록한다. 진행 파일 `_owner`가 죽은 프로세스를 가리키면 읽기 쪽(`run_progress_payload`)도 같은 판단을 내려 `plan.outcome="interrupted"`, 실행 중이던 태스크를 `partial`(행>0)/`cancelled`(행 0)로 **보여 준다**(파일은 고치지 않는다 — analyses `load_state` 규칙, `analyses.py:870-898`). "이어서 실행" = `POST /retry {resume:true}` → `RunRequest.resume=True` + 같은 `output_dir`; `collect_artifact_stages`가 완료 출력을 `reused`로 넘기고, `load_reusable_artifact_payload`(`core/run/__init__.py:1353-1366`)에 **`summary.collection_status in {"cancelled-partial","failed-isolated"}`면 None** 조건을 추가해 부분 출력이 재사용되지 않게 한다. 주의: resume은 지문을 파일 내용 해시로 만든다(`build_run_input_fingerprint(scan_root, hash_contents=resume)`, `__init__.py:583`; 파일당 16 MB 상한) — 큰 증거에서 수십 분이 들 수 있으므로 계획표 `fingerprint` 태스크에 "이어서 실행 지문 계산 중" 메시지를 낸다.

### 3.3 취소·건너뛰기의 실행 의미

- **협조적 취소 지점**: (a) 공급자 태스크 — `stream_artifact_collection`의 행 루프(`core/artifacts.py:216-242`)에 `check_cancel` 콜백(기본 None = CLI `artifacts` 명령 동작 불변)을 넣어 200행마다 또는 1초마다 확인한다. 취소되면 생성기를 닫고(`generator.close()`) 그때까지의 raw 행으로 2·3패스를 끝내 JSONL을 완성한다; payload `summary.collection_status="cancelled-partial"`, `summary.rows_before_cancel=n`. 취소는 파서 오류가 아니므로 `parser_errors`에 넣지 않는다. `tracked_artifact_collection`(`__init__.py:1598-1616`)이 태스크별 이벤트를 넘긴다. (b) 대기 중 태스크 — 풀에 제출하기 전에 건너뛴다: 지금은 전부 한 번에 제출하므로(`__init__.py:1480-1490`) **제출을 워커 수만큼만 하고 완료될 때마다 다음 대기 태스크를 꺼내는 방식**으로 바꾼다(`as_completed` 루프 유지, 대기열은 리스트). 그래야 대기 태스크의 skip/cancel이 "제출 전"에 걸린다. (c) 단계 경계 — `_run_triage_stages`의 각 `begin_stage` 앞에서 `cancel_all`/`finish`를 확인한다. (d) 1차에서 파일 인벤토리·문서 검색·타임라인·persist 안쪽은 취소 지점이 없다(단계 경계에서만). 2단계(§3.9)에서 `run_files_scan`/`scan_document_candidates` 후보 루프에 카빙과 같은 `check_cancel` 훅을 넣는다.
- **skip vs cancel**: `skip`은 `queued`에만(409 "이미 시작된 태스크는 건너뛸 수 없습니다. 취소를 사용하세요"), `cancel`은 `queued|running`에(대기 중이면 즉시 `cancelled`, 사유 "시작 전 취소"). 그룹 대상은 그 안의 해당 상태 태스크 전부에 적용. `completed|partial|failed|skipped|cancelled`에는 409 "이미 끝난 태스크입니다".
- **cancel_all**: 실행 중 전부에 취소 이벤트, 대기 전부 `cancelled`, 이후 단계(docs/files/timeline/indicators/persist)는 `cancelled`로 건너뛰되 **`report` 태스크는 항상 실행**(요약·계획·감사·마크다운). 런 상태 `cancelled`, `plan.outcome="cancelled"`. 요약이 생기므로 열람·보고서 내보내기가 된다(지금은 취소된 런에 요약이 없다).
- **finish**: 대기 중 태스크만 `cancelled`(사유 "마치기 요청"), 실행 중은 끝까지, 이후 단계는 **정상 실행**(부분 입력으로). 런 상태 `completed`, `outcome="partial"`.
- **증거 무결성**: 취소·건너뜀은 파일을 삭제하거나 덮어쓰지 않는다. 기록 지점: ① 진행 파일/계획(위) ② 스케줄러 이벤트 `status: cancelled|skipped`(`core/run/scheduler.py:295-329`; row_hash에 포함) ③ 체크포인트 `status: cancelled|skipped`(`checkpoints.py:40-56`; `--resume` 판정이 이를 "재사용 불가"로 본다) ④ 매니페스트 공급자 행 `collection_status`(`docs.py:171-173`) ⑤ 요약 `steps` 행 `status: cancelled|skipped|partial`, `warning_level: "warning"`, 메시지 한국어(`steps.py:107-127` 확장) ⑥ 감사 `options.plan_control = [요청 목록]`, `options.skip_groups/skip_tasks`, `notes`에 "부분 런: 그룹 X 취소(web, 시각)"(`audit.py:111-154`) ⑦ 마크다운 보고서에 "건너뛴·취소된 처리" 절 ⑧ 타임라인/지표/케이스 DB 요약에 `inputs_partial: true, partial_kinds:[…]`. 리뷰어 번들·제출 매니페스트는 요약을 그대로 담으므로 자동으로 따라온다.
- **런 상태 철자**: 잡 스토어는 `"cancelled"`를 쓰고, 읽을 때 `"canceled"`를 `"cancelled"`로 정규화한다(`RunJob.from_record`). 새 상태 `interrupted`. `ACTIVE_RUN_STATUSES`는 그대로.

### 3.4 API 계약 (B가 구현, A는 이 계약으로 mock)

공통 오류 모양은 P1과 같다(`{"detail": "<한국어>"}`; 404 "런을 찾을 수 없습니다").

- `GET /api/run-plan/preview?mode=&carve=&extract=&case_db=&input_kind=` → `{mode, groups:[{id,label,default_on,tasks:[{id,label}]}]}`. 실행 대화상자의 체크 목록용(파일 접근 없음).
- `POST /api/runs` 본문에 `skip_groups: [id…]`, `skip_tasks: [id…]` 추가(`RunCreateRequest`, `core/jobs.py:79-149 RunRequest`에도). 알 수 없는 id → 400 "알 수 없는 그룹입니다: x". `prepare`·`fingerprint`·`report`는 건너뛸 수 없다(400 "건너뛸 수 없는 그룹입니다: report").
- `GET /api/runs/{id}/plan` → 계획 루트(§3.1) + `run_status` + `live: bool`(런 프로세스 살아 있음) + `elapsed_ms`. 진행 파일이 없으면(아직 prepare 전) 상태만 `queued`인 뼈대 계획을 돌려준다(요청에서 바로 만들 수 있다). `If-None-Match`에 `updated_at` 해시 → 304.
- `GET /api/runs` 각 행 `progress`에 `plan_counts {groups, tasks, completed, partial, failed, skipped, cancelled, running}`, `heartbeat_at`, `current:[{task, rows_so_far, started_at}]`(≤3) 추가(`compact_run_progress`, `routes_runs.py:83-99`).
- `POST /api/runs/{id}/plan/control` 본문 `{action: "cancel"|"skip"|"cancel_all"|"finish", targets?: [{group: id} | {task: id}]}` → 202 `{accepted:[…], rejected:[{target, reason}], plan}`. 런이 `queued|running`이 아니면 409 "실행 중인 런이 아닙니다". `cancel`/`skip`에 targets 없으면 400 "대상을 지정하세요". 대상 일부가 불가면 그 항목만 `rejected`(전체 409 아님). `cancel_all`/`finish` 중복 요청은 멱등(202, 이미 기록된 시각 반환).
- `POST /api/runs/{id}/cancel`(기존) = `cancel_all`의 별칭(응답 모양 유지 + `plan` 추가).
- `POST /api/runs/{id}/retry` 본문 `{resume: bool = false}`. `interrupted|failed|cancelled` 런에 허용(409 메시지 "실패·취소·중단된 런만 다시 실행할 수 있습니다"). `resume:true`면 같은 `output_dir`로 `RunRequest(resume=True)`; 응답에 `retry_mode: "resume"|"fresh"`.
- **라이브 열람**: `GET /api/runs/{id}/artifacts?kind=…`, `GET /api/runs/{id}/tree`, `GET /api/runs/{id}/summary`가 `job.summary is None`일 때 409 대신 — 진행 파일의 계획에서 `completed|partial`인 공급자 태스크의 `output.path`(런 출력 디렉터리 아래인지 `is_relative_to` 검증, `core/jobs.py:1860`)를 읽어 **그 kind만** 돌려준다. 응답에 `live: {run_status:"running", partial: true, available_kinds:[…], pending_kinds:[…]}`. `/tree`는 공급자 노드만(파일·문서·타임라인·IOC 노드는 해당 단계 완료 후 — `files` 태스크가 끝나면 `rapidtriage-files.json`을 읽어 파일 노드도), 도메인 노드에 `state: "pending"|"running"|"completed"|"partial"|"skipped"`와 `reason`. `/summary`는 409 유지(요약은 마무리 산출물). 검색·타임라인·IOC·리뷰 API는 1차에서 409 유지하되 메시지를 "런 마무리 후 사용할 수 있습니다(진행: 그룹 x/y)"로 바꾼다. 정렬 인덱스(`artifact_sort`)는 완료 kind에만 만들고(파일이 바뀌지 않으므로 캐시 키 그대로), `partial` kind의 JSONL도 완성 파일이므로 가능. `running` kind는 돌려주지 않는다(raw.tmp 단계라 읽지 않는다).
- `RunJobStore`에 `provisional_output_path(run_id, name)`(진행 파일 기반, 요약 없이)를 추가하고 `read_output`은 기존 그대로 둔다(완료 런 경로 불변).
