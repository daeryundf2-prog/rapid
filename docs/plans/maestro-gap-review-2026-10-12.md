## 2. RapidTriage 현황 요약

- 공급자 24개(윈도우 12, 범용 문서/미디어/이메일/합성미디어, 클라우드 내보내기, 모바일 내보내기, 카카오톡 2, 리눅스, macOS, 메모리, APK). 아티팩트 유형 리터럴 202개.
- 분류 감사 51/51 "covered"이지만, 이 감사는 "수집기·유형·뷰어·테스트·문서 바인딩이 존재하는가"를 묻는 것이지 "네이티브로 깊게 파싱하는가"를 묻지 않는다. 제한 문서 §Parser Coverage는 레지스트리(.reg 내보내기 + 하이브 셀 후보), MFT/USN(내보내기 + 바운디드 네이티브), Prefetch(섹션 위치만, 파일 메트릭/볼륨 테이블 미디코딩), SAM(후보 행), Jump List DestList, EVTX 메시지 렌더링 등을 "baseline/bounded/validation-required"로 명시한다.
- CLI만 있는 분석: `carve`, `vsc-discover/compare/extract`, `ntfs-meta`, `ocr-queue`, `kakaotalk-decrypt`, `cloud-collect`, `collect-plan/export`, `case-export-uco`, `cross-case-correlate`, `columnar-*`, `known-good-index`.
- API 83 경로 중 콘솔이 쓰는 분석 기능: 검색/문서/파일/아티팩트/타임라인/IOC(+TI enrichment)/소스 뷰어(헥스·SQLite·이미지·OCR·번역·미디어 큐·이메일 첨부·갤러리)/추출/보고서·리뷰어 번들·제출 매니페스트·검증 패키지/키워드 팩/케이스 DB.
- 콘솔 트리는 AXIOM식 12개 범주(웹, 커뮤니케이션, 미디어, 이메일·캘린더, 문서, 클라우드, 앱 사용량, 운영 체제, 암호화·로그인, 연결된 디바이스, 위치·여행, 기타)로 kind를 묶는다. 마에스트로의 "분석 작업" 관점(카빙, VSC, 메모리, 암호 파일, 웹 로그, 정보 유출, LotL…)은 트리에 없다.
- 실행 모델: `run --mode {fraud,hacking,recovery,seizure}` + 옵션(carve, columnar, case-db, eventlog detail). 진행률은 단계·공급자 단위(상태 바 카드). 그룹/태스크 단위의 부분 완료·개별 취소·스킵 집계는 없다.

## 4. 솔직한 평가

1. **넓이는 비슷하고 깊이가 다르다.** 마에스트로 그리드의 핵심은 "이미지에서 바로 네이티브로 파싱한 결과"다. 우리는 레지스트리·MFT/USN·Prefetch·SAM·Jump List 상당수가 내보내기 의존이거나 "바운디드 후보"라서, 실제 E01 케이스에서는 열이 비거나(§Q-C3에서 본 것처럼) 검증 블로커가 붙는다. 분류 감사의 "51/51"은 이 차이를 숨긴다.
2. **있는 기능이 콘솔에 없다.** 카빙·VSC·메모리·OCR 일괄·웹 로그·교차 케이스는 CLI로만 돌릴 수 있다. 검사관은 콘솔에서 발견할 수 없다.
3. **분석을 "작업"으로 노출하지 않는다.** 마에스트로는 43개 그룹/414 태스크를 켜고 끄고 부분 완료를 본다. 우리는 모드 4개 + 플래그다. 3일 런(BSH) 경험에서 봤듯이 "무엇이 끝났고 무엇이 건너뛰었는지"가 그룹 단위로 보여야 한다.
4. **행 단위 출처 정보가 약하다.** MFT 엔트리 번호, 파일 시스템 종류, 소스 이미지 경로는 법정 인용에 자주 쓰이는데 메타 탭에 없다.
5. **열별 필터**는 우리 필터 바로 대체되지만, 검사관 습관(AXIOM·마에스트로 모두 열 머리 아래 입력)을 생각하면 "열 머리 필터" 모드가 필요하다.

| **P1 콘솔 노출** | 트리에 "분석 작업" 섹션: 카빙·VSC·메모리·OCR 일괄·웹 로그/웹셸·교차 케이스. 각 노드 = 실행 대화상자(옵션·대상·예상 시간) + 결과 컬렉션. 행 메타에 MFT 엔트리·파일시스템·소스 이미지 경로. 열 머리 필터 모드. | C→A 7건, B 3건 | 프런트 중심, API 얇게 (2~3일) |
| **P2 실행 모델** | 런을 그룹(공급자 묶음)/태스크 단위로 계획·진행·부분 완료·개별 취소·스킵 집계. 마에스트로식 진행 대화상자. 완료된 그룹부터 열람 가능(이미 JSONL 스트리밍 기반). | 3일 런 체감 해결 | 코어 run 스케줄러 + 콘솔 (3~4일) |
| **P3 네이티브 깊이** | 레지스트리 키 트리 탐색기(하이브 네이티브 파서), Prefetch 파일 메트릭/볼륨 테이블, Jump List DestList, SAM 그룹 구성원, MFT 속성 리스트 | B→A 5건(가장 큰 품질 차이) | 파서 작업, 검증 데이터 필요 (1~2주, 단계별 PR) |
| **P4 분류 트리 확장** | 마에스트로식 2차 분류: 소스/환경설정(XML/JSON), 실행 파일(DLL/EXE), 스크립트(JS/JSE/PS1 + 도메인 추출), 이미지 포맷별, 안티 포렌식, 침해사고 하위. 기존 파일 인벤토리 위에 규칙으로 구현 | D→A 3건 | 규칙 + 트리 (2일) |
| **P5 신규 분석기** | PII/인증서 스캐너(주민번호·카드·계좌·PEM/PFX), 랜섬웨어 흔적(랜섬노트·확장자 패턴·VSS 삭제 명령), 정보 유출 워크플로(USB+클라우드+이메일+인쇄 상관) | D 3건 | 각 1~2일 |
| 제외 | 원격 시스템 연결, 암호 크래킹, 외부 프로그램 직접 실행 | 보안·검증 모델 확정 전 보류(제한 문서와 일치) | — |

권장 순서: **P1 → P4 → P2 → P3 → P5**. P1·P4는 기존 기능을 검사관이 보게 하는 일이라 비용 대비 효과가 가장 크고, P2는 BSH 런 경험의 직접 해법, P3는 품질 차이의 본질이지만 가장 오래 걸린다.

## 6. QA 원칙(단계 공통)

실데이터(bsh-subset, run-subset7)에서 각 노드/작업 버튼이 ① 요청을 보내거나 ② URL/aria를 바꾸거나 ③ 사유와 함께 비활성인지 e2e Q-A3로 강제한다. 새 파서는 known-answer 픽스처 + trusted diff(외부 도구 출력)를 요구하며, 실제 E01 결과는 Git 밖에 둔다.
