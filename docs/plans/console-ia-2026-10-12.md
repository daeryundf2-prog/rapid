# 콘솔 정보 구조(IA) 재설계 — "분석 기능을 어디에 두는가" (2026-10-12)

사용자 질문: "현재 보여지는 구조가 분석 기능을 정리할 최선의 구조인지 모르겠다. 최적의 디자인을 고려해라."
결론: **단계 레일(워크플로) × 도메인 트리(데이터) × 처리 페이지(작업)** 로 분리한다. 작업(무엇을 돌릴지)과 결과(무엇이 나왔는지)를 한 트리에 섞지 않는다.

## 1. 지금 구조의 문제

현재 왼쪽 트리: 증거 소스 · 접수 · 검색 결과 · 파일/미디어 · 문서/메일 · 아티팩트(12 범주) · 타임라인 · IOC/위험 · 리뷰보드 · 산출물. 여기에 P1이 "분석 작업(카빙·VSC·NTFS·OCR·메모리·웹 로그·교차 케이스)"을 같은 트리에 더하려 했다.

- **세 가지 다른 것이 한 목록에 있다**: 워크플로 단계(접수·리뷰보드·산출물), 데이터 뷰(파일·문서·아티팩트·타임라인), 실행 작업(분석 작업). 검사관은 "다음에 뭘 해야 하지"와 "뭐가 있지"를 같은 트리에서 찾아야 한다.
- **작업과 결과가 분리되지 않는다**: 카빙을 "실행"하는 곳과 카빙 "결과"를 보는 곳이 같은 노드라서, 결과는 파일시스템 맥락(복구된 파일)에 있어야 자연스러운데 작업 묶음 아래 갇힌다.
- **처리 전략이 보이지 않는다**: 마에스트로의 43그룹/414태스크처럼 "무엇을 어느 깊이로 돌렸는가"를 보는 곳이 없다. 런 카드 하나가 전부다.
- **범주가 AXIOM식 12개로 고정**: 포렌식 도메인(운영체제·실행 흔적·파일시스템·안티 포렌식·침해사고…)이 아니라 콘텐츠 유형(웹·미디어·문서…)이라, 사건 유형별 탐색(침해사고 → 웹셸·RDP·LotL)이 어렵다.

## 2. 참고한 구조

- **AXIOM Examine**: 케이스 대시보드 / 증거 개요 / 아티팩트(범주 탐색 + Explorer 뷰) / 처리 옵션은 Process 앱으로 분리. 장점: 탐색이 깨끗함. 단점: 처리와 분석이 다른 앱.
- **마에스트로 WISDOM**: 리본(작업) + 분류 격자(도메인) + 트리(도메인별 결과) + 진행 대화상자(그룹/태스크). 장점: 작업이 눈에 보임. 단점: 리본·격자·트리에 같은 이름이 중복되고 단계 개념이 없음.
- **EnCase/FTK**: Evidence / Overview / Bookmarks / Index 탭. 장점: 단계가 탭으로 명확. 단점: 아티팩트 범주화가 약함.

## 3. 결정한 구조

```
┌──┬──────────────────┬──────────────────────────┬────────────────┐
│레│ 단계별 왼쪽 패널   │ 중앙 작업 영역             │ 뷰어(항상)      │
│일│                  │                          │                │
└──┴──────────────────┴──────────────────────────┴────────────────┘
```

**레일(세로 아이콘 5개, 항상 표시, 단축키 Alt+1~5 — Ctrl+1~5는 브라우저 탭 전환과 충돌)**
1. **접수** — 케이스 대시보드(요약 노트·증거 소스·범주 요약·처리 세부·리뷰 상태·시작할 곳). 지금 대시보드 그대로.
2. **처리** — 런과 분석을 다루는 곳. 왼쪽: 런 목록(상태·소요·오류) + "추가 분석" 목록. 중앙: 선택한 런의 **처리 계획표**(그룹 → 태스크, 상태 Running/Pending/Partial/Skipped/Cancelled, 그룹별 취소·재실행, 건수·소요)와 **추가 분석 카드**(카빙·볼륨 섀도우·NTFS 메타·OCR 일괄·메모리·교차 케이스·도메인 추출: 옵션·실행·진행·이력·"결과 보기 →"). P1의 `analyses` API와 P2의 그룹/태스크 모델이 여기에 산다.
3. **탐색** — 데이터를 보는 곳. 왼쪽: **도메인 트리**(아래 §4) + 전체 뷰(전체 파일·전체 타임라인·검색 결과·IOC). 중앙: 그리드(열/썸네일/대화/히스토그램) + 1줄 필터 칩. 분석 결과는 도메인 트리의 노드로 나타난다(카빙 결과 → 파일시스템 › 복구/카빙, NTFS 메타 → 파일시스템 › MFT/USN, OCR → 미디어 › OCR 텍스트, 메모리 → 메모리, 교차 케이스 → 침해사고 › 교차 케이스 지표).
4. **검토** — 리뷰보드(관련/재검토/제외/보고서 포함), 태그별, 메모, 북마크, 증거 선별 요약. 중앙 그리드는 동일.
5. **보고** — 케이스 보고서(PDF/MD), 리뷰어 번들, 제출 매니페스트, 검증 패키지, 추출 결과(산출물). 미리보기 + 내보내기 이력.

**전역(모든 단계)**: 상단 바(케이스 전환·전역 검색·명령 팔레트·도움말), 뷰어 패널(선택 행 따라감), 상태 바(실행 진행 칩·시간대·연결). 전역 검색 결과는 탐색 단계의 "검색 결과" 뷰로 연다.

**URL**: `#/case/{run}/{stage}/{view}[/{sub}]?…` — stage ∈ intake|process|explore|review|report. 기존 `#/case/{run}/{collection}` 링크는 리디렉션(artifacts/files/docs/search/timeline/indicators → explore, review → review, outputs → report, intake → intake)으로 호환.

## 4. 탐색 단계의 도메인 트리 (마에스트로 + 우리 kind 매핑)

| 도메인 | 하위 노드(→ 컬렉션/필터) |
|---|---|
| 증거 소스 | 이미지·파티션(→ 접수 카드) |
| 운영체제·계정 | OS 정보, 사용자·그룹(SAM), 설치 프로그램, 작업 스케줄러, 서비스, WER |
| 실행 흔적 | Prefetch, Amcache/ShimCache, UserAssist/BAM, Jump List/LNK, PowerShell 히스토리, 스크립트(JS/VBS/PS1) |
| 파일시스템 | 전체 파일, 파일 유형별(문서/이미지/실행/스크립트/설정/압축/DB/이메일), MFT/USN(NTFS 메타 결과), 복구/카빙(카빙 결과), 삭제/휴지통, 시그니처 불일치, ADS |
| 레지스트리 | 하이브, ShellBags, 셀 복구, 트랜잭션 로그 |
| 이벤트 로그 | 채널별(Security/System/Application/PowerShell…), 복구 레코드 |
| 웹·브라우저 | 히스토리, 다운로드, 캐시/세션/확장, 검색어, 웹메일, 소셜(SNS), 유튜브, 클라우드 저장소 |
| 메신저·메일 | 카카오톡, 모바일 메시지, 이메일(EML/MBOX/PST), 첨부 |
| 클라우드 | Takeout/iCloud/M365 내보내기, 인가 API 수집 |
| 미디어·문서 | 이미지 갤러리, 동영상/음성, OCR 텍스트(OCR 결과), 문서 메타데이터 위험, 합성 미디어 |
| 모바일 | iOS 백업, Android, APK, 통합 뷰 |
| 연결 장치·원격 | USB 타임라인, RDP, 원격 제어 도구 |
| 안티 포렌식 | ADS, 숨김/시스템 속성, 타임스탬프 조작 의심, 와이퍼 흔적 |
| 침해사고 | 웹셸, 웹 서버 로그, LotL/파일리스, IOC 일치, 교차 케이스 지표, 랜섬웨어 흔적 |
| 메모리 | Volatility 정규화, 덤프 스캔 |
| 위치·여행 | EXIF GPS, 클라우드 위치 |

각 노드는 (컬렉션, kind, artifact_type[], ext[], host_group) 매핑 한 줄로 정의한다(`features/tree/domains.ts`). 건수는 서버 `/tree`가 준다. 0건 노드는 흐리게 + 사유. 트리 검색 입력.

## 5. P1·P4·P2에 미치는 영향

- **P1 프런트(진행 중)**: "분석 작업" 트리 섹션 → **처리 단계의 추가 분석 카드**로 바꾼다. AnalysisDialog·진행 칩·이력·결과 그리드는 그대로 쓰되, 결과는 탐색 도메인 트리 노드(위 매핑)로 노출. 레일 + 단계별 왼쪽 패널 + URL 단계 체계를 이번 P1에서 도입(가장 큰 구조 변경이므로 지금 하는 게 가장 싸다). 기존 라우트 리디렉션 유지, e2e 갱신.
- **P1 백엔드**: 변경 없음(`/analyses` 계약 그대로). `/tree`에 도메인 그룹 응답 추가는 P4에서.
- **P4**: 도메인 트리 2차 노드 완성(파일 유형·안티 포렌식·침해사고·웹 호스트군)을 §4 표대로.
- **P2**: 처리 단계의 처리 계획표(그룹/태스크)가 자리를 갖는다.
- **시각 품질 라운드**: 레일·단계 패널이 생기므로 그 뒤에 적용.

## 6. 왜 이 구조가 최선인가(검증 가능한 주장)

1. 검사관의 질문이 세 가지("다음에 뭘 하지" = 레일, "뭐가 나왔지" = 도메인 트리, "뭘 더 돌리지" = 처리)로 분리되어 각 화면이 한 가지만 답한다.
2. 분석 결과가 포렌식 맥락(도메인)에 붙으므로 보고서 인용 경로가 자연스럽다(예: "파일시스템 › 복구/카빙 › JPEG #12").
3. 처리 계획표가 생겨 "3일짜리 런에서 무엇이 끝났고 무엇을 건너뛰었는지"가 보인다(마에스트로 진행 대화상자의 핵심 가치).
4. 범주가 사건 유형(침해사고·정보 유출·안티 포렌식)으로 묶여 모드별 조사 흐름과 일치한다.
5. 상단 바·뷰어·상태 바는 그대로라 기존 단축키·리뷰 루프·a11y 계약이 보존된다.
