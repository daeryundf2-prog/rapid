# P1 — 분석 작업 워크벤치: CLI에만 있던 분석을 콘솔에 노출 (2026-10-12)

상위: `docs/plans/maestro-gap-review-2026-10-12.md` §5 P1. 브랜치 `feat/analysis-workbench-p1`.
범위: 콘솔(frontend) + API 얇은 층 + 런 디렉터리의 `analyses/` 저장. 기존 코어 함수(`core/carving.py`, `core/vsc.py`, `core/ntfs_metadata.py`, `core/cross_case.py`, `api/app/image.py` OCR, `artifacts/memory.py`)를 호출만 하고 알고리즘은 바꾸지 않는다. 복구 엔진·파서·DB 스키마 불변.

## 1. 최종 사용자가 보는 문제

마에스트로에서는 리본의 "복구/카빙", "메모리 덤프|분석", "볼륨 섀도우 분석", "OCR 추출/번역/분석", "웹 로그 분석"이 버튼이다. 우리 검사관은 같은 일을 하려면 터미널에서 `rapidtriage carve …`, `vsc-compare …`, `ntfs-meta …`, `ocr-queue …`, `cross-case-correlate …`를 알아야 하고, 결과 JSON을 직접 열어야 한다. 파일 행에는 생성/접근 시각과 MFT 엔트리가 없어 법정 인용에 쓸 수 없고, 열 머리에서 바로 거를 수도 없다.

## 2. 이상 상태

- **U-P1-1 분석 작업 섹션**: 트리에 "분석 작업" 섹션이 있고 노드 7개 — 카빙 · 볼륨 섀도우 · NTFS 메타(MFT/USN) · OCR 일괄 · 메모리 · 웹 로그·웹셸 · 교차 케이스. 노드를 열면 (a) 마지막 실행 결과 그리드, (b) "실행…" 버튼(옵션 대화상자, 예상 범위·주의 표시), (c) 실행 이력(상태·시작·소요·건수·취소). 실행 중이면 상태 바에 진행 칩(%, 메시지)과 취소 버튼.
- **U-P1-2 영속**: 분석 결과는 런 디렉터리 `analyses/<id>/`에 저장되어 서버 재시작·런 재열람 후에도 보인다. 결과 행은 아티팩트처럼 페이징·서버 정렬·리뷰 표시·뷰어 연결이 된다.
- **U-P1-3 파일 행 출처**: NTFS 메타 분석을 한 번 돌리면 파일 그리드와 메타 탭에 생성·접근·MFT 수정 시각, MFT 엔트리 번호, 파일 시스템(NTFS), 소스 이미지 경로가 채워진다. 돌리기 전에는 열 머리/메타에 "NTFS 메타 분석을 실행하면 채워집니다" 링크가 있다(조용히 빈 칸 금지).
- **U-P1-4 열 머리 필터**: 툴바 "열 필터" 토글로 열마다 입력(텍스트 포함, 시각 from/to, 숫자 min/max)이 열리고, URL에 실린다. 서버가 지원하는 열(아티팩트 경로·유형, 검색 확장자)은 서버에서, 나머지는 불러온 행에서 걸러지며 상태줄에 "불러온 n행 기준"이 명시된다.
- **U-P1-5 유형 필터 서버화**: 아티팩트 API가 `artifact_type=`(반복)로 거른다. 웹 로그·웹셸 노드는 windows-system kind의 `web-server-log`·`webshell-source-candidate`만 보여준다.

## 3. API 계약 (B가 구현, A는 이 계약으로 mock)

### 3.1 분석 작업
- `POST /api/runs/{run_id}/analyses` body `{"kind": K, "options": {...}}` → 202 `{"analysis_id","kind","status":"queued","analysis": AnalysisState}`. 런이 completed/failed가 아니면 409. 같은 kind의 분석이 이 서버 프로세스에 등록돼 있으면(실행 중, 대기 중, **취소 요청 후 스레드가 아직 멈추지 않은 경우 포함**) 409 `"이미 실행 중인 분석이 있습니다"`.
- `GET /api/runs/{run_id}/analyses` → `{"analyses":[AnalysisState…]}` (최신순).
- `GET /api/runs/{run_id}/analyses/{id}` → AnalysisState.
- `POST /api/runs/{run_id}/analyses/{id}/cancel` → AnalysisState. 취소는 **요청**이다: `cancel_requested_at`이 채워지고 `status`는 `queued|running` 그대로이며, 러너가 단위 작업 경계에서 멈춘 뒤 `cancelled`(+`finished_at`)가 기록된다. 클라이언트는 폴링으로 `cancelled`를 확인한다. 아직 작업자가 잡지 않은 `queued` 분석은 대기열에서 바로 빠지고 응답 자체가 `cancelled`(+`finished_at`)이며 같은 kind를 곧바로 다시 제출할 수 있다. 등록 뒤 실행기 시작(스레드 생성·대기열 투입)이 실패하면 등록을 풀고 `failed`(`error="분석 실행기를 시작할 수 없습니다: …"`)로 끝난 상태를 202로 돌려준다.
- `GET /api/runs/{run_id}/analyses/{id}/rows?offset&limit(1..1000)&sort&order&locate&path_contains` → `{run_id, analysis_id, kind, status, rows[…record_index], record_count, matched, pagination{…}, sort?{…}}`. 정렬은 `artifact_sort` 인덱스를 끝난 분석의 `rows.jsonl`에 그대로 적용(캐시 키 = run id + `analysis:<id>#<row_count>` + 파일 크기/mtime; 같은 분석의 이전 `#<n>`·이전 파일 판은 새 인덱스가 밀어냄). `queued|running` 분석에 `sort`를 주면 인덱스를 만들지 않고 JSONL 순서 페이지에 `sort.status:"unsupported"`, `reason:"실행 중인 분석은 전체 정렬을 할 수 없습니다. 분석이 끝난 뒤 다시 정렬하세요."`(아티팩트 정렬의 unsupported와 같은 모양)를 돌려준다. `order`가 asc/desc가 아니면 `sort`가 없어도 400 "정렬 순서(order)는 asc 또는 desc여야 합니다"(대소문자 무시; `GET /artifacts`는 `sort` 없는 `order`를 예전처럼 무시). `record_count`는 디스크에 flush된 행 수(실행 중에도 읽을 수 있는 행만)이고, 모든 읽기(페이지·`path_contains`·정렬 인덱스·정렬 대체 경로)는 `row_count`번째 레코드 앞에서 멈춘다 — 실행 중인 분석이 아직 세지 않았거나 쓰는 중인 줄은 내보내지 않는다. 손상된 줄은 건너뛰되 `{`로 시작하는 줄은 번호를 소비(아티팩트와 같은 번호 규칙). 정렬 인덱스가 파일 변경으로 낡으면 409 "정렬 인덱스가 오래되었습니다. 다시 시도하세요".
- AnalysisState = `{analysis_id, run_id, kind, label, status: queued|running|completed|failed|cancelled, options(정규화된 값), created_at, started_at?, finished_at?, elapsed_s?, cancel_requested_at?, progress: {done, total|null, unit, message, percent|null}, row_count, output_dir, rows_path, summary: {...kind별}, error?: str(한국어), interrupted_reason?}`. `progress`는 단조: `done`은 줄지 않고 `total ≥ done`, `percent`는 완료 전 최대 99.9, `completed`일 때만 100.
- 저장: `<run output_dir>/analyses/<id>/analysis.json`(상태; 변화 시와 1초 이하 간격, 실행 중에는 15초 heartbeat로 atomic replace, 종료 상태는 재시도를 늘리고 실패하면 일반 쓰기로 대체) + `rows.jsonl`(결과 행 `{"artifact_type": "<kind>-row", "path"?: str, "details": {...}}`) + kind별 파일. `analyses/index.json`은 쓰지 않고 디렉터리 나열로 복원.
- 실행: API 프로세스 전역 데몬 스레드 풀(작업자 2개); `threading.Event`로 취소. 앱 종료(FastAPI lifespan) 시 **그 앱이 제출한** 실행 중 분석에 취소 이벤트를 걸고 그 앱의 대기 중 작업은 버려 `cancelled`로 기록한다(`create_app`마다 소유자 토큰 `app.state.analysis_owner`; 같은 프로세스의 다른 앱 분석과 공유 풀은 건드리지 않음). 소유자 없이 `AnalysisRunner.shutdown()`을 부르면 전부 취소하고 풀을 멈추며, 풀은 다음 제출 때 다시 만든다.
- 재시작 복원: 실행 중 상태에는 내부 소유자 `{pid, boot_id, heartbeat_at}`이 기록된다(API 응답에는 나오지 않음). 이 프로세스가 실행하지 않는 `queued|running` 상태는 소유 프로세스가 죽었거나, 재부팅됐거나, 이 프로세스 자신이거나, heartbeat가 90초 넘게 끊긴 경우에만 `failed`·`error="서버 재시작으로 중단"`·`interrupted_reason`으로 **보여 준다**(읽기는 상태 파일을 고쳐 쓰지 않는다). 다른 살아 있는 서버 프로세스가 소유하면 그대로 `running`.
- 보안(경로): 모든 경로 옵션은 파일 시스템 호출 전에 형태로 먼저 거른다 — UNC(`\\server`)·`\\?\`·`\\.\`·`//…`, 상대 경로, 드라이브 상대(`C:foo`), 루트 상대(`\foo`), `~`는 403. 그다음 `os.path.abspath` 결과를 허용 루트와 어휘적으로 비교하고, resolve 전에 허용 루트 아래 경로 구성 요소를 `lstat`(따라가지 않음)으로 보고, 심볼릭 링크·정션이면 저장된 대상(`readlink`)을 읽어 UNC(`\\server`, `\\?\UNC\…`, `//…`)이거나 허용 루트 밖이면 대상을 열지 않고 403 "링크를 거쳐 … 밖을 가리킵니다"(루트 안 대상은 같은 방식으로 계속, 최대 40단계). 마지막으로 resolve(심볼릭 링크·정션)한 경로를 다시 비교한다(링크로 빠져나가면 같은 403). 입력 허용 루트 = 런 root/scan_scope_root/output_dir/source.analysis_root/stage_dir/source_path + `allowed_source_roots` + `RAPIDTRIAGE_ANALYSIS_ROOTS`(**입력 전용**: 증거로 취급하며 출력 대상이 아니다); 출력 허용 루트 = 런 출력 디렉터리 + `RAPIDTRIAGE_ANALYSIS_OUTPUT_ROOTS`(같은 파싱 규칙). 출력 허용 루트 안이어도 스냅샷·스캔·소스·스테이지·입력 루트(`RAPIDTRIAGE_ANALYSIS_ROOTS` 포함) 안이면 403 "추출 출력 경로가 증거 경로(…) 안에 있어 쓸 수 없습니다" — 그 루트가 런 출력 디렉터리를 품고 있고 출력이 런 출력 디렉터리 안일 때만 예외. 출력 허용 루트 밖이면 403 "… 허용 범위(런 출력 디렉터리 또는 서버 허용 출력 루트(RAPIDTRIAGE_ANALYSIS_OUTPUT_ROOTS)) 밖에 있습니다". 환경 변수 항목은 플랫폼 경로 구분자(Windows `;`)로 나누고 따옴표를 벗기며, 상대·UNC·`~` 항목은 경고 로그와 함께 무시한다. 외부 프로그램 실행 없음(ntfs-meta는 기존 Sleuth Kit 러너, OCR은 기존 검색 경로의 tesseract). OCR 재사용 색인도 각 분석의 `row_count` 앞에서 멈춘다.
- 오류 모양: 400(알 수 없는 kind·경로 해석 불가·이미지 없음·필터에 `limit=0` 등)·403(경로 형태/허용 루트 위반)·404(분석 없음)·409(런이 completed/failed 아님, 같은 kind 등록 중, 낡은 정렬 인덱스)는 모두 평문 `{"detail": "<한국어 문장>"}`. 옵션 검증 실패는 422 `{"detail": [{"loc": ["options", <필드>…], "msg": "<한국어>", "type": <pydantic 오류 유형>}]}`(대화상자 필드별 표시용); 바이트 필드(`*_bytes`)의 범위 메시지는 MB로 표기("16,384 MB 이하", 최소 1바이트는 "0 MB보다 커야 합니다"). 본문 자체가 잘못된 경우(JSON 아님, 객체 아님, `kind` 없음)도 같은 422 목록 모양에 한국어 메시지(`loc`은 `["body", …]`). 조사는 라벨 마지막 음절의 받침으로 고른다(`with_josa`: "최대 후보 수는", "카빙 파일 저장은", "파티션 시작 섹터가"; 괄호 꼬리 `(kind)`는 무시, 숫자는 읽는 소리, 판단할 수 없는 라틴 문자만 "은(는)"). 콘솔이 쓰는 런 공통 오류도 한국어: 404 "런을 찾을 수 없습니다", 404 "런 출력을 찾을 수 없습니다", 409 "완료된 런이 아닙니다", review-batch 400 "케이스 DB에 이 런 로케이터에 해당하는 행이 없습니다: <collection:kind:locator, …>"·"로케이터 대상에는 run_id가 필요합니다"(기계 판독 코드는 원래 없음).

### 3.2 kind별 옵션과 결과 행 (details 키)
| kind | 옵션 | 단위/진행 | 결과 행 details |
|---|---|---|---|
| `carve` | `ext?`(문자열 쉼표 구분 또는 목록), `kinds?[]`, `max_scan_bytes`(≤16,384 MB), `max_carve_bytes`(≤1,024 MB), `max_candidates`(≤100,000), `extract: bool`, `include_rejected: bool`(기본 false) | 소스 파일 1개 = 1단위(후보 상한 도달 시 total = 확인한 파일 수). 취소는 파일마다가 아니라 스캔 청크(8 MB)마다와 후보마다 확인하고, 행은 후보가 만들어질 때마다 기록하므로 큰 파일 도중 취소해도 그 앞 후보 행이 남는다. 구조 검증에서 거부된 후보(`status:"false-positive-rejected"`, `length` 0)는 `max_candidates`에 세지 않고 `summary.rejected_count`(전체 수)로만 센다; `include_rejected=true`일 때만 행으로 내며 그 행은 따로 최대 `max_candidates`개(`summary.rejected_row_count`). `summary.candidate_count`는 거부되지 않은 후보 수. 소스 순회는 심볼릭 링크·정션·재분석 지점 디렉터리를 따라가지 않고 링크 파일도 건너뛰며(`summary.skipped_link_count`), `rapidtriage-run*` 폴더와 이 런의 출력 디렉터리는 가지치기(`summary.pruned_output_dir_count`); 소스 목록은 메모리 대신 분석 디렉터리의 임시 파일에 쌓고(디렉터리마다 이름순 깊이 우선 순서) 끝나면 지운다 | `signature_kind, source_path, offset, offset_hex, end_offset, length, sha256, extracted_path?, confidence, status, extension, notes`; 행 `path` = 소스 파일 |
| `vsc-discover` | `max_depth`(0..1, 기본 1: 스캔 루트의 부모를 한 단계까지만) | 디렉터리 | `snapshot_root, label, score, reason, file_count_bounded, exists`. **입력 허용 루트 밖의 탐색 루트·후보는 파일 시스템 호출(나열·stat·파일 수 세기) 전에 건너뛴다** — 허용 루트 밖인 부모는 나열하지 않고, 그 아래에 있는 허용 루트만 후보로 걷는다. 결과 행, `vsc-discovery.json`, vsc-compare의 `snapshot_discovery`, `summary.search_roots`에는 허용 루트 안의 경로만 남고 건너뛴 수는 `summary.excluded_outside_roots` — compare/extract가 거부할 경로를 제시하지 않는다. 이 런의 출력 디렉터리(그 아래 `analyses/<id>/extract` 복사본 포함)와 `rapidtriage-run*` 폴더는 후보로 내지 않고 그 아래를 걷지도 않으며(CLI도 `rapidtriage-run*`는 제외), 링크 디렉터리는 따라가지 않는다 |
| `vsc-compare` | `snapshot_root`(입력 허용 루트 아래여야 함; discover 결과라도 예외 없음), `hash: bool`, `case_sensitive`, `max_records` | 파일 인덱스 항목. 현재 루트·스냅샷 인덱스는 링크를 따라가지 않는다(`vsc-compare.json` 비교 요약 `link_skipped_count`); CLI `vsc-compare`는 예전처럼 따라간다. 건수 `summary.deleted/modified/added`는 **전체 변경 기준(정확)**이고, 행 목록만 `max_records`로 자르되 deleted → modified → added 순(각 안에서는 경로순)으로 채운다. `summary.change_count`(전체 변경 수), `summary.record_count`(기록한 행 수), `summary.truncated`(변경 일부가 행에서 빠졌을 때만 true), `summary.truncated_reason`(한국어, 아니면 null). ### 3.3 파일 행 보강과 유형 필터
- `GET /api/runs/{run_id}/files` 각 행에 `ntfs: {entry_number, created_at, accessed_at, mft_modified_at, in_use} | null`, `filesystem: "NTFS"|null`, `source_image: str|null`. 가장 최근 completed `ntfs-meta` 분석과 조인한다.
  - 조인 대상: `summary.mft_record_count > 0`인 가장 최근 completed `ntfs-meta`(`parse=false`·`too_large`인 분석은 그 전의 파싱된 분석을 가리지 않음). 색인에는 `path_status == "reconstructed-bounded-parent-cache"`(완전 재구성) MFT 행만 넣는다. 같은 경로 키에 in-use 행이 정확히 하나면 그것(삭제 행보다 우선), in-use 행이 둘 이상이거나 삭제 행만 둘 이상이면 모호한 키로 조인하지 않는다.
  - 색인: (run, analysis, rows.jsonl 크기/mtime) 키로 한 번만 만든다(같은 키의 동시 요청은 하나의 빌드를 기다림). 런마다 색인 하나만 유지(새 분석이 이전 것을 밀어냄, 최대 4개 런). 경로별로 `entry_number, created_at, accessed_at, mft_modified_at, in_use`만 압축 저장(경로 키는 casefold NFC 경로의 64비트 blake2b 해시), USN 줄은 `json.loads` 전에 바이트 검사로 건너뛴다. 예상 크기(MFT 레코드 수 × 200바이트)가 512 MB를 넘으면 만들지 않고 `ntfs_join.status="too_large"`와 한국어 `reason`.
  - 볼륨 접두어: 런마다 한 번 정한다 — 런 스캔 루트/스테이지 디렉터리 바로 아래 경로가 색인에 있는 센티널(`Windows`·`Users`·`$MFT`)로 시작하면 그 루트, 아니면 그 아래 깊이 1~3에서 센티널이 맞는 첫 디렉터리. 행은 이 접두어 기준 상대 경로로만 조인하며 **행마다 앞 구성 요소를 잘라 보지 않는다**(`Backup/Old/Windows/System32/foo.dll`은 `\Windows\System32\foo.dll`과 조인되지 않음).
  - 응답 `ntfs_join: {analysis_id|null, status: joined|no_analysis|no_volume_prefix|too_large|skipped, matched, total, analysis_total|null, volume_prefix|null, prefix_method|null, partition|null, reason?}`. `matched/total`은 **이번 페이지 행 기준**(전체 파일 수가 아님), `analysis_total`은 조인한 분석의 전체 결과 행 수(MFT+USN), `partition`은 그 분석의 파티션 시작 섹터. 런 출력 디렉터리를 확인할 수 없으면 조인만 건너뛴다(`status:"skipped"`, 409 아님).
  - 모든 행(필터 여부와 무관)은 `record_index` = rapidtriage-files.json `candidates` 안의 원래 위치(로케이터 `/candidates/<record_index>`)를 가진다.
  - `category=`(반복)는 행 `categories` 목록에 대한 서버 필터로 `record_count/matched/scanned/truncated`를 보고(트리 범주 개수와 그리드 행이 일치). `limit=0`이면 400.
- `GET /api/runs/{run_id}/artifacts?artifact_type=`(반복) 서버 필터(스트리밍, 정렬·path_contains와 조합 가능, `scanned/truncated` 보고). 필터(`artifact_type`/`path_contains`)에 `limit=0`이면 400 "필터는 limit>0에서만 지원합니다".
- 개수 필드(아티팩트 kind 페이지와 분석 `rows` 공통): `record_count` = 필터 전 전체 행 수, `matched` = `path_contains`/`artifact_type` 일치 수(필터 스캔이 kind 끝까지 갔을 때만 정확, 스캔 상한(`truncated`)이나 페이지 다음 행 확인(`has_more`)에서 멈췄으면 `null`; 필터 없으면 `record_count`와 같음), `pagination.scanned/truncated/matched`.
- 여러 kind에 걸친 필터: `artifact_type=` 또는 `path_contains`(또는 둘 다)가 있고 `kind=`가 없거나 2개 이상이며 `sort`가 없으면 `offset/limit`은 kind들(요청 순서, 없으면 알파벳순)을 한 컬렉션으로 이어 페이지한다. 요청당 스캔 상한 200,000행(상한에 정확히 맞춰 끝나면 `truncated=false` — 단일 kind 필터 페이지도 같은 규칙). 응답 `cross_kind = {kinds, offset, limit, returned, order:[[kind, record_index]…], record_count, matched, has_more, next_offset, next_after, scanned, truncated}`, 각 kind 페이지에는 그 창의 행만. 다음 페이지는 `after=<next_after>`(`<kind>:<record_index>:<matched>`, 숫자 부분은 음이 아닌 정수만 — 아니면 400 "after 값은 … 형식(숫자는 0 이상 정수)이어야 합니다", 요청에 없는 kind면 400 "after 값이 이 요청에 없는 종류를 가리킵니다: …"; 마지막으로 소비한 행 뒤부터 재개; `offset`만 주면 처음부터 다시 스캔).
- 트리 kind 노드에 `artifact_type_counts`(출력 요약의 `artifact_type_counts` 그대로, 행 스캔 없음).
- 트리(`/tree`): `analyses` 노드 그룹 `{id:"analyses", label:"분석 작업", collection:"analysis", children:[{id:"analysis:<key>", label, kind:<key>, analysis_kinds:[POST할 kind…], count, latest, latest_completed, state}, …]}` — key는 `carve, vsc(vsc-discover/compare/extract), ntfs-meta, ocr-batch, memory-import, web-logs, cross-case`. `latest`는 그 노드 kind들의 최신 분석(상태 무관), `latest_completed`는 최신 completed 분석(각각 `{analysis_id, kind, status, finished_at, row_count}|null`), `count = latest_completed.row_count`(없으면 0), `state`는 `latest`의 별칭. 웹 로그·웹셸 노드는 분석 없이 `link:{collection:"artifacts", kind:"windows-system", artifact_types:["web-server-log","webshell-source-candidate"], node_ids:[…]}`로 이동하며 count는 두 유형 개수 합. 기존 아티팩트 유형 자식의 id는 **`artifacts:<kind>:<artifact_type>`**(예: `artifacts:windows-system:web-server-log`; `kind`·`artifact_type` 필드도 있음).
- 디렉터리 행: `GET /api/runs/{run_id}/source-metadata?path=<디렉터리>`는 200 `{command:"source-metadata", path, name, extension:"", is_directory:true, size:null, modified_at, created_at, mime_type:"inode/directory", hashes:{}, hash_status:"not-applicable-directory"}`(`hash=true`여도 해시 없음), `GET …/source-preview?path=<디렉터리>`는 200 `{run_id, path, name, extension:"", is_directory:true, size:null, modified_at(epoch 초), mime_type:"inode/directory", metadata_url, preview_type:"directory", text:"", truncated:false, message:"디렉터리는 미리보기가 없습니다. 디렉터리 안의 파일을 선택하세요.", viewer_metadata{source_format:"directory", strategy:"directory-no-preview", preview_status:"not-applicable", …}}`. 파일 응답에는 `is_directory:false`가 추가됐다. 다른 소스 라우트(hex-range, 썸네일 등)는 디렉터리에 예전처럼 404. 프런트엔드는 디렉터리 행에서 미리보기를 요청하지 않는다.
- 리뷰 표시: `review-batch` 대상에 `{collection:"analysis", kind:"<analysis_id>", locator:"/rows/<record_index>"}`를 받아 case-db `review_mark`의 `target_type:"analysis_row", target_id:"<analysis_id>/<record_index>"`로 기록(`run_review.py`; 그 런의 출력 디렉터리 아래에 분석이 있고 `record_index < row_count`일 때만, 아니면 400). `/review-map`은 같은 `{collection:"analysis", kind, locator}`로 돌려준다.
- 리뷰 보드·개수에서 **해제된 표시 제외**: 상태를 `unreviewed`로 되돌려 기본값만 남은 표시(`status=unreviewed`, 메모·태그 없음, `include_in_report=false`, `verification_status=unverified`)는 `review_mark` 행과 `review_mark_history`(감사 기록)에 그대로 남지만 `GET /review-map`의 `marks`에 나오지 않고 `GET /review-counts`의 `by_status`·`include_in_report`·`report_candidates`에도 세지 않는다. `review-counts`에 `cleared: int`(해제된 표시 수, 참고용)가 추가됐다. 메모·태그·보고서 포함·검증 상태 중 하나라도 있으면 `unreviewed`여도 보드에 남는다.
- 분석 행 보드 항목: `/review-map`의 `target_type:"analysis_row"` 표시에 `title`(사람이 읽는 제목 — 카빙 `"<시그니처> 후보 @ <offset_hex> · <파일명>"`, VSC 비교 `"삭제|수정|추가 · <상대 경로>"`, NTFS MFT `"<경로>"`/`"MFT 엔트리 #N (이름 없음)"`(+삭제 행은 `" (삭제됨)"`), USN `"USN <reason> · <경로>"`, OCR `"<파일명> · <텍스트 앞 60자>"`, 메모리 `"<memory_artifact_type> · <이름>"`, 교차 케이스 `"<kind> · <indicator>"`, 그 밖 `"<종류> 결과 #<n>"`), `path`(행 `path` 또는 `details.source_path`), `timestamp`, `target_kind`(종류 라벨 + "결과": `"카빙 결과"`, `"볼륨 섀도우 비교 결과"`, `"NTFS 메타(MFT/USN) 결과"`, `"OCR 일괄 결과"` …), `analysis_kind`(`carve` 등 kind 키)가 채워진다. 행을 더 읽을 수 없으면 `title:"분석 결과 행 #<n> (읽을 수 없음)"`. 원시 id(`analysis_row <id>/<n>`)는 제목으로 쓰지 않는다.
- 분석 행 원본 열기(뷰어): 모든 소스 라우트(`source-metadata`, `source-preview`, `source-file`, `source-thumbnail`, `source-hex-range`, `source-sqlite-table`, `source-sqlite-wal-preview`, `source-email-attachment`, `source-image-gallery`, `source-media-cue`, `source-ocr-queue`, `source-ocr-translation`, `source-search`)에 선택 쿼리 `analysis_id=<분석 id>&locator=/rows/<record_index>`가 있다. 경로가 런 증거 루트 안이면 예전과 같고, 밖이면(예: vsc-compare `deleted`/`modified` 행의 스냅샷 안 경로) **그 행 자신의 경로**(`path`·`details.source_path`·`details.destination` 중 하나와 같은 절대 경로)일 때만, 그 분석의 검증된 입력 루트(옵션 `snapshot_root`·`volatility_output_dir`를 지금의 입력 허용 루트로 다시 confine한 것) 안에서 §3.1과 같은 검사(`confine_path`+`precheck_links`, 링크로 밖을 가리키면 403 "…링크를 거쳐…")로 읽기 전용으로 연다. 오류: 로케이터 형식 400 "분석 행 로케이터는 /rows/<번호> 형식이어야 합니다", 행 없음 404 "분석 결과 행을 찾을 수 없습니다", 다른 행·임의 경로 403 "요청한 경로가 이 분석 결과 행의 경로가 아닙니다", 스냅샷 루트가 더는 허용 루트가 아니면 403, 파일이 사라졌으면 404 `{detail:{message:"이 분석의 입력 루트에서 원본 파일을 찾을 수 없습니다", path}}`. 콘솔은 분석 행에서 뷰어를 열 때 이 두 쿼리를 항상 붙인다(일반 경로 접근은 넓어지지 않음).
- 소스 라우트 공통 오류 문구(한국어): 404 `{detail:{message:"허용된 증거 루트에서 원본 파일을 찾을 수 없습니다", source_path_resolution}}`, 403 `{detail:{message:"원본 파일이 허용된 증거 루트 밖에 있습니다: <경로>", source_path_resolution}}`(예전 영어 "source file not found in allowed evidence roots" / "source file is outside allowed evidence roots" 대체; 모양 동일).
- 분석 대화상자 파일 선택기: `GET /api/browse?scope=analysis-input|analysis-output&run_id=<런>&path?&show_hidden?`. `scope`가 없으면 예전 그대로(런 생성·가져오기 대화상자의 전체 파일 시스템 선택기, 홈에서 시작). `scope`가 있으면 그 런의 입력 허용 루트(§3.1: 런 root/scan_scope_root/output_dir/analysis_root/stage_dir/source_path + `RAPIDTRIAGE_ANALYSIS_ROOTS`) 또는 출력 허용 루트(런 출력 디렉터리 + `RAPIDTRIAGE_ANALYSIS_OUTPUT_ROOTS`)만: 응답은 기존 `BrowseListing` 모양에 `scope`, `scope_label`, `run_id`, `at_roots: bool`이 붙고 `roots:[{name, path, kind:"directory"|"file"}]`(존재하는 허용 루트, 중복 제거; 파일 루트 = 런 소스 이미지), `home:""`. `path`가 없으면 `path:""`, `parent:null`, `at_roots:true`, `entries` = 루트 목록(`kind`, `evidence_candidate:true`, 파일이면 `size_bytes`). `path`가 있으면 §3.1 경로 검사(`confine_path`) 후 그 디렉터리(파일이면 부모 — 부모가 허용 루트 밖인 파일 루트면 루트 목록)를 나열하고, 루트 자체이거나 부모가 루트 밖이면 `parent:null`(콘솔은 `path` 없이 다시 불러 루트 목록으로). 허용 루트 밖 → 403 "찾아보기 경로가 허용 범위(…) 밖에 있습니다: …"(UNC·상대·`~`도 403, 링크로 빠져나가면 403). 400: 알 수 없는 scope "알 수 없는 찾아보기 범위(scope)입니다: …", run_id 없음 "분석 찾아보기(scope)에는 run_id가 필요합니다"; 런 없음 404 "런을 찾을 수 없습니다". 입력 필드(`snapshot_root`, `image_path`, `volatility_output_dir`, OCR 경로)는 `analysis-input`, 출력 필드(`output_dir`)는 `analysis-output`.

- (구현 메모, A 2026-10-12) **IA 변경 반영**(`console-ia-2026-10-12.md`): "분석 작업" 트리 섹션은 만들지 않았다. 실행·진행·이력·취소는 처리 단계 카드(`#/case/{run}/process[/{node}]`), 결과는 탐색 도메인 트리 노드(파일시스템 › 복구/카빙·MFT/USN·볼륨 섀도우, 미디어·문서 › OCR 텍스트, 메모리 › 메모리 분석 가져오기, 침해사고 › 교차 케이스 지표 → `#/case/{run}/explore/analysis/{node}?id=`). 웹 로그·웹셸은 침해사고 › 웹셸 / 웹 서버 로그 노드(`explore/artifacts/windows-system?types=…` → 서버 `artifact_type=`). 옛 `#/case/{run}/{collection}` 링크는 시작 시와 hashchange 때 replace로 단계 URL로 바뀐다.
- (구현 메모) **`cf=` 문법**(`router.ts` `parseColumnFilters`/`serializeColumnFilters`): `cf = entry *("," entry)`, `entry = enc(열 id) op enc(값)`, `op = ":"`(텍스트 포함, 시각 열은 `from..to` — 한쪽 생략 가능, 날짜만 쓰면 UTC 그 날 전체) `| ">"`(최솟값, 이상) `| "<"`(최댓값, 이하). `enc`는 encodeURIComponent라 열 id·값에 날 `,` `:` `<` `>`가 없고, 열 id 다음 첫 연산자가 경계다. 브라우저가 프래그먼트의 `<`·`>`를 `%3C`·`%3E`로 바꿔도 연산자로 읽는다. 열 id는 그리드 `ColumnSpec.id`(`path`, `size`, `d:<details 키>`, 승격 열 `f:<키>`). 예: `cf=path:foo,size>1000,timestamp:2025-01-01..2025-02-01`.
- (구현 메모) **서버/클라이언트 분할**(`filterModel.partitionFilters`): 아티팩트 `path` 열 → `path_contains`(필터 바 경로가 있으면 그것이 우선, 열 필터는 클라이언트), `type` 열 → `artifact_type`(정확히 일치), 분석 결과 `path` 열 → `path_contains`, 검색 `extension` 열 → `extension`. 나머지 열은 불러온 행(최대 8페이지 자동 로드)에서 걸러지고 상태줄 "열 필터: n건 / 불러온 m행 기준". 필터 바 유형은 아티팩트에서 항상 서버 `artifact_type=`(반복, kind 유무 무관).
