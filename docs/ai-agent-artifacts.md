# AI coding-agent artifacts

Point the collector at a mounted or exported evidence directory containing the profile trees. Select a kind with the normal artifacts command.

```sh
python -m rapidtriage artifacts ./sample-evidence --kind codex-cli --output ./artifacts-codex-cli.json
```

The execution section of the evidence tree includes these kinds. Seizure, fraud, hacking and recovery runs schedule them.

| Kind | Evidence-relative paths | Records |
| --- | --- | --- |
| `claude-code` | `.claude/projects/**/*.jsonl`, `.claude/history.jsonl`, `.claude.json`, `.claude/settings{,.local}.json` | User and assistant text, tool use and results, working directory, model, typed prompt history with its project folder, and selected settings |
| `codex-cli` | `.codex/sessions/**/*.jsonl`, `.codex/history.jsonl`, `.codex/config.toml` | Replay messages, function and custom tool calls and results, turn model and working directory, prompt history and settings |
| `gemini-cli` | `.gemini/tmp/*/chats/*.json` or `*.jsonl`, `.gemini/tmp/*/logs.json`, `.gemini/settings.json` | Session messages, tool calls and embedded results, prompt logs and settings |
| `omp-pi` | `.omp/agent/sessions/**/*.jsonl`, `.pi/agent/sessions/**/*.jsonl`, `.senpi/agent/sessions/**/*.jsonl`, `.omo/agent/sessions/**/*.jsonl` (also omp profiles `.omp/profiles/*/agent/`), `.omp/agent/history.db`, `.omp/logs/omp.*.log`, `<home>/agent/config.yml`, `settings.json`, `models.yml`, `models.yaml` or `models.json`; omp's Linux XDG layout `.local/share/omp/sessions/**`, `.local/share/omp/history.db`, `.local/state/omp/logs/omp.*.log`; any other `*.jsonl` whose first record is a pi-family session header | User, developer and assistant text, tool calls and results, commands the user ran directly, mentioned file paths, model, working directory, session and subagent lineage, prompt history, process log messages, and model names from settings |

The editor may appear under Windows `AppData/Roaming`, macOS `Library/Application Support` or Linux `.config` in the evidence. The recognized product directories are Cursor, Code, Code - Insiders and VSCodium. Product directories can belong to any profile. Discovery matches path components below the evidence root only; the examiner's own home directory and environment are never consulted, and symbolic links that leave the evidence root are skipped. The collector reads a verified private SQLite snapshot, includes committed WAL content and queries only ordinary tables. A WAL, shared-memory or journal sidecar that is not a regular file, or a hot rollback journal, makes the database unreadable with a diagnostic instead of being followed or replayed. SQLite locators identify a table, rowid and key. Recognized keys include `bubbleId:*`, `composerData:*`, `composer.composerData`, `aiService.prompts` and selected workbench chat keys. Index-only or unfamiliar chat values can produce a diagnostic.

### omp, pi, senpi and OmO

oh-my-pi (omp) and pi write the same JSONL session format, and senpi and OmO (which runs senpi with the agent directory `~/.omo/agent`) are pi forks that keep it. One collector, `omp-pi`, reads them all. `agent` names the product from the folder: `omp`, `pi`, `senpi` or `omo`. A session saved elsewhere, for example with `--session-dir` by a tool that launches omp, is recognized by its first logical record: the `session` header with a string `id`, after omp's fixed-width `title` slot when present. omp's loader rejects a file by the same check. Because this check runs on every unclaimed `.jsonl` in the evidence, not only on session folders, the header must also carry the string `cwd` and `timestamp` that omp and pi always write, and the first 64 KiB are decoded as strict UTF-8, as the session reader decodes them; a byte-order mark or UTF-16 file is not taken as a session. Such a file gets `agent` `omp` when the title slot is present and `pi-family` otherwise, because the header does not name the product. The header check reads at most the first 64 KiB of each unclaimed `.jsonl` file and runs only for this kind. An unclaimed file that cannot be opened is skipped, not reported as an unreadable omp-pi source.

The header supplies `session_id`, `cwd` and `schema_version` (the session layout version). A fork or a subagent records its parent transcript as `parentSession`, exported as `parent_session`; omp writes subagent transcripts below the parent session's folder, so `source_path` shows the nesting too. Each row keeps the tree position of its entry as `entry_id` and `parent_entry_id`. `role` is the message role. omp also records on `user` and `developer` messages who initiated the turn, exported as `attribution`: `user` for input a person typed, `agent` for text an extension generated or relayed from another agent, such as a subagent's task prompt or a parent agent's steering. A row with role `user` and `attribution` `agent` was not typed by a person; its timeline summary names both. Rows without `attribution` come from a transcript that did not record it. `model_change` sets the model for the entries below it in the tree; an assistant message's own `model` names the model that answered. A file can hold abandoned branches: omp keeps every entry when the user branches from an earlier point, and keeps entries written by another process as a side branch. As omp's loader does, the last entry in the file is taken as the leaf, and rows whose entry is not on the `parentId` chain from that leaf back to the root are exported with the flag `off-active-branch`. When the file is longer than the 64 MiB read prefix the leaf is unknown and no row is flagged. Tool calls are `toolCall` blocks in assistant messages, and `toolResult` messages carry the call ID and tool name. `bashExecution` and `pythonExecution` are commands the user ran directly: each produces a call row with role `user` and a result row. `fileMention` rows keep only the mentioned paths, not the inlined file contents. System prompts, thinking blocks, compaction and branch summaries, extension messages and state entries are not exported. An unknown entry type or message role produces a diagnostic. A file in a sessions folder whose first record is not a header produces one `session-header-missing` diagnostic and is not read further.

omp's `history.db` table `history` keeps one row per distinct prompt. Its `created_at` is the latest submission, not the first, and `use_count` is the number of submissions. `logs/omp.<date>.<pid>.log` holds one JSON record per line; rows (`agent-log`) export only the time, `level`, `pid`, `message` and `sessionId`. Other log context fields can hold request data and are omitted. Settings rows export model names only: omp `config.yml` `modelRoles` (`model` is the `default` role, `model_roles` lists every role), pi-family `settings.json` `defaultProvider` and `defaultModel`, and one row per provider in `models.yml` or `models.json` with its `model_ids`. Provider base URLs, API keys, headers and authentication settings are never exported, and `secrets.yml`, `.env`, `auth.json` and `agent.db` are not read.

## Reading a row

`source_path` is relative to the evidence root. JSONL citations use a one-based physical line and zero-based byte offset. A whole JSON or TOML document starts at offset zero. Array indexes, project and server names distinguish entries within documents. SQLite rowids are logical locators.

Text messages, tool calls and tool results have distinct artifact types. An assistant message with text and two tool calls produces three rows. Structured tool arguments and patch headers supply referenced file paths. A call records a request to operate on a file. Any recorded result is a separate observation. Tool names can be associated with results by call ID within a session and file.

`timestamp_raw` preserves the source representation. `timestamp_utc` is ISO 8601 UTC with a `+00:00` offset. Text is normalized only when it is an RFC 3339 date-time with an explicit `Z` or `±HH:MM` offset (hours 00-23, minutes 00-59; an out-of-range offset such as `+01:60` is not rolled over); week dates, the basic format, a space separator and wall times without an offset are not guessed. Fraction digits are kept as recorded, padded to microseconds, so nanosecond digits are not rounded. Claude prompt history and editor values use integer epoch milliseconds and Codex history and omp prompt history integer epoch seconds, converted exactly. pi-family session rows use the entry's ISO 8601 time and fall back to the message's epoch milliseconds only when the entry has none; omp log lines record local time with its offset. Tool blocks can share the timestamp of their enclosing message. Embedded Gemini results share the recorded call time, which does not establish a separate completion time. The timeline uses only normalized evidence timestamps. A missing time stays empty. An ambiguous or invalid time carries `timestamp-not-normalized`. Missing session IDs, roles, models and paths stay empty.

`schema-version-not-validated` marks every row in this release. The input layouts have synthetic fixture coverage. A product version and a declared schema version are separate fields, copied only from the record that declares them (`version`, `cli_version`, `schemaVersion`, a VS Code chat session file's `version`, or a pi-family session header's `version`). When neither is recorded the row carries `version-unknown`; no version is inferred from field shapes. Gemini JSONL update and rewind records receive a diagnostic because reconstructing the final edited conversation requires replay. Codex user and assistant progress messages are compared with replay messages by role, exact text and occurrence count within the same turn of the same file. A turn starts at a `turn_context` record and is identified by its recorded `turn_id` (a context repeated with the same `turn_id` continues the turn); without one, each `turn_context` starts a new turn. A replay never stands in for a progress message of another turn. When one turn holds more progress copies of a message than replays, the earliest copies are paired and each remaining copy carries `replay-pairing-ambiguous`, because the source does not record which copy a replay duplicates. If a progress message is present, a second bounded pass counts up to 20,000 replay messages. Independent prompt history may document the same interaction. pi-family sessions are trees: every recorded entry is exported in file order, including branches the session later abandoned, and `context_edit` replacements are not applied.

## Bounds and privacy

| Scope | Limit and behavior |
| --- | --- |
| JSONL | 64 MiB prefix per source, 1 MiB per physical line including its delimiter. Oversized lines are drained in bounded chunks. Malformed UTF-8, malformed JSON and oversized lines produce cited diagnostic rows with a damage count. |
| Whole JSON, TOML or YAML | 8 MiB per document. Larger documents produce a diagnostic. Without PyYAML installed, a YAML document produces a `parser-unavailable` diagnostic and the other sources are still read. |
| SQLite | 256 MiB for the database and sidecars combined, 2 MiB per selected value. Oversized inputs produce diagnostics. |
| Output | 20,000 rows per source and kind, then a limit diagnostic. Text fields hold up to 8,192 characters and lists up to 64 entries. Tool-name correlation retains up to 1,024 call IDs per source. |

MCP rows select server names, executable commands and environment variable names. Environment values, server arguments, headers and connection URLs are omitted. Every exported text field, including commands, file paths and tool results, passes redaction before it reaches a row: Rapid's URL credential redaction, the whole value of `Authorization`, `Proxy-Authorization`, `Cookie` and `Set-Cookie` headers in any scheme, credential assignments and option values (API keys, access and secret keys, tokens, passwords), bearer and basic credentials, private key blocks, JSON Web Tokens, AWS access key IDs and common token prefixes (`sk-`, GitHub, GitLab, Slack, Google, Hugging Face, npm). Arbitrary free text and command lines can still contain sensitive material without a recognizable label.
