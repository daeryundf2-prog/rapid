# AI coding-agent artifacts

Point the collector at a mounted or exported evidence directory containing the profile trees. Select a kind with the normal artifacts command.

```sh
python -m rapidtriage artifacts ./sample-evidence --kind codex-cli --output ./artifacts-codex-cli.json
```

The execution section of the evidence tree includes these kinds. Seizure, fraud, hacking and recovery runs schedule them.

The editor may appear under Windows `AppData/Roaming`, macOS `Library/Application Support` or Linux `.config` in the evidence. The recognized product directories are Cursor, Code, Code - Insiders and VSCodium. Product directories can belong to any profile. Discovery matches path components below the evidence root only; the examiner's own home directory and environment are never consulted, and symbolic links that leave the evidence root are skipped. The collector reads a verified private SQLite snapshot, includes committed WAL content and queries only ordinary tables. A WAL, shared-memory or journal sidecar that is not a regular file, or a hot rollback journal, makes the database unreadable with a diagnostic instead of being followed or replayed. SQLite locators identify a table, rowid and key. Recognized keys include `bubbleId:*`, `composerData:*`, `composer.composerData`, `aiService.prompts` and selected workbench chat keys. Index-only or unfamiliar chat values can produce a diagnostic.

### omp, pi, senpi and OmO

oh-my-pi (omp) and pi write the same JSONL session format, and senpi and OmO (which runs senpi with the agent directory `~/.omo/agent`) are pi forks that keep it. One collector, `omp-pi`, reads them all. `agent` names the product from the folder: `omp`, `pi`, `senpi` or `omo`. A session saved elsewhere, for example with `--session-dir` by a tool that launches omp, is recognized by its first logical record: the `session` header with a string `id`, after omp's fixed-width `title` slot when present. omp's loader rejects a file by the same check. Because this check runs on every unclaimed `.jsonl` in the evidence, not only on session folders, the header must also carry the string `cwd` and `timestamp` that omp and pi always write, and the first 64 KiB are decoded as strict UTF-8, as the session reader decodes them; a byte-order mark or UTF-16 file is not taken as a session. Such a file gets `agent` `omp` when the title slot is present and `pi-family` otherwise, because the header does not name the product. The header check reads at most the first 64 KiB of each unclaimed `.jsonl` file and runs only for this kind. An unclaimed file that cannot be opened is skipped, not reported as an unreadable omp-pi source.

The header supplies `session_id`, `cwd` and `schema_version` (the session layout version). A fork or a subagent records its parent transcript as `parentSession`, exported as `parent_session`; omp writes subagent transcripts below the parent session's folder, so `source_path` shows the nesting too. Each row keeps the tree position of its entry as `entry_id` and `parent_entry_id`. `role` is the message role. omp also records on `user` and `developer` messages who initiated the turn, exported as `attribution`: `user` for input a person typed, `agent` for text an extension generated or relayed from another agent, such as a subagent's task prompt or a parent agent's steering. A row with role `user` and `attribution` `agent` was not typed by a person; its timeline summary names both. Rows without `attribution` come from a transcript that did not record it. `model_change` sets the model for the entries below it in the tree; an assistant message's own `model` names the model that answered. A file can hold abandoned branches: omp keeps every entry when the user branches from an earlier point, and keeps entries written by another process as a side branch. As omp's loader does, the last entry in the file is taken as the leaf, and rows whose entry is not on the `parentId` chain from that leaf back to the root are exported with the flag `off-active-branch`. When the file is longer than the 64 MiB read prefix the leaf is unknown and no row is flagged. Tool calls are `toolCall` blocks in assistant messages, and `toolResult` messages carry the call ID and tool name. `bashExecution` and `pythonExecution` are commands the user ran directly: each produces a call row with role `user` and a result row. `fileMention` rows keep only the mentioned paths, not the inlined file contents. System prompts, thinking blocks, compaction and branch summaries, extension messages and state entries are not exported. An unknown entry type or message role produces a diagnostic. A file in a sessions folder whose first record is not a header produces one `session-header-missing` diagnostic and is not read further.

omp's `history.db` table `history` keeps one row per distinct prompt. Its `created_at` is the latest submission, not the first, and `use_count` is the number of submissions. `logs/omp.<date>.<pid>.log` holds one JSON record per line; rows (`agent-log`) export only the time, `level`, `pid`, `message` and `sessionId`. Other log context fields can hold request data and are omitted. Settings rows export model names only: omp `config.yml` `modelRoles` (`model` is the `default` role, `model_roles` lists every role), pi-family `settings.json` `defaultProvider` and `defaultModel`, and one row per provider in `models.yml` or `models.json` with its `model_ids`. Provider base URLs, API keys, headers and authentication settings are never exported, and `secrets.yml`, `.env`, `auth.json` and `agent.db` are not read.

### Cataly hub

Cataly supervises OMP agent sessions from Discord, Telegram and Slack. It keeps its configuration in `$XDG_CONFIG_HOME/cataly`, its state in `$XDG_STATE_HOME/cataly` and its program folder in `$XDG_DATA_HOME/cataly`. Because one account can run several hubs with different XDG bases (`.local/state/<name>/cataly`, `.config/<name>/cataly`), the collector matches the `cataly` folder at any depth and recognises each file by its name below it. Content still has to fit: a store with none of the known tables gives one `hub-tables-missing` note, a `config.toml` with none of Cataly's sections gives `unrecognized-hub-config`, and a systemd unit without a `[Service]` section gives `unrecognized-service-definition`. `agent` is `cataly-hub`.

The store is read through the same verified private SQLite snapshot as editor storage, committed WAL content included. Its schema version (`PRAGMA user_version`, one per migration) becomes `schema_version`. A column that an older schema lacks reads empty. Rows come in this order, each citing `source_table`, `source_rowid` and `snapshot_id`:

- `agent-lane` (`lanes`): `lane_key`, `state`, `outcome`, `thread`, `revision`, open time as `timestamp_utc`, `closed_utc`, and from the lane record the title (`text`), `model`, `cwd`, `worktrees`, `origin`, `run_id`, `worker`, the OMP `session_id` and `session_file`, and `spend_tokens` and `spend_usd_estimate`. Cataly records spend as its own estimate when a run ends. The brief, done checks, shell rules and grants in the record are not exported.
- `agent-lane-history` (`lane_history`): `lane_key`, `seq`, `state` and the note as `text`.
- `agent-request` (`requests`): `request_id`, `source_message` (the originating message reference), `thread`, `state` (`open` or `closed`), the open time as `timestamp_utc`, `updated_utc` and `closed_utc`. The title is the first line of the owner's message, so it is not read, nor are the lead's next step, result and notes. Backup stores are read the same way.
- `agent-question` (`questions`): `question_id`, the question as `text`, `options`, `recommended`, `request_id`, `state`, the owner's answer or choice as `answer`, and `settled_utc`.
- `agent-stream-job` (`stream_jobs`): `job_name`, the program (first `argv` entry) as `command_line`, `filter` and `restarts`. Arguments are not exported: they can hold bot tokens in URLs and unlabelled positional secrets.
- `agent-hosted-session` (`sessions`): every OMP session the hub started, with `handle`, `session_role` (`lead`, `duty` or `lane`), `runtime`, `session_name`, `model`, `cwd`, `state`, `session_id`, `session_file`, `pid`, `stop_how` and `stopped_utc`.
- `agent-hub-event` (`events`): `event_id`, `job`, `subject`, `event_kind`, `severity`, the event's one-line text, `lane_key`, `thread`, `urgent` and `dry`. Event bodies are not exported.

`thread`, `source_message` and `origin` are relay references, `<relay>:<room>` or `<relay>:<room>/<message>`. A reference to a private chat is left empty: a Telegram private chat's ID is the user's own ID, so with the relay owner it is the owner's ID, and a Slack `D` room is a direct-message conversation. Group (negative Telegram ID), channel and Discord thread references are kept. A Discord direct-message channel cannot be told apart from a channel by its ID and is kept; its ID is the channel's, not the owner's.

Relay intake, delivery and reply text (`inbox`, `deliveries`, `arrival_queue`, `outbox_parts`, `recall`, `unanswered`) are not read. `logs/events.jsonl` copies store events line by line, so the same `event_id` can appear from both sources with the same fields. `logs/hub.log` lines are `agent-log` rows with time, `level` and message only; the other key-value pairs are omitted, although Cataly already masks secrets in them. `*.err` files are an OMP session's or probe's standard error: one `agent-log` row per non-empty line with level `stderr` and no time, decoded as UTF-8 with undecodable bytes replaced. A store counts as one source for the row limit below, and its tables are read in the order above, so a very large `events` table is the part that is cut.

The hub's lead transcripts in `sessions/lead/*.jsonl` and lane transcripts are OMP session files and are not read by this collector. `session_id` and `session_file` in lane and hosted-session rows name them.

`config.toml` gives one `agent-settings` row: the lead `model`, `lanes_model`, `fallback_chains`, `log_level`, `omp_path`, the configured `token_file` paths of the relays and `[voice] key_file` as `token_files`, and the credential variable names of `[sessions]` as `env_names`. The relay owner IDs (`[discord]`, `[telegram]` and `[slack]` `owner`, the account that controls the hub) are personal identifiers and are omitted. Token and key files are listed by path only. Each `[jobs.<name>]` gives an `agent-hub-job` row with `job_name`, `job_kind`, `every`, the program (first `argv` entry) as `command_line`, `cwd_configured` and `destinations`, without private chat references. The OMP overlays give `fallback_on`, `fallback_chains`, `goal_enabled` and `eval_approval`. Files in `secrets/` (bot tokens, Slack tokens, the voice key and `service.env`) are never opened: each gives one `agent-secret-file` row with its name. A launchd agent gives `service_label`, `run_at_load`, the names of `EnvironmentVariables` and, for Cataly's `/bin/sh -c <script> <env file> <program>` wrapper, the program as `command_line` and the env file as `environment_file`; that path is what ties the agent to its hub's config folder. Another `ProgramArguments` layout gives its first entry as `command_line`. A systemd user unit gives `Description` as `service_label`, the program of `ExecStart` as `command_line`, `environment_file` and the names in `Environment=` lines. Install records give `install_version` (also `app_version`), `commit`, `target`, `binary_sha256`, `extension_sha256`, `install_source`, `install_role` and the install time. Program files in `versions/<version>/` are named, not read. Settings, overlay, service and install files are whole documents under the 8 MiB limit below; one that does not parse, such as a plist with an unknown XML encoding, gives an `invalid-document` note and the other files are still read.

In the timeline, a lane and a request each have an `opened` and, when closed, a `closed` event, every hub event is one `event`, and every timed hub log line is one `written` event (shown as 에이전트 로그, apart from journald and unified-log `logged` events).

### dori

dori (github.com/sisyphuslabs/dori-superagent) is a lead harness that runs coding-agent lanes in herdr or hc panes and takes orders over Telegram, Discord and Slack. It has two writers. The harness keeps its store in `$DORI_HOME`, default `~/.dori`. The dori-mode skill keeps its state in `stateDir`, default `~/.dori/state`. Both read `~/.dori/config.json`. The collector matches a `.dori` folder at any depth and recognises each file by its place below it. A `$DORI_HOME` or `stateDir` moved elsewhere is not searched. dori's own source checkout in `~/.dori/src` is not read. `agent` is `dori-state`.

Both writers keep one JSON record per lane in `lanes/<key>.json`, and the content tells them apart. `record_layout` names the writer.

- `agent-lane`, skill (`dori-mode`): `lane_key`, the title as `text`, `state` (`closed` once `closedAt` is set), `thread`, `model`, `cwd`, `worktrees`, the omo `session_id` and `session_via`, the pane as `session_ref`, `brief_path`, `paused_from`, the claim evidence and its time, objection reasons and time, the close receipt note, `timestamp_utc` (`openedAt`) and `closed_utc`. The done signal and the posted report lines are not exported.
- `agent-lane`, harness (`dori-harness`): `lane_key`, `state`, `session_ref`, `session_file`, `brief_path`, `nudges`, the closing answer as `result` and its `evidence`, `last_activity_utc`, `timestamp_utc` (`createdAt`) and `closed_utc`, the time of the last `done` event. The harness records no title, model or thread.
- `agent-lane-history`: one row per state change (skill `history`) or lane event (harness `log`: start, report, ready, nudge, done, lost), with `state` and the note or text.
- `agent-lane-report` (`lanes/<key>/reports.jsonl`): a lane's own report (`report_kind` milestone, blocker, question, halted or done) or an activity mark (running or stalled), with `record_type` and text.
- `agent-lane-checkpoint` (`checkpoints.jsonl`): `step`, the result as `text`, `evidence` and `remote_effects`.
- `agent-lane-usage` (`cost.jsonl`): `tokens`, `cost_usd` and `final`, as the configured usage command reported them.
- `agent-brief` (`briefs/<key>.md`, `<key>.handoff.md`, `<key>.migrate-<ms>.md`): `lane_key`, `brief_kind` and the first Markdown heading in the first 64 KiB as `text`. The brief text, handoff screen dumps and queued messages inside it are not exported. A migrate brief's time comes from its name.
- `agent-worklog` (`worklog.jsonl`): one row per event with `item_id`, `worklog_op` (add, next, note, close), the title, text or result as `text`, and on `add` the owner request reference as `source_message`. `worklog.md` is rendered from it and is not read.
- `agent-lesson` (`lessons.jsonl`): `lesson_id`, `lane_key`, `cwd` or `scope`, the rule as `text`, `evidence` and `outcome`. The file is append-only: the newest record of an ID is current.
- `agent-queued-message` (`inbox/<session>.jsonl`): a message dori queued for a lead, duty or lane session and typed into its pane. `target_ref` comes from the file name (`w1_p3` is herdr pane `w1:p3`, `hc--t7` is `hc:t7`). The row also has `sender` (`cli`, `duty` or a lane key), the message as `text`, and `delivery_state`, `delivery_detail` and `delivery_utc` of the last typing attempt. An `ambiguous` attempt is a held message.
- `agent-messenger-thread` (`slack-threads.json`): `channel_kind` `slack`, `channel`, the root message `thread_ts` as the time, and the newest seen reply as `seen_ts` and `seen_utc`. A Slack `ts` is converted exactly to the microsecond.
- `agent-messenger-offset` (`telegram-offset`): `channel_kind` `telegram` and the `next_update_id` the inbound poller asks for.
- `agent-review-receipt` (`receipts/<pr>@<sha>.json`): `pr`, `sha`, `verdict` (CLEAR or BLOCK), reviewer `model` and the output tail as `text`. A `*.noverdict.txt` reviewer output is not read; its row gives `file_name`, the encoded `pr_file_key` and `sha`, and an empty `verdict`.
- `agent-backlog-item` (`backlog/<id>.json`): `item_id`, the title as `text`, `state`, `priority`, `source_message`, `decision`, `attempts`, `brief_path`, `cwd`, `updated_utc`, `asked_utc`, and `closed_utc` once done or dropped. The brief copy `backlog/<id>.md` is not read.
- `agent-loop-run` (`loop/runs/*.json`, `loop/last-run.json`): one hourly-loop pass with `lanes`, `max_lanes`, the skip reason as `text`, and `findings`, `started`, `held`, `asked` and `synced`. `last-run.json` repeats the newest run.
- `agent-pause` (`loop/stop`, `duty/stop`): `loop_name` and the reason as `text`.
- `agent-migration` (`migrate/<name>.json`): an unfinished move of a session to another runtime, with `migration_name`, `migration_kind`, `phase`, `from_ref`, `to_runtime`, `new_ref` and `brief_path`.
- `agent-settings`: from `config.json` (and `config.json.bak*` copies), `model` (`defaultModel`), `runtime`, `state_dir`, `sessions_dir`, `default_cwd`, `lane_workspace`, the program (first `agentCommand` entry) as `command_line`, and the names in `config_keys`, `hook_names` and `repo_identities`. `agentCommand` arguments, hook argv and the commit names and e-mail addresses are not exported. From `roles.json`, `role_refs`. From `telemetry.json`, `telemetry_install_id`, `last_active_day`, `notice_shown`, `installed_sent`, `duty_counts_since_utc` and whether an ingest key is stored (`telemetry_key_stored`); the key itself is not exported.
- `agent-secret-file`: `secrets.env` and its `secrets.env.bak*` copies by name. They are never opened.
- `agent-service`: a user LaunchAgent with a `dori` label component (`com.<user>.dori-*.plist`) or a plist parked in `.dori/disabled-launchd` (`disabled` true), with `service_label`, the program (first `ProgramArguments` entry, or `Program`) as `command_line`, `run_at_load` and environment variable names. Arguments are not exported: they can hold bot tokens in URLs, unlabelled positional secrets and owner IDs. dori installs no launchd agent, so there is no known wrapper layout to read an environment file path from. A plist that does not parse leaves an `invalid-document` note; the other dori records are still collected.

dori-state exports messenger message text and chat, thread and channel IDs on purpose. Queued messages, lane reports, worklog titles, notes and results, lesson rules, lane titles, history notes and closing answers, review summaries, loop findings and pause reasons are exported as text, the way the session collectors export conversation text: they are the evidence. Lane `thread`, worklog and backlog `source_message`, lesson `evidence` and Slack `channel` carry Telegram, Discord and Slack chat or channel IDs, including the owner's. Both are personal data; treat dori-state output as personal data when sharing it. Every text field passes the redaction below and the 8,192-character text limit, but free text can still hold personal or sensitive material without a recognizable label.

dori writes no log of messenger traffic. `dori inbound` prints each Telegram or Slack message for the lead to read and `dori send` prints only a message ID, so message bodies stay in the lead's transcript and the messenger. Telegram attachments are reported as file IDs and not downloaded. Files in `.dori/inbox` other than the `*.jsonl` queues, such as pictures, and folders that dori's source never writes (`collect/`, `lane-out/`) are left to the general file collectors. Lane locks, inbox locks, the heavy-job slots, `supervision.json` and the rendered prompts are working state and are not read. dori installs no launchd agent; its loops run as sessions opened by `dori up`. A dori LaunchAgent comes from the operator's own tooling.

Times are epoch milliseconds in the harness store and in skill lane counters, and RFC 3339 text elsewhere in the skill state. In the timeline, a lane and a backlog item each have an `opened` and, when closed, a `closed` event. Lane state changes, reports, checkpoints, usage readings, worklog events, lessons, queued messages and their delivery attempts, Slack thread roots and seen replies, review verdicts, loop runs, pauses and migrations are one event each.

## Reading a row

`source_path` is relative to the evidence root. JSONL citations use a one-based physical line and zero-based byte offset. A whole JSON or TOML document starts at offset zero. Array indexes, project and server names distinguish entries within documents. SQLite rowids are logical locators.

Text messages, tool calls and tool results have distinct artifact types. An assistant message with text and two tool calls produces three rows. Structured tool arguments and patch headers supply referenced file paths. A call records a request to operate on a file. Any recorded result is a separate observation. Tool names can be associated with results by call ID within a session and file.

`timestamp_raw` preserves the source representation. `timestamp_utc` is ISO 8601 UTC with a `+00:00` offset. Text is normalized only when it is an RFC 3339 date-time with an explicit `Z` or `±HH:MM` offset (hours 00-23, minutes 00-59; an out-of-range offset such as `+01:60` is not rolled over); week dates, the basic format, a space separator and wall times without an offset are not guessed. Fraction digits are kept as recorded, padded to microseconds, so nanosecond digits are not rounded. Claude prompt history and editor values use integer epoch milliseconds and Codex history and omp prompt history integer epoch seconds, converted exactly. pi-family session rows use the entry's ISO 8601 time and fall back to the message's epoch milliseconds only when the entry has none; omp log lines record local time with its offset. Tool blocks can share the timestamp of their enclosing message. Embedded Gemini results share the recorded call time, which does not establish a separate completion time. The timeline uses only normalized evidence timestamps. A missing time stays empty. An ambiguous or invalid time carries `timestamp-not-normalized`. Missing session IDs, roles, models and paths stay empty.

`schema-version-not-validated` marks every row in this release. The input layouts have synthetic fixture coverage. A product version and a declared schema version are separate fields, copied only from the record that declares them (`version`, `cli_version`, `schemaVersion`, a VS Code chat session file's `version`, or a pi-family session header's `version`). When neither is recorded the row carries `version-unknown`; no version is inferred from field shapes. Gemini JSONL update and rewind records receive a diagnostic because reconstructing the final edited conversation requires replay. Codex user and assistant progress messages are compared with replay messages by role, exact text and occurrence count within the same turn of the same file. A turn starts at a `turn_context` record and is identified by its recorded `turn_id` (a context repeated with the same `turn_id` continues the turn); without one, each `turn_context` starts a new turn. A replay never stands in for a progress message of another turn. When one turn holds more progress copies of a message than replays, the earliest copies are paired and each remaining copy carries `replay-pairing-ambiguous`, because the source does not record which copy a replay duplicates. If a progress message is present, a second bounded pass counts up to 20,000 replay messages. Independent prompt history may document the same interaction. pi-family sessions are trees: every recorded entry is exported in file order, including branches the session later abandoned, and `context_edit` replacements are not applied.

## Bounds and privacy

| Scope | Limit and behavior |
| --- | --- |
| JSONL | 64 MiB prefix per source, 1 MiB per physical line including its delimiter. Oversized lines are drained in bounded chunks. Malformed UTF-8, malformed JSON and oversized lines produce cited diagnostic rows with a damage count. |
| Whole JSON, TOML or YAML | 8 MiB per document. Larger documents produce a diagnostic. Without PyYAML installed, a YAML document produces a `parser-unavailable` diagnostic and the other sources are still read. |
| SQLite | 256 MiB for the database and sidecars combined, 2 MiB per selected value. Oversized inputs produce diagnostics. |
| Output | 20,000 rows per source and kind, then a limit diagnostic. Text fields hold up to 8,192 characters and lists up to 64 entries. Tool-name correlation retains up to 1,024 call IDs per source. |

MCP rows select server names, executable commands and environment variable names. Environment values, server arguments, headers and connection URLs are omitted. Every exported text field, including commands, file paths and tool results, passes redaction before it reaches a row: Rapid's URL credential redaction, the whole value of `Authorization`, `Proxy-Authorization`, `Cookie` and `Set-Cookie` headers in any scheme, credential assignments and option values (API keys, access and secret keys, tokens, passwords), bearer and basic credentials, private key blocks, JSON Web Tokens, AWS access key IDs, Telegram bot tokens (also inside a `/bot<token>/` URL path), Discord bot tokens and common token prefixes (`sk-`, GitHub, GitLab, Slack, Google, Hugging Face, npm). Arbitrary free text and command lines can still contain sensitive material without a recognizable label.
