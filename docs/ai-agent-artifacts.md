# AI coding-agent artifacts

Point the collector at a mounted or exported evidence directory containing the profile trees. Select a kind with the normal artifacts command.

```sh
python -m rapidtriage artifacts ./sample-evidence --kind codex-cli --output ./artifacts-codex-cli.json
```

The execution section of the evidence tree includes these kinds. Seizure, fraud, hacking and recovery runs schedule them.

| Kind | Evidence-relative paths | Records |

| `codex-cli` | `.codex/sessions/**/*.jsonl`, `.codex/history.jsonl`, `.codex/config.toml` | Replay messages, function and custom tool calls and results, turn model and working directory, prompt history and settings |

The editor may appear under Windows `AppData/Roaming`, macOS `Library/Application Support` or Linux `.config` in the evidence. The recognized product directories are Cursor, Code, Code - Insiders and VSCodium. Product directories can belong to any profile. Discovery matches path components below the evidence root only; the examiner's own home directory and environment are never consulted, and symbolic links that leave the evidence root are skipped. The collector reads a verified private SQLite snapshot, includes committed WAL content and queries only ordinary tables. A WAL, shared-memory or journal sidecar that is not a regular file, or a hot rollback journal, makes the database unreadable with a diagnostic instead of being followed or replayed. SQLite locators identify a table, rowid and key. Recognized keys include `bubbleId:*`, `composerData:*`, `composer.composerData`, `aiService.prompts` and selected workbench chat keys. Index-only or unfamiliar chat values can produce a diagnostic.

### Orca Bots

Orca (github.com/stablyai/orca) is an agent IDE whose bots take requests from Slack, GitHub, Linear and Discord and run coding agents (Claude Code, Codex and others) in git worktrees. It keeps its state in Electron's userData folder (`<appData>/orca`, `orca-dev` for development builds; `app.setName` may write it as `Orca`) and each bot's home in `~/.orca/bots/<folder>`. A non-standard userData folder keeps the bot homes in `<userData>/bots`. The collector matches the userData folder below `Library/Application Support`, `AppData/Roaming` or `.config`, and `.orca` at any depth. Folders moved by `--user-data-dir` or `ORCA_DEV_USER_DATA_PATH`, and shared-home server folders (`~/.orca-<hex>`), are not searched. `agent` is `orca-bots`.

A bot's agent conversations stay in that agent's store. `session_id` on bot, item, memory change and run rows is the Orca chat or agent session the row belongs to.

- `agent-bot`: from the profile state (`profile_state_documents` rows `bots` and `botsNewerAgents` in `profile-state.db`, or the same keys in `orca-data.json`; `record_layout` `profile-state` or `orca-data`): `bot_id`, the name as `text`, `bot_folder`, `bot_agent`, `model` (`launch.model`), `permission_mode` (`ask`, `accept-edits`, `auto`, `full-access`; empty is the agent default), `paused`, `trigger_channels` (`slack`, `linear`, `github`), `slack_teams`, `linear_workspaces`, `member_count` and `member_sources`, `google_access`, `look_around`, `template_id`, the bot's chat as `session_id`, `timestamp_utc` (`createdAt`) and `updated_utc`. Member names and IDs are not exported. From `bot.json` in the home (`record_layout` `bot-home`), which Orca regenerates from the record: `bot_id`, name, `bot_agent`, `member_count` and `member_sources`.
- `agent-bot-memory-file` (`SOUL.md`, `MEMORY.md`, `memory/<topic>.md`): `bot_folder`, `memory_file`, `memory_role` (`soul`, `memory`, `memory-topic`), `file_bytes` and the text. At most the first 64 KiB is read; the text passes the usual redaction and length limit. `AGENTS.md`, `CLAUDE.md` and `.orca/bot-tools.json` in the home are generated or name credential IDs and are not read.
- `agent-bot-memory-change` (`bot-memory-history/<bot ID>.json`, kept 90 days): `bot_id`, `change_id`, `author_kind` (`chat`, `kept`, `owner`, `bot`, `undo`, `tidy-up`), `speaker` (the outside person speaking in that chat window; empty is the owner), `undo_of`, `added_lines`, `removed_lines` and `undoable`. Orca already redacts secret-looking lines here; the lines also pass Rapid's redaction.
- `agent-bot-item` (`bot-items.sqlite` `items` and `item_links`): `item_id`, `item_number`, `bot_id`, the title as `text`, `description`, `done_means`, `state` (`planned`, `working`, `needs_you`, `done`, `canceled`), `close_note`, `item_source` and `item_source_title` (where the request came from), `made_by_bot`, `pr_links`, `url_links`, `file_links`, `dispatch_ids`, the item's chat as `session_id`, and `updated_utc`, `closed_utc`, `last_activity_utc` and `snoozed_until_utc`.
- `agent-bot-item-event` (`item_events`): `item_id`, `event_kind` (`made`, `edited`, `status`, `commented`, `linked`, `snoozed`, `unsnoozed`), `actor_kind` (`bot`, `owner`, `orca`), `actor_bot`, `actor_reason`, `status_from`, `status_to`, a comment's text or a status note as `text`, and the other data by key name in `event_keys`.
- `agent-bot-work` (`bot-work.sqlite` `bot_work`): a conversation on a channel linked to the orchestration task and dispatch that work it: `bot_id`, `channel_kind` (`slack`, `github`, `linear`, `discord`), `external_id` (thread or issue), `generation`, `task_id`, `dispatch_id`, `host`, `asked_in_app`, `current`, `close_reason` and `closed_utc`. The file holds no request text.
- `agent-bot-request` (`orchestration.db` `bot_requests` with `bot_request_outcomes`): `message_id`, `root_key`, `from_bot_id` and `from_bot_name`, `to_bot_id` and `to_bot_name`, `purpose` (`status`, `handoff`, `question`), `depth`, the original request as `text`, and `outcome` (`answered`, `posted`, `unanswered`, `dropped`) with `outcome_utc`.
- `agent-bot-dispatch` (`orchestration.db` `worker_dispatches`): `dispatch_id`, `state`, `stage`, `worktree_id`, `worktree_path` (the part after `::` in Orca's `<repo ID>::<path>` worktree ID), the last error as `text`, and `updated_utc`. Start options, effects and terminal handles are not exported.
- `agent-bot-run` and `agent-bot-suggestion` (`bot-look-around.json`): background look-around and nightly tidy-up runs with `run_kind`, the run's agent session as `session_id`, `ended_utc`, the error as `text`, `asleep` and `usage_limited`; and the suggestions they left with the title as `text`, `why`, `ask`, `link`, `channel_kind`, `state` and `resolved_utc`. Dismissals are not exported.
- `agent-cloud-profile` (`orca-profile-index.json`): `profile_id`, the name as `text`, `profile_kind` (`local`, `cloud-linked`), `active`, and for a linked profile `cloud_user_id`, `cloud_profile_id`, `cloud_email`, `cloud_display_name`, `cloud_org_id`, `cloud_org_name` and `linked_utc`, with `last_opened_utc`.
- `agent-secret-file`: the Orca Cloud session `profiles/<id>/account-session.json.enc` with `profile_id`, `session_format` (`electron-safe-storage-v1`, `orcad-host-key-v1`, or `dev-plaintext-v1` in development builds) and `saved_utc`; the ciphertext and any plain session are not exported. `connector-host-key.json` (the connector's private key), `.orca/linear-token.enc`, `.orca/linear-tokens/*.enc` and `.orca/bitbucket-credential.enc` are named only and never opened.

SQLite stores are read from a verified private snapshot like the editor stores. `bot-items.sqlite` (3 at `c46704e1`), `orchestration.db` (49) and `profile-state.db` (3) record their migration count in `user_version`, given as `schema_version`; `bot-work.sqlite` adds columns instead and records none. Bot, item and look-around times are epoch milliseconds; `orchestration.db` times are SQLite `datetime('now')` UTC text, kept as `timestamp_raw`. Other profile state (settings, sessions, SSH relays, worktree metadata), the GitHub cache, the connector outbox, terminal history, the native chat journal and the trace logs in `logs/` are not read. In the timeline a bot and an item are `created` and `last-updated` (an item also `completed`), conversation links, dispatches and runs `started` and `ended` or `last-updated`, item events `event`, requests `sent` and `completed`, memory changes `modified`, suggestions `created`, linked accounts `created`, `last-opened` and `linked`, and a cloud session file `session-saved`.

## Reading a row

`source_path` is relative to the evidence root. JSONL citations use a one-based physical line and zero-based byte offset. A whole JSON or TOML document starts at offset zero. Array indexes, project and server names distinguish entries within documents. SQLite rowids are logical locators.

Text messages, tool calls and tool results have distinct artifact types. An assistant message with text and two tool calls produces three rows. Structured tool arguments and patch headers supply referenced file paths. A call records a request to operate on a file. Any recorded result is a separate observation. Tool names can be associated with results by call ID within a session and file.

`timestamp_raw` preserves the source representation. `timestamp_utc` is ISO 8601 UTC with a `+00:00` offset. Text is normalized only when it is an RFC 3339 date-time with an explicit `Z` or `±HH:MM` offset (hours 00-23, minutes 00-59; an out-of-range offset such as `+01:60` is not rolled over); week dates, the basic format, a space separator and wall times without an offset are not guessed. Fraction digits are kept as recorded, padded to microseconds, so nanosecond digits are not rounded. Claude prompt history and editor values use integer epoch milliseconds and Codex history integer epoch seconds, converted exactly. Tool blocks can share the timestamp of their enclosing message. Embedded Gemini results share the recorded call time, which does not establish a separate completion time. The timeline uses only normalized evidence timestamps. A missing time stays empty. An ambiguous or invalid time carries `timestamp-not-normalized`. Missing session IDs, roles, models and paths stay empty.

`schema-version-not-validated` marks every row in this release. The input layouts have synthetic fixture coverage. A product version and a declared schema version are separate fields, copied only from the record that declares them (`version`, `cli_version`, `schemaVersion`, or a VS Code chat session file's `version`). When neither is recorded the row carries `version-unknown`; no version is inferred from field shapes. Gemini JSONL update and rewind records receive a diagnostic because reconstructing the final edited conversation requires replay. Codex user and assistant progress messages are compared with replay messages by role, exact text and occurrence count within the same turn of the same file. A turn starts at a `turn_context` record and is identified by its recorded `turn_id` (a context repeated with the same `turn_id` continues the turn); without one, each `turn_context` starts a new turn. A replay never stands in for a progress message of another turn. When one turn holds more progress copies of a message than replays, the earliest copies are paired and each remaining copy carries `replay-pairing-ambiguous`, because the source does not record which copy a replay duplicates. If a progress message is present, a second bounded pass counts up to 20,000 replay messages. Independent prompt history may document the same interaction.

## Bounds and privacy

| Scope | Limit and behavior |
| --- | --- |
| JSONL | 64 MiB prefix per source, 1 MiB per physical line including its delimiter. Oversized lines are drained in bounded chunks. Malformed UTF-8, malformed JSON and oversized lines produce cited diagnostic rows with a damage count. |
| Whole JSON or TOML | 8 MiB per document. Larger documents produce a diagnostic. |
| SQLite | 256 MiB for the database and sidecars combined, 2 MiB per selected value. Oversized inputs produce diagnostics. |
| Output | 20,000 rows per source and kind, then a limit diagnostic. Text fields hold up to 8,192 characters and lists up to 64 entries. Tool-name correlation retains up to 1,024 call IDs per source. |

MCP rows select server names, executable commands and environment variable names. Environment values, server arguments, headers and connection URLs are omitted. Every exported text field, including commands, file paths and tool results, passes redaction before it reaches a row: Rapid's URL credential redaction, the whole value of `Authorization`, `Proxy-Authorization`, `Cookie` and `Set-Cookie` headers in any scheme, credential assignments and option values (API keys, access and secret keys, tokens, passwords), bearer and basic credentials, private key blocks, JSON Web Tokens, AWS access key IDs and common token prefixes (`sk-`, GitHub, GitLab, Slack, Google, Hugging Face, npm). Arbitrary free text and command lines can still contain sensitive material without a recognizable label.
